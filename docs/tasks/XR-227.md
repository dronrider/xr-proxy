# XR-227: Нет валидации конфига при старте: битый config.toml, пустой ключ или мусорный salt валят процесс на боевом старте, procd/systemd крутят рестарт, deploy проверяет только pgrep. Добавить подкоманду validate/--check-config (dry-run парсинга и ключей без подъёма листенеров)

## Что происходит

Битый config.toml, пустой ключ или мусорный salt валят процесс на боевом
старте, а procd и systemd крутят рестарт бесконечно. Deploy проверяет
живость только pgrep, поднимутся ли листенеры, он не видит.

## Чего хотим

Подкоманда validate (или `--check-config`): сухой прогон парсинга
и проверки ключей без подъёма листенеров, с ненулевым кодом и названной
причиной на битый конфиг. Обвязка (deploy, init) получает способ проверить
конфиг до старта. Задача из состава цели XR-286, конвейер идёт по её файлу.

## DoD

- Подкоманда validate есть у xr-server и xr-client, проверяет конфиг
  целиком: парсинг, ключи, salt, адреса; листенеры не поднимаются.
- Битый конфиг даёт ненулевой код возврата с причиной, годный конфиг
  отвечает ok.
- Интеграционный тест: битый и годный конфиги дают ожидаемые коды
  и сообщения.

## Тесты

Причинная часть покрыта в три слоя. Юниты в `xr-proto/src/config.rs`
(модуль `tests`) закрывают годный конфиг, пустой пул, пустой и мусорный
ключ, чужой модификатор, соль вне u32, домен в адресе сервера, override
ключа у записи пула, адрес VPS у включённого relay и конфиг сервера.
Интеграционные прогоны субкоманды идут на живых бинарях, это
`xr-server/tests/validate_cli.rs` и `xr-client/tests/validate_cli.rs`.
Годный конфиг даёт `ok` и код 0. Битый даёт код 1 с причиной. Причины
перебирают мусор TOML, пустой ключ, соль вне u32, адреса, отсутствующий
файл и override ключ записи. Стенд init в `xr-setup/src/render.rs`
держит два теста. `init_validates_config_before_start` гонит годный
конфиг до киллсвитча и перехвата, отметка проверки видна в логе.
`init_refuses_invalid_config_before_killswitch` ждёт от битого конфига
отказа с причиной, правила не встают.

- Исключение: тесты (ворота слияния узнают тестовые файлы по суффиксам
  `_test.go/.py/.sh`, а Rust-тесты в `tests/*.rs` и модулях `#[cfg(test)]`
  не видит).

## Ревью

- validate у xr-client мягче старта: глобальная тройка [obfuscation] проверяется только как fallback записи пула, и когда у всех [[servers]] стоит свой key или modifier, битый общий ключ или модификатор validate пропускает, а обычный старт валит: старт декодирует их безусловно при построении Obfuscator (xr-client/src/main.rs, до цикла пула). Пруф на бинаре ветки: конфиг с [obfuscation] key = "" и key = "dGVzdA==" у единственной записи даёт validate -> ok с rc=0, а обычный старт -> FATAL: key must not be empty с rc=1; то же с modifier = "garbage" глобально и валидным override у записи (FATAL: unknown modifier strategy). Прошу проверять глобальную тройку obfuscation в validate_client_config безусловно, до цикла записей, и закрыть юнит-тестом конфига с override у всех записей и битым общим ключом: без этого не держится фраза AGENTS.md о том, что validate и старт не расходятся.: исправлено, коммит 6d1e38a3: глобальная тройка [obfuscation] проверяется безусловно до цикла пула, юнит validate_checks_shared_obfuscation_behind_full_override и интеграционный broken_shared_obfuscation_fails_behind_server_overrides закрывают кейс, regcheck красит код ревью и проходит на правке

Второй проход, без замечаний. Глобальная тройка [obfuscation] проверяется безусловно, до цикла пула. Причины именуются секцией obfuscation. Два старых теста ждут теперь эту секцию вместо записи пула. Ожидания поменялись вместе с владельцем значения, подмены нет. Кейс первого прохода перепроверен на живом бинаре правки. При override у всех записей пустой общий ключ даёт validate -> rc=1 с причиной. Мусорный общий модификатор даёт то же. ## Сценарий проверки

Агентский, после выката (машины из `local-docs/fleet.ini`).

1. Годный конфиг на роутере: `ssh ROUTER /usr/bin/xr-client validate -c /etc/xr-proxy/config.toml` печатает `ok`, код возврата 0.
2. Битый ключ без риска для прода, конфиг пишется в /tmp, живой не трогается: `ssh ROUTER 'printf "[obfuscation]\nkey = \"\"\n\n[routing]\ndefault_action = \"direct\"\n\n[[servers]]\naddress = \"192.0.2.1\"\nport = 8443\n" > /tmp/xr-bad.toml && /usr/bin/xr-client validate -c /tmp/xr-bad.toml; echo rc=$?'` отвечает в stderr `config invalid: servers '192.0.2.1'.key: key must not be empty` и печатает `rc=1`.
3. Мусорный salt в той же копии: `ssh ROUTER 'printf "[obfuscation]\nkey = \"dGVzdA==\"\nsalt = 99999999999\n\n[routing]\ndefault_action = \"direct\"\n\n[[servers]]\naddress = \"192.0.2.1\"\nport = 8443\n" > /tmp/xr-bad.toml && /usr/bin/xr-client validate -c /tmp/xr-bad.toml; echo rc=$?'` отвечает `does not fit in u32` и `rc=1`.
4. Init ходит проверкой до правил: `ssh ROUTER '/etc/init.d/xr-proxy restart && logread | grep xr-proxy | tail -5'` содержит `config validation ok`, юнит после перезапуска жив (`pgrep -x xr-client` непуст).
5. Диагностика называет шаг: `ssh ROUTER sh /tmp/xr-diagnose.sh` (скрипт раскладывает deploy) в разделе «2. Конфиг» печатает `[OK] xr-client validate: ok`.
6. Сервер: `ssh VPS /usr/local/bin/xr-server validate -c /etc/xr-proxy/server.toml` печатает `ok`; битая копия `ssh VPS 'cp /etc/xr-proxy/server.toml /tmp/xr-bad.toml && sed -i "s/^listen.*/listen = \"not an address\"/" /tmp/xr-bad.toml && /usr/local/bin/xr-server validate -c /tmp/xr-bad.toml; echo rc=$?'` отвечает `invalid listen address` и `rc=1`.
7. Systemd видит причину: `ssh VPS 'systemctl restart xr-proxy-server && systemctl status xr-proxy-server --no-pager | head -5'` показывает active, а журнал юнита содержит строку успешного ExecStartPre; при желании убедиться в отказе можно на /tmp-копии из шага 6, живой конфиг не трогая.
