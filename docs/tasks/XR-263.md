# XR-263: xr-web: новый крейт на VPS, вход владельца по cookie-сессии на поддомене публикации, кеш маршрутов и пул соединений relay плюс pinned-TLS, проксирование HTTP до агента, страницы входа и ошибок, раскладка xr-setup --with-web с юнитом (LLD-38 фаза 2)

## Ход работы

- Исполнение: субагент opus/high по вердикту pick (квота: week_all 42%, снимок 30м назад, сдвига нет), 2026-08-06.
- Написан крейт `xr-web/`: листенер, вход и сессии, кеш маршрутов, пул
  соединений до агента, проксирование, вшитые страницы. Раскладка профилем
  `xr-setup server --with-web`, юнит `deploy/xr-web.service`, образец конфига
  `configs/web.toml`, дока в `ARCHITECTURE.md` (раздел 4.10) и `HUB-DEPLOY.md`.
- Фундамент XR-267 взят как есть: `relay_tls_connect`, `WebRoute`,
  `web_share_id`, служебные ручки хаба. Из правок в чужих крейтах только
  `encode_expose_mandate` в `xr-proto` (форма блоба мандата переехала к типу,
  хабовый `encode_mandate` теперь зовёт её) и `xr-web` в `CRATES` скрипта
  раздачи: без этого бинарь не доедет до `--with-web` на чужой машине.

## Решения

- **Метка `s` зарезервирована.** `s.<домен>` это будущий путь шар (фаза 4,
  XR-265), и публикацией эта метка не считается уже сейчас: иначе имя `s` в
  реестре хаба однажды перехватило бы весь путь шар, и чинить это пришлось бы
  ломая живой поддомен. Сейчас на этом хосте отказ с названной причиной.
- **Гейт сессии стоит раньше похода в хаб.** Неизвестная публикация без сессии
  получает форму входа, а не `404`: маршрут у хаба спрашивают только за гейтом,
  поэтому чужой браузер не может гонять хаб запросами по перебору имён. Цена в
  том, что «нет такой публикации» владелец видит после входа.
- **Аренда соединения живёт в теле ответа.** `LeasedBody` держит `Lease` до
  последнего кадра, поэтому соединение не вернётся в пул на середине чужого
  ответа. Отвергнутый вариант: возвращать по получении заголовков (проще, но
  ровно этим ломает keep-alive) и не пулить вовсе (каждый запрос страницы платит
  RTT через VPS, ради чего пул в п. 3.6 и заведён).
- **Свой `[tls]` через `tokio-rustls`, а не `axum-server`.** `axum-server` с
  `tls-rustls` тянет aws-lc, а в процессе уже живёт ring из пиннинга агента;
  два провайдера в одном процессе ссорятся за умолчание. Ручной акцептор это
  тридцать строк, и он всё равно нужен: без своего цикла accept адрес браузера
  не положить в запрос.
- **Адрес браузера приходит расширением запроса, а не `ConnectInfo`.** Так он
  одинаково берётся у сокета (без фронта) и из `X-Forwarded-For` (за фронтом), а
  тесты гоняют роутер напрямую.
- **`X-Forwarded-For` до агента не едет** и снимается вместе с `X-Real-IP` и
  `Forwarded`: адрес браузера остаётся на VPS (п. 2.3), а приложение за
  апстримом не должно принимать за адрес клиента то, что ему написал кто угодно.
- **Общий секрет генерирует установщик и кладёт в оба конфига.** Конфиг хаба
  целиком не перерисовывается (хеш пароля админки из него не восстановить),
  поэтому блок `[web]` дописывается в конец шагом `AppendBlock`. Повторный
  запуск берёт уже стоящий секрет, а разъехавшиеся секреты установщик не чинит
  молча: он называет оба файла и команду перезапуска находкой.
- **Отвергнуто: единый вход через отдельный хост** (п. 8 дизайна) и свой лимит
  попыток вместо хабового. Первое дороже пользы при одной-двух публикациях,
  второго мало: лимит стоит на обеих сторонах, потому что фронтов может стать
  больше одного, а учётка одна.

## Тесты

Инлайновые, без сети: агент это половинка `duplex` с HTTP/1.1-сервером, хаб это
подставной `HubApi` со счётчиками вызовов. `test_web_requires_session`,
`test_web_session_cookie_is_host_only`, `test_web_route_cache_and_refresh`,
`test_web_agent_offline_page`, `test_web_login_rate_limit`, проксирование
заголовков, служебные пути, переиспользование соединения и `detach` под фазу 3,
раскладка установщика и находки. Типовые мутации прогнаны руками: cookie без
`SameSite`, нулевой запас кеша, сессия без сверки публикации, неснятый
`X-Forwarded-For`. На каждой падал хотя бы один тест.

## Сценарий проверки (агентский, DoD цели XR-266 п. 3)

Прогнан живьём на маке 2026-08-06 целиком: хаб, relay, агент с публикацией и
`xr-web` на loopback, сеть за пределами машины не нужна. DNS не нужен тоже,
имя публикации подставляется заголовком `Host`.

Стенд ($S это пустой каталог, порты 18099 хаб, 18444 relay, 18443 агент, 18765
локальный сервис, 18090 фронт):

```bash
cd <worktree>
cargo test --workspace --exclude xr-client          # зелёный, 0 warnings
cargo build -p xr-hub -p xr-relay -p xr-web
cargo build -p xr-share --features relay
BIN=$PWD/target/debug

# 1. Хаб: конфиг как в XR-267 (админ owner с паролем стенда в $PASS, ключ
#    подписи, [relay] на 127.0.0.1:18444) плюс блок браузерного входа
cat >> $S/hub.toml <<EOF
[web]
domain = "web.test"
shared_secret = "s3cret"
EOF
$BIN/xr-hub --config $S/hub.toml & sleep 2
B=http://127.0.0.1:18099/api/v1

# 2. Relay с ключом хаба (curl $B/public-key отдаёт голый base64) и той же
#    обфускацией, что в [relay.obfuscation] хаба
$BIN/xr-relay --config $S/relay.toml &

# 3. Агент: reg-token в админке, install, публикация на локальный сервис
SESSION=$(curl -s -X POST $B/auth/login -H 'content-type: application/json' \
  -d "{\"username\":\"owner\",\"password\":\"$PASS\"}" | jq -r .token)
REG=$(curl -s -X POST $B/admin/shares/reg-token -H "Authorization: Bearer $SESSION" \
  -H 'content-type: application/json' -d '{}' | jq -r .token)
$BIN/xr-share -c $S/agent.toml install --hub http://127.0.0.1:18099 --token $REG \
  --listen 127.0.0.1:18443 --no-service --non-interactive
echo 'живая страница дашборда' > $S/site/index.html
(cd $S/site && python3 -m http.server 18765 &)
$BIN/xr-share -c $S/agent.toml expose add --name dash --upstream 127.0.0.1:18765
$BIN/xr-share -c $S/agent.toml &      # ждать строки «registered on relay»

# 4. Фронт
cat > $S/web.toml <<EOF
[web]
bind = "127.0.0.1:18090"
domain = "web.test"
hub_url = "http://127.0.0.1:18099"
shared_secret = "s3cret"
EOF
$BIN/xr-web --config $S/web.toml &     # в логе «хаб ... принял секрет, публикаций: 1»
```

Проверка и ожидаемый вывод (совпал построчно):

```bash
W=http://127.0.0.1:18090; H='Host: dash.web.test'
curl -s -H "$H" $W/.xr-web/healthz                                   # ok
curl -s -H "$H" -H 'Accept: application/json' $W/                    # {"error":"unauthenticated"}, код 401
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" $W/                 # 200 (форма входа)
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" \
     -d 'username=owner&password=nope' $W/.xr-web/login              # 401
curl -si -H "$H" -d "username=owner&password=$PASS" \
     $W/.xr-web/login | grep -i set-cookie
# set-cookie: xrweb=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800  (без Domain)
TOK=<токен из cookie>
curl -s -H "$H" -b "xrweb=$TOK" $W/                                  # живая страница дашборда
curl -s -H 'Host: notes.web.test' -b "xrweb=$TOK" $W/ | grep -c Вход # 1 (чужая публикация просит вход)
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" -b "xrweb=$TOK" $W/.xr-web/nope   # 404
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H "$H" -b "xrweb=$TOK" $W/.xr-web/logout  # 303
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" -H 'Accept: application/json' \
     -b "xrweb=$TOK" $W/                                             # 401 после логаута
pkill -f "xr-share -c $S/agent.toml"                                  # выключить агента
curl -s -w '\nHTTP %{http_code}\n' -H "$H" -b "xrweb=<свежий токен>" $W/
# страница «Машина не на связи», HTTP 502, за 1 мс, не таймаутом
```

В логе фронта на этом прогоне: вход с адресом (успех и промах),
`dash GET / -> 200 за 16 мс`, следующий запрос по тому же соединению
`dash GET /index.html -> 200 за 6 мс` (пул работает), `туннель dash: relay:
agent offline` перед `502`. Тел, query-строк и cookie в логе нет.
