# XR-268: check-browser-entry.py считает Sec-WebSocket-Accept по неверному магическому GUID (258EAFA5-E914-47DA-95CA-5AB0DC85B11F вместо 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 из RFC 6455): ошибка симметрична, тот же GUID стоит в эхо-сервисе скрипта, поэтому на стенде проверка зелёная, а против настоящего сервера рукопожатие объявляется несошедшимся. Найдено на живой проверке цели XR-266

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 45%, снимок 10ч 32м назад, протух, сдвига нет), 2026-08-07.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 45%, снимок 10ч 55м назад, протух, сдвига нет), 2026-08-07.

## Что сделано

Константа `WS_GUID` в [check-browser-entry.py](../../scripts/check-browser-entry.py)
исправлена на верную из RFC 6455 (раздел 1.3):
`258EAFA5-E914-47DA-95CA-C5AB0DC85B11`. Вычисление `Sec-WebSocket-Accept`
(SHA-1 от склейки ключа с GUID, дальше base64) сведено в одну функцию
`ws_accept(key)`, её теперь зовут оба места, где раньше стояла своя копия
формулы: сверка ответа сервера в режиме `ws` и подсчёт ответа в эхо-сервисе
режима `echo-service`. Разъехаться им заново негде, менять есть что менять
только в одном месте.

Тестов у скрипта не было вовсе, заведены в
[check_browser_entry_test.py](../../scripts/check_browser_entry_test.py)
рядом со скриптом, по раскладке devkit (`<имя>_test.py`, `unittest`, модуль
грузится через `importlib.util.spec_from_file_location`, потому что имя
скрипта с дефисами). Главный тест сверяет `ws_accept` с эталонным вектором
из самого RFC 6455 (ключ `dGhlIHNhbXBsZSBub25jZQ==` -> ответ
`s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`), то есть с внешней истиной, а не со вторым
местом того же скрипта: именно так была устроена исходная ошибка, симметричная
и потому невидимая при сверке скрипта с самим собой.

Поведение скрипта в `docs/ARCHITECTURE.md` и `docs/HUB-DEPLOY.md` описано верно
и без деталей формулы `Sec-WebSocket-Accept` - править там нечего.

## Проверка красноты

Со старым значением GUID (`258EAFA5-E914-47DA-95CA-5AB0DC85B11F`) тест падает
на обеих проверках - и на эталонном векторе RFC, и на самом значении константы:

```
FAIL: test_guid_matches_rfc
AssertionError: '258EAFA5-E914-47DA-95CA-5AB0DC85B11F' != '258EAFA5-E914-47DA-95CA-C5AB0DC85B11'
FAIL: test_rfc6455_sample
AssertionError: 'tF+4yo8PvjWV9zMFht911yVrKKY=' != 's3pPLMBiTxaQ9kYGzzhZRbK+xOo='
```

С исправленной константой (текущий код) обе проверки зелёные.

## Сценарий проверки

```
cd scripts && python3 -m unittest discover -p '*_test.py' -v
```

Ожидается `OK`, 2 теста. Живая проверка входа целиком (`ws`/`offline` против
настоящего сервера) остаётся тем же сценарием, что в `docs/HUB-DEPLOY.md`;
починка этой задачи и есть то, из-за чего он раньше ложно объявлял
рукопожатие несошедшимся против боевого .NET HttpListener.
