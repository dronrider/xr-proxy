# XR-300: Весь трафик Mac уходит в туннель независимо от настроек приложений

Модель: max (решение человека 2026-10-14: максимальный бюджет серии)
Эффорт: max

## Что происходит

Макбук работает в двух кейсах. Дома роутер сам заворачивает чувствительный трафик на сервер xr-proxy. В чужой сети идёт подключение через другие точки доступа, и тут возможна утечка. Перехват у xr-client сегодня линуксовый, iptables на OpenWRT. Ядро кроссплатформенное, iOS-спайк закрыт и оставил профиль ядра в docs/lld/39-ios-core-spike.md, слоя для macOS нет. На доске стоит XR-017 «Клиент под macOS».

Проверил 2026-10-13. Перехват клиента живёт в xr-client/src/redirect.rs и udp_relay.rs и построен на iptables и nft, слоя для macOS нет. На доске рядом стоит XR-017 «Клиент под macOS», тип LLD, файла задачи нет, строка не двигалась 85 дней. Такой клиент строится приложением с Network Extension. Граница между строками на момент проверки неочевидна.

Без системного перехвата гарантия падает до «каждое приложение настроено». Один забытый процесс, и запрос уходит с чужой точки доступа.

## Чего хотим

Mac из любой сети гонит весь трафик через туннель приложения на сервер. Поведение дома и в чужой сети одинаковое. Приложение без настроек не утекает, резолв доменов идёт через туннель. Падение туннеля не открывает прямой выход. Без туннеля соединения рвёт отдельный фильтр.

## Границы

Цифры и выводы iOS-спайка на macOS не переносятся. Платформа своя, и слой перехвата свой.

Раздельный туннель по приложениям остаётся строкой XR-016. Здесь весь IP-трафик уходит в туннель целиком, выбор приложений не входит.

Опыт XR-077 учитывается как история утечки при пропаже перехвата. Сам nft-скрипт роутера на Mac не переезжает.

Грумминг 2026-10-14 разрезал задачу на серию. UDP-реле в ядре живёт строкой XR-301, туннелирование IPv6 в ядре строкой XR-302. Обе стоят жёсткими предпосылками этой строки. Здесь остаётся NE-приложение macOS с хост-мостом по LLD-39, kill-switch, перехватом DNS, срезом QUIC, подписью и соседними VPN.

## Развилки

Мост через pf отпал ещё до реализации. pf не документирован Apple как публичный путь для приложений. UDP и QUIC требуют своего слушателя, IPv6 свои правила, соседство с другими VPN не закрыто. Решение от 2026-10-13 в пользу минималистичного приложения с Network Extension. Packet Tunnel Provider забирает весь IP-трафик, включая QUIC, и переживает перезагрузки штатно. Открытыми остаются объём минимального набора, ловля DNS внутри туннеля, подпись с нотаризацией. Кольца не будет, туннель до сервера роутером не перехватывается.

## DoD

- Mac в чужой сети: весь IP-трафик идёт в туннель на сервер.
- Дома поведение то же, туннель к серверу роутер не заворачивает.
- Приложение без настроек не утекает, резолв доменов идёт через туннель.
- Падение туннеля не открывает прямой выход, соединения рвёт фильтр.
- Приложение переживает перезагрузку Mac штатно.
- QUIC срезается на mac-пути, браузеры уходят на TCP через туннель.
- Остальной UDP и IPv6 уходят через туннель. Их дорога в ядре закрыта предпосылками XR-301 и XR-302.
- Соседние VPN не ломают работу приложения.
- Приложение подписано и нотаризовано и на чужой машине ставится штатно.

## Ранг

`50+8+2+0+4 = 64`, P1.

- Серьёзность 50 (Critical). Основной сценарий без задачи не работает. Один забытый процесс, и запрос уходит с чужой точки доступа. Обход через настройку каждого приложения болезненный.
- Ценность 8. Минималистичное приложение с Network Extension выбрано сознательно вместо pf, ради него задача и затевается.
- Неопределённость 2. Подход выбран, все развилки закрыты. UDP-реле и IPv6 вырезаны в XR-301 и XR-302. По NE-приложению план лежит в LLD-39 (хост-мост, профиль тюнинга ядра). Остаются детали Xcode-проекта и цикла подписи.
- Поправка на баг 0. Новый перехват трафика для macOS.
- Рычаг 4. Хост-мост по LLD-39 становится дорогой для остальных NE-приложений, вся mac-серия стоит на этой строке.

## Приёмка

- вид: mixed
- барьер «доступ»:
  - эмулятор: не годится, Network Extension на macOS не эмулируется; расширение ставится только на настоящий Mac и с подтверждением пользователя в Системных настройках.
  - синтетическая среда: годится для агентской части. Ядро, мост и чистая логика гоняются тестами на машине агента; полный пакетный путь через NE и системный диалог согласия не проверяются.
  - вторая машина контура: не годится, второго Mac в контуре нет, а подпись и нотаризация требуют учётки Apple Developer у человека.
  - стенд с подменой сети: не годится, стенд не ставит Network Extension и не подменяет системный диалог.
