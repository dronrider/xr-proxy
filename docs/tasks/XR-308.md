# XR-308. Валидация доменов пресета на хабе расходится с клиентской и серверной

## Что происходит

Парсер домена в `xr-proto` требует, чтобы у суффикса после звёздочки было
минимум две метки (`is_valid_domain` в `xr-proto/src/user_rule.rs`). Запись
`*.google` или `*.goog` классификацию не проходит. Три слоя проекта относятся
к такому домену по-разному.

Хаб принимает его в пресет. PUT на `/api/v1/admin/presets/{name}` вернул 200
и поднял версию, пресет разъехался по клиентам. Клиент в `compile_rule`
(`xr-proto/src/routing.rs`) битую запись выкидывает с WARN «Invalid domain in
config», остальное правило продолжает работать. Домен тихо не маршрутизируется,
трафик по нему уходит напрямую. Сервер ловит наоборот, слишком строго. Функция
`outbound_rule_reject_reason` называет битый домен причиной, и `validate`
отвергает конфиг целиком.

Поймано 2026-10-20 на XR-307. Хаб принял `*.google` и `*.goog` в группу
«Google», сервер собранный конфиг не принял. Увидеть это удалось только потому,
что сервер отказался стартовать; обрывись история на клиентах, домен молча не
заворачивался бы в туннель. Обход готов, TLD записывается явным доменом
(`*.antigravity.google`), боевые пресеты годные. Остался риск. Хаб как источник
пресетов примет домен, который устройства не применят, и никакой признак этого
наружу не вылезет.

## Чего хотим

Хаб валидирует домены пресета той же функцией классификации из `xr-proto`,
которой пользуются клиент и сервер. Тогда «годно» означает одно и то же на всех
трёх слоях. Битый домен отклоняется на входе: PUT отвечает ошибкой с именем
домена и причиной, пресет остаётся прежним, версия не поднимается.

## Развилки

- Отклонять весь PUT или отдельный домен. Решение предложить fail-closed, как
  у сервера. Частично применённый пресет оставил бы группу без половины
  доменов, и это снова молчаливая правка.
- Уже лежащие в базе пресеты. Боевые сейчас годные, поэтому достаточно
  валидации на входе. Разовый прогон по базе при выкатке проверить тем же
  кодом и напечатать найденное, если задача при реализации покажет его нужным.

## DoD

- PUT с битым доменом (`*.google`, `*.goog`, `a..b`) отвечает ошибкой, в тексте
  имя домена и причина; годный пресет проходит как раньше;
- автотесты хаба гоняют валидацию на битых и годных наборах;
- пресет `russia` в текущем составе принимается без правок;
- в долгоживущей доке упомянуто, что домены пресета валидируются на входе.

## Сценарий проверки

1. Автотесты хаба: битые наборы отбиваются с причиной, годный `russia`
   принимается, версия растёт только на годных.
2. Живой прогон из свежей сборки: поднять хаб локально, PUT с `*.google` даёт
   отказ, PUT с `*.antigravity.google` проходит.
- Исключение: обкатка (хаб для проверки API поднимается локально одной
  командой, стенд не нужен).

Живой прогон целиком, из корня репозитория. Хаб поднимается на 18778 с
разовым каталогом и учёткой root, логин и оба PUT идут curl'ом:

```sh
cargo build -p xr-hub
S=$(mktemp -d) && mkdir -p "$S/data"
HASH=$(./target/debug/xr-hub hash-password devpass)
cat > "$S/hub.toml" <<EOF
[server]
bind = "127.0.0.1:18778"
data_dir = "$S/data"

[admin]
[[admin.users]]
username = "root"
password_hash = "$HASH"
EOF
RUST_LOG=info ./target/debug/xr-hub --config "$S/hub.toml" > "$S/hub.log" 2>&1 &
HUB=$!
until [ "$(curl -s --max-time 1 http://127.0.0.1:18778/healthz)" = ok ]; do sleep 0.3; done

TOK=$(curl -s -X POST http://127.0.0.1:18778/api/v1/auth/login \
  -H 'content-type: application/json' \
  -d '{"username":"root","password":"devpass"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')

GOOD='{"name":"russia","description":"","rules":{"default_action":"direct","rules":[{"name":"Google","action":"proxy","domains":["*.antigravity.google","*.google.com"],"ip_ranges":[],"geoip":[]}]}}'
BAD='{"name":"russia","description":"","rules":{"default_action":"direct","rules":[{"name":"Google","action":"proxy","domains":["*.google"],"ip_ranges":[],"geoip":[]}]}}'

# заведение годного пресета: 201
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:18778/api/v1/admin/presets \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' -d "$GOOD"

# PUT с битым доменом: 400, в теле имя домена и причина
curl -s -w '\n%{http_code}\n' -X PUT http://127.0.0.1:18778/api/v1/admin/presets/russia \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' -d "$BAD"

# версия не поднялась: 1
curl -s http://127.0.0.1:18778/api/v1/presets/russia \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["version"])'

# PUT с годным доменом: 200, версия 2
curl -s -o /dev/null -w '%{http_code}\n' -X PUT http://127.0.0.1:18778/api/v1/admin/presets/russia \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' -d "$GOOD"
curl -s http://127.0.0.1:18778/api/v1/presets/russia \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["version"])'

kill "$HUB"; rm -rf "$S"
```

## Ход работы

- 2026-10-20: задача заведена из находки XR-307, пока следы свежие записаны
  слои и их поведение.
- 2026-10-20: хаб проверяет домены правил пресета классификацией из
  `xr-proto` (`normalize_pattern` + `classify_pattern`), той же, которой
  пользуются клиент и сервер. POST и PUT отвечают на битый домен ошибкой 400
  с именем и причиной, пресет и его версия остаются прежними. IP в списке
  `domains` отказывает тем же кодом, клиент такую запись выкидывает с WARN.
  Автотесты гоняют битые наборы (`*.google`, `*.goog`, `a..b`, IP в
  `domains`) и годные; эталон `configs/routing-russia.toml` прогоняется
  через ручку PUT целиком. `regcheck --inline xr-hub/src/api/presets.rs`
  показал красноту теста на старом коде. Прогон `cargo test --workspace`
  зелёный, warnings нет. Живой прогон сценария выше сошёлся. Битый PUT
  ответил 400, тело назвало домен и причину, версия осталась 1, годный PUT
  поднял её до 2.
