# XR-212: relay_direct единственный путь без idle-таймаута: ограничен только часом жизни, тогда как mux и обе стороны сервера держат idle 5 минут. Зависший direct-сокет за мобильным NAT час удерживает задачу, оба канала и запись в sessions

## Разбор корня

`relay_direct` в [session.rs](../../xr-core/src/session.rs) качал данные двумя
голыми ветками: upload ждал `data_rx.recv()` без срока, download сидел в
`tr.read()` тоже без срока. Ограничение было одно, общее на всю сессию,
`tokio::time::timeout(Duration::from_secs(3600), ...)`. Пока обе стороны молчат,
завершиться нечему: приложение уснуло, ответы из интернета за мобильным NAT
перестали доходить, FIN ниоткуда не придёт, и таск живёт час.

Час висит не только таск: за ним держатся оба mpsc-канала (по 512 буферов) и
запись в `sessions` движка, потому что снимает её именно закрытие канала
(`DownloadDrain::Disconnected` в [engine.rs](../../xr-core/src/engine.rs)). На
телефоне, где сеть перещёлкивается между LTE и Wi-Fi по нескольку раз в час, так
копятся десятки мёртвых сессий.

Соседние пути такого не допускают, и механика у них одна: каждая сторона читает
через `tokio::time::timeout(IDLE_TIMEOUT, ...)`, по простою выходит из цикла с
`Ok(())`, а общий `select!` на этом сворачивает сессию целиком. Так сделано в
`relay_mux` у xr-client ([proxy.rs](../../xr-client/src/proxy.rs)) и на обеих
сторонах сервера ([handler.rs](../../xr-server/src/handler.rs)). Direct-путь в
xr-core оказался единственным, куда это не доехало. Mux-путь того же файла
формально тоже без своего простоя, но его сворачивает сервер, у которого таймаут
стоит, а direct до сервера не доходит вовсе.

## Что сделано

Тело relay после `connect` вынесено в `relay_via_direct_stream` (симметрично
соседнему `relay_via_mux_stream`), и обе его стороны читают через
`tokio::time::timeout(IDLE_TIMEOUT, ...)`, как upstream и downstream на сервере.
По простою сторона выходит из цикла, `select!` завершает сессию с `Ok(())`,
`data_tx` роняется, движок видит закрытый канал и снимает запись из `sessions`
своим обычным путём. Константа та же, что у соседей: `IDLE_TIMEOUT` 300 секунд.
Заодно час жизни, стоявший в файле двумя литералами `Duration::from_secs(3600)`,
собран в `MAX_LIFETIME` рядом с `IDLE_TIMEOUT`.

Простой считается по каждой стороне отдельно, и молчание любой из них сворачивает
сессию. Это ровно поведение сервера, где upstream и downstream независимы, и
проксируемые сессии живут по нему давно.

Наблюдаемость: срабатывание пишется в `tracing::debug` теми же словами, что и у
соседей (`direct upload idle timeout (5m)`, `direct download idle timeout (5m)`),
а снаружи видно по счётчику активных соединений, который перестаёт копить мёртвые
сессии. Дока: в `ARCHITECTURE.md` у пункта про `session.rs` сказано, что оба пути
relay живут под теми же таймаутами, что клиент и сервер (простой 5 минут, потолок
часа), и что запись из `sessions` снимается следом за сворачиванием relay.

## Проверка красноты и мутации

Регрессионные тесты в `xr-core/src/session.rs` гоняют `relay_via_direct_stream`
на паре loopback-сокетов под `#[tokio::test(start_paused = true)]`: часы
виртуальные, сон не настоящий, ожидание сверяется по `Instant::elapsed()`.

- `direct_relay_gives_up_on_idle` это исходный случай: обе стороны молчат,
  отправители живы, EOF ниоткуда не приходит. Сессия обязана свернуться на 300
  секундах.
- `direct_relay_gives_up_when_only_upload_flows`: наверх данные идут раз в 100
  секунд, обратно тишина, сворачивает download.
- `direct_relay_gives_up_when_only_download_flows`: зеркально, сворачивает upload.

```
$ regcheck --base main --inline xr-core/src/session.rs -- cargo test -p xr-core session::tests::direct
тест краснеет на main и проходит на текущем коде, регрессия закрыта (тесты: xr-core/src/session.rs)
```

Краснота на main ложная, это несобираемость: на базе нет
`relay_via_direct_stream`, которого тесты требуют. Настоящая проверка сделана
возвратом поломки руками (мутация M1): таймауты сняты, функция оставлена, все три
теста краснеют на `left: 3600s, right: 300s`.

Мутации, каждая гонялась отдельным прогоном с восстановлением файла:

| Мутация | Кто краснеет |
|--------|--------------|
| M1: обе стороны снова читают без срока (возврат исходной поломки) | все три теста, ожидание 3600s вместо 300s |
| M2: `IDLE_TIMEOUT` 600 вместо 300 | все три теста |
| M3: таймаут только на upload | `direct_relay_gives_up_when_only_download_flows` |
| M4: таймаут только на download | `direct_relay_gives_up_when_only_upload_flows` |
| M5: простой upload отдаётся ошибкой, а не `Ok(())` | `direct_relay_gives_up_on_idle`, `direct_relay_gives_up_when_only_download_flows` |
| M6: простой download отдаётся ошибкой, а не `Ok(())` | `direct_relay_gives_up_when_only_upload_flows` |

Первая версия тестов сверяла ожидание с самой константой (`assert_eq!(elapsed,
IDLE_TIMEOUT)`) и мутацию M2 пропускала: подмена константы двигала и ожидание.
Ожидание выведено руками и записано числом.

Тесты завязаны на время, поэтому проверены на устойчивость: 40 прогонов
`cargo test -p xr-core session::tests::direct` подряд, красных нет.

## Сценарий проверки

Агентский, все шаги выполнимы с машины агента и на проде ничего не меняют.
Первый шаг воспроизводит исходную поломку.

1. Воспроизведение. Снять таймауты в `xr-core/src/session.rs` и убедиться, что
   молчащая сессия снова живёт до часа:

   ```sh
   python3 - <<'EOF'
   p='xr-core/src/session.rs'; s=open(p).read()
   s=s.replace("""            let data = match tokio::time::timeout(IDLE_TIMEOUT, data_rx.recv()).await {
                Ok(Some(data)) => data,
                Ok(None) => break,
                Err(_) => {
                    tracing::debug!("direct upload idle timeout (5m)");
                    break;
                }
            };""", """            let data = match data_rx.recv().await {
                Some(data) => data,
                None => break,
            };""")
   s=s.replace("""            let n = match tokio::time::timeout(IDLE_TIMEOUT, tr.read(&mut buf)).await {
                Ok(r) => r?,
                Err(_) => {
                    tracing::debug!("direct download idle timeout (5m)");
                    break;
                }
            };""", """            let n = tr.read(&mut buf).await?;""")
   open(p,'w').write(s)
   EOF
   cargo test -p xr-core session::tests::direct
   ```

   Все три теста обязаны упасть на `left: 3600s / right: 300s`. После
   `git checkout xr-core/src/session.rs` тот же прогон обязан пройти. Прогнано:

   ```
   test session::tests::direct_relay_gives_up_on_idle ... FAILED
   test session::tests::direct_relay_gives_up_when_only_upload_flows ... FAILED
   test session::tests::direct_relay_gives_up_when_only_download_flows ... FAILED
   assertion `left == right` failed
     left: 3600s
    right: 300s
   test result: FAILED. 0 passed; 3 failed; 0 ignored; 0 measured; 129 filtered out

   $ git checkout xr-core/src/session.rs
   test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 129 filtered out
   ```
2. `cargo test --workspace` зелёный, а `cargo test --workspace 2>&1 | grep
   "warning:" | grep -v generated` пустой. Прогнано, все крейты зелёные
   (`xr-core` 132 из 132), вывод грепа пустой.
3. Устойчивость по времени: 40 прогонов подряд
   `for i in $(seq 1 40); do cargo test -q -p xr-core session::tests::direct; done`
   без красных. Прогнано.

Живой проверки на телефоне сценарий не требует: поведение целиком внутри
relay-таска и снимается тестами на виртуальных часах, на устройстве тот же эффект
виден только по отсутствию накопления сессий за час.
