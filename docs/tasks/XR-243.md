# XR-243: Приложение показывает сырые категории ошибок шары: humanError не знает http_*, parse: и manifest_*, на экране висит «Манифест: http_404», и офлайн-ретрай для них не заводится. Найдено при разборе XR-219

## Разбор

`humanError` живёт в
[FilesViewModel.kt:294](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt#L294)
(до правки) и раскладывает категорию ошибки в русский текст. Категория идёт
строкой из xr-core через JNI: `direct_then_relay`
([sync.rs:1365](../../xr-core/src/sync.rs#L1365)) уже отсеивает чужой хост
прощупом (XR-219), так что `http_*`, `parse:`, `read:` и `manifest_*`,
дошедшие до экрана, это ответ настоящего агента шары -
[sync.rs:1622](../../xr-core/src/sync.rs#L1622) (`http_<код>`),
[sync.rs:1648](../../xr-core/src/sync.rs#L1648) (`parse:`),
[sync.rs:1634](../../xr-core/src/sync.rs#L1634) (`read:`, сбой чтения тела
уже после успешного статуса - `resp.bytes().await.map_err(|e| format!("read:
{e}"))`),
[sync.rs:1642](../../xr-core/src/sync.rs#L1642) и
[sync.rs:1645](../../xr-core/src/sync.rs#L1645) (`manifest_unsigned` /
`manifest_signature:`). `humanError` этих префиксов не знал, они падали в
`else -> e`, и `openShare` в
[FilesViewModel.kt:545](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt#L545)
(до правки) вообще не звал `humanError` для этой ветки, показывая `e.message`
голым текстом - отсюда «Манифест: http_404» на экране.

Офлайн-ретрай (`maybeStartOfflineRetry` / `startOfflineRetry`,
[FilesViewModel.kt:626](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt#L626))
до правки заводился только на `isOffline()` (префикс `network`) и
`isAgentOffline()` (`agent_offline`): для `http_*`/`parse:`/`read:`/`manifest_*`
список не подтягивался сам, только ручным обновлением.

## Что сделано

Раскладка вынесена из `FilesViewModel` в отдельный файл
[ShareErrorText.kt](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/ShareErrorText.kt)
(чистая Kotlin-логика без Android SDK, XR-243) с двумя функциями:

- `humanShareError(e: String): String` - прежняя раскладка `humanError` плюс
  новые категории: `http_404` -> «файл не найден на сервере (404)» (путь не
  существует именно у настоящего агента, перебор кандидатов уже отсеял чужие
  хосты раньше); `http_5xx` -> «агент шары сейчас отвечает ошибкой (код),
  пробуем ещё раз»; прочие `http_<код>` -> «агент шары ответил ошибкой
  <код>»; `parse:` -> «ответ сервера не разбирается»; `read:` -> «не удалось
  дочитать ответ сервера» (тот же обрыв, что и `parse:`, только раньше -
  статус пришёл, а тело оборвалось); `manifest_unsigned` -> «манифест шары
  пришёл без подписи»; `manifest_signature:` -> «подпись манифеста не
  сошлась».
- `isTransientAgentErrorCategory(e: String): Boolean` - `5xx`, `parse:` и
  `read:` похожи на переходный сбой агента (форма ответа сломалась, а не
  решение по существу; обе ветки чтения тела входят в `should_try_next` у
  ядра, [sync.rs:1453](../../xr-core/src/sync.rs#L1453)), для них имеет смысл
  офлайн-ретрай, как и для настоящей недоступности сети. `404` (пути нет у
  агента) и `manifest_*` (подпись не сошлась - вопрос доверия к адресату, а
  не сети) в список не входят: повтор их не лечит, как и соседние
  авторитетные `401`/`403`/`412`/`413`/`422`/`429` из `should_try_next` в
  ядре ([sync.rs:1449](../../xr-core/src/sync.rs#L1449)).

`FilesViewModel.humanError` теперь делегирует в `humanShareError`. Добавлена
`Throwable.isTransientAgentError()`, подключена в трёх местах:
`openShare` (новая ветка перед `!e.isOffline()`, ставит `offlineLocal = true`
и текст через `humanError` вместо голого `e.message`),
`refreshManifest` (расширен предикат `offline`), `maybeStartOfflineRetry` и
цикл `startOfflineRetry` (условие продолжения ретрая).
