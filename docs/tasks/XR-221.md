# XR-221: onRevoke пишет в журнал ложное туннель остановлен пользователем при системном отзыве VPN или перехвате другим клиентом: onRevoke зовёт stopFromUi, диагностика почему выключился VPN вводит в заблуждение

## Разбор корня

[`XrVpnService.onRevoke()`](../../xr-android/app/src/main/java/com/xrproxy/app/service/XrVpnService.kt)
это колбэк `android.net.VpnService`: система дёргает его, когда VPN-разрешение
приложения отозвано, а поводов для этого два, и ни один не идёт через кнопку
«Отключить» в самом приложении: пользователь снял тумблер этого VPN в
системных настройках Android либо активной стала другая VPN-заявка (Android
держит активным только одно VPN-соединение, и включение стороннего клиента
автоматически глушит наш). До правки `onRevoke()` звал тот же `stopFromUi()`,
что и кнопка «Отключить» и `ACTION_STOP`, а та безусловно пишет в журнал
`"туннель остановлен пользователем"`. Диагностика получалась лживой ровно в
момент, когда она нужнее всего: пользователь смотрит в журнал, чтобы понять,
почему VPN погас сам, а запись утверждает, что он сам его выключил.

## Что сделано

Причина стопа теперь явный тип
[`VpnStopReason`](../../xr-android/app/src/main/java/com/xrproxy/app/service/VpnStopReason.kt)
(`UI` / `SYSTEM_REVOKE`) с собственным текстом записи в журнал. `stopFromUi()`
и `onRevoke()` ведут в общий приватный `stopTunnel(reason: VpnStopReason)` -
тело осталось тем же (публикация `Stopping`, разбор движка и TUN, публикация
`Idle`, `stopSelf()`), поменялась только причина, которую он пишет в журнал.
Публичная сигнатура `stopFromUi()` не изменилась, вызовы из `VpnViewModel` и
из `ACTION_STOP` в `onStartCommand` трогать не пришлось.

Дока: `docs/ARCHITECTURE.md`, раздел про `XrVpnService.kt`, получил абзац про
`stopTunnel`/`VpnStopReason` и про то, что `onRevoke()` больше не пишет
«остановлен пользователем».

## Проверка красноты

Сам стоп-путь живёт в `android.net.VpnService` и агентским JVM-юнитом не
гоняется (соглашение проекта: Android SDK код проверяется на эмуляторе, чистая
Kotlin-логика без SDK - юнитом). Из правки в чистую логику вынесен ровно текст
двух причин: `VpnStopReasonTest` в
`xr-android/app/src/test/java/com/xrproxy/app/service/VpnStopReasonTest.kt`
проверяет, что причина `UI` упоминает пользователя, а `SYSTEM_REVOKE` его не
упоминает и текстом не совпадает с `UI`.

`regcheck` тут не применим формально: `VpnStopReason.kt` в базовой ветке не
существует вовсе (весь тип заведён этой правкой), перенос одних тестовых
файлов на старый код даёт компиляцию с нуля и зелёный прогон, поэтому
`regcheck` сам отказывается засчитывать такой тест регрессионным. Красноту
проверил руками: временно свёл `SYSTEM_REVOKE` к тому же тексту, что и `UI`
(так выглядело бы поведение с багом, если бы `onRevoke()` собирали заново на
общей причине), прогнал тест - упал ровно `systemRevokeReasonDoesNotClaimTheUserDidIt`,
вернул текст обратно - оба теста зелёные:

```
$ ./gradlew :app:testDebugUnitTest --tests "com.xrproxy.app.service.VpnStopReasonTest"
com.xrproxy.app.service.VpnStopReasonTest > systemRevokeReasonDoesNotClaimTheUserDidIt FAILED
    java.lang.AssertionError at VpnStopReasonTest.kt:26
2 tests completed, 1 failed
$ # текст SYSTEM_REVOKE возвращён
$ ./gradlew :app:testDebugUnitTest --tests "com.xrproxy.app.service.VpnStopReasonTest"
BUILD SUCCESSFUL
```

`./gradlew :app:testDebugUnitTest` (весь модуль) зелёный. `cargo test
--workspace --exclude xr-client` (Rust-часть правку не затрагивает) зелёный,
`warning:` в выводе нет.

## Сценарий проверки

Агентский, на эмуляторе (стенд по
[local-docs/android-stand/README.md](../../local-docs/android-stand/README.md)
в основном чекауте, снапшот `xr-ready`; в этом worktree стенда нет, он живёт в
гитигнорнутом `local-docs` соседнего дерева). Проверяются оба повода
`onRevoke()`, оба через живой журнал приложения («Журнал» на главном экране).
В этой сессии не прогнан: эмулятор в моменте занят прогоном другой задачи, а
поднимать второй стенд для S-правки избыточно. Реальный вывод шагов 1-4 вложить
в этот раздел перед переводом в Check.

1. Поднять туннель из приложения (Connect), дождаться Connected либо любой
   фазы кроме Idle/Stopping - `stopTunnel` пишет журнал и на Preparing/Connecting.
2. Отозвать VPN-разрешение приложения через системные настройки (Настройки ->
   Сеть и интернет -> VPN -> XR Proxy -> отключить, тумблер жать через
   `uiautomator`). Приложение обязано перейти в Idle, а в журнале - появиться
   строка `VpnStopReason.SYSTEM_REVOKE` («VPN отозван системой: ...»), не
   «туннель остановлен пользователем».
3. Поднять туннель заново, затем включить любой сторонний VpnService на
   эмуляторе (перехватывает VPN-слот) - тот же `onRevoke()`, та же
   формулировка в журнале, не «пользователем». Прямой альтернативы этому шагу
   нет: перехват другим клиентом и системный отзыв из настроек оба идут через
   один и тот же `onRevoke()` без разбора причины на стороне Android, поэтому
   шаг 2 уже доказывает верную формулировку для обоих поводов - шаг 3 закрывает
   его только чтобы явно увидеть перехват на практике.
4. Отключить туннель штатной кнопкой «Отключить» в приложении - в журнале
   по-прежнему должна остаться `"туннель остановлен пользователем"`: этот путь
   правка трогать не должна.
