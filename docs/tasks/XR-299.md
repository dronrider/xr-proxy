# XR-299: Чувствительные домены уходят с сервера через резидентский прокси

## Что происходит

Купил резидентский прокси (http+socks). Хочу, чтобы весь трафик к Anthropic, OpenAI и Gemini с серверов timeweb и aeza шёл через него всегда, со стопроцентной гарантией мимо прямого выхода. Сегодня сервер строит исходящее соединение напрямую в xr-server/src/handler.rs. В маршрутизации уже есть Action::Block и политика on_server_down с поведением «отказ вместо утечки», xr-proto/src/routing.rs. Правила лежат в пресетах хаба и разъезжаются по клиентам.

Проверил 2026-10-13. Исходящее соединение сервер собирает в xr-server/src/handler.rs через TcpStream::connect, выхода через socks5 или http в xr-server/src нет. Политика on_server_down с fail-closed на месте в xr-proto/src/routing.rs, её держит тест test_on_server_down_is_fail_closed. Дублей не нашёл. В архиве ближайший XR-077 про kill-switch роутера при пропаже перехвата, предмет другой.

При падении прокси запрос уходит с IP хостинга, и гарантии нет. Переменные окружения её не дают. Пропущенный cron, свой HTTP-стек или запуск без окружения уйдут напрямую, и об этом никто не узнает.

## Чего хотим

Чувствительные домены с любого клиента идут через сервер и резидентский прокси. При недоступном резиденте соединение рвётся, и с IP хостинга эти домены не открываются. Все серверы ходят в сеть одним резидентным IP, он фиксирован покупкой. Канарейка с ip-эхом в правиле показывает резидентский IP для чувствительных доменов и IP сервера для остального.

## Границы

Гарантия покрывает два кодовых пути исходящего соединения сервера, handler и mux_handler. Оба собирают соединение одинаково, и оба идут под правило.

UDP-релей клиента в предмет не входит. Данные чувствительных правил идут по TCP, но правила покрывают и веб-интерфейсы сервисов, chatgpt.com, claude.ai, gemini.google.com. Браузер может открыть такой домен по HTTP/3 поверх UDP. Такой поток уходит с IP сервера мимо резидента. Реле на сервере шлёт пакеты наружу своим сокетом и минует правила. Гарантия действует при срезе QUIC на клиентских путях. Срез делает block_quic в конфиге клиента, после него браузер уходит на TCP через туннель. Сам срез к задаче не относится. Он живёт в конфиге роутера и в XR-300.

Клиентский край on_server_down со значением direct остаётся за пределами задачи. Там клиент сам уходит напрямую при пропаже сервера, и это другая гарантия.

## Развилки

Кто назначает выход. Либо клиент везёт тег выхода вместе с адресом назначения, это правка протокола. Либо сервер сам матчит домен по правилам хаба, тогда политика в одной точке и клиент ничего не решает, но серверу нужен домен соединения. Склоняюсь ко второму. Заодно в LLD сверить, как резолвятся домены правила, чтобы сам запрос резолва не утекал в локальную точку доступа. Два входа снаружи. Нужен формат фиксированной сессии у провайдера, и решить, нужен ли http-выход кроме socks5.

## DoD

- Запрос к чувствительному правилу уходит через резидентский IP, канарейка с ip-эхом его показывает.
- При падении резидента соединение рвётся, с IP хостинга чувствительные домены не открываются.
- Все серверы уходят в резидента одним фиксированным IP.
- Обычный трафик идёт напрямую, как шёл раньше.
- Цель по ip_ranges правила, включая подсеть инференса Claude, уходит через резидента.
- Резолв доменов чувствительного правила уходит через резидента.
- Правило держит сервер, старый клиент гарантию не ломает.

## Ранг

`50+8+3+0+2 = 63`, P1.

- Серьёзность 50 (Critical). Основной сценарий без задачи не работает. Запрос уходит с IP хостинга, и гарантии нет. Обход через ручной прокси в каждом приложении болезненный.
- Ценность 8. Ради стопроцентного обхода прямого выхода куплен резидентский прокси.
- Неопределённость 3. Правка идёт через xr-proto и xr-server, в стыках развилки поля выхода, доставки правил и формата сессии. Подход выбран, сервер матчит правило перед connect.
- Поправка на баг 0. Новая гарантия выхода через резидента.
- Рычаг 2. Поле outbound в правиле и путь через резидента достаются следующим чувствительным правилам.

## Сценарий проверки

Агентский шаг обкатки гоняется в свежем дереве. Шаги после выката идут
руками, им нужен боевой резидент и адреса VPS из `local-docs`.

```sh
cargo test -p xr-server
```

Ожидаемо `test result: ok` без warning'ов. Среди прошедших
`sensitive_target_exits_through_resident_and_never_directly`,
`sensitive_connect_relays_through_resident`,
`resident_down_closes_without_direct_leak` и
`unmatched_target_keeps_direct_path`.

После выката с секцией `[outbound.resident]` в конфиге VPS в журнале старта
стоит строка с числом outbound-правил. Команда:
`ssh <VPS> 'journalctl -u xr-proxy-server -n 200 --no-pager | grep -m1 outbound'`.

Канарейка с ip-эхом. В конфиг одного VPS добавлено правило с
`outbound = "resident"` и доменом `api.ipify.org`. С телефона в LAN через
туннель открыть `https://api.ipify.org`. Ожидаемо резидентский IP. Сайт
без правила показывает прежний IP VPS.

Падение резидента. Остановить резидента в панели провайдера и повторить
шаг с ip-эхом. Ожидаемо, что соединение к чувствительному домену рвётся и
в журнале есть outbound-отказ. Сайт без правила открывается.

Все серверы туннеля сходятся в один резидентский IP. Шаг с ip-эхом на
втором VPS показывает тот же адрес, что на первом.
