# XR-216. Одноразовый инвайт сгорал при сорванном разборе ответа

## Разбор корня

`POST /api/v1/invite/<token>/claim` в
[invites.rs](../../xr-hub/src/api/invites.rs) делает две вещи разом: отдаёт
`InvitePayload` и тут же ставит `consumed_at` одноразовому инвайту. Дальше всё
держится на предположении, что ответ доехал до клиента целым.

На клиенте (`apply_invite` в
[onboarding.rs](../../xr-core/src/onboarding.rs)) разбор тела идёт уже после
того, как сервер отчитался: `resp.json::<InvitePayload>()`. Не сложилось (хаб
свежее приложения и сменил формат, ответ обрезан посредине, оборвалась сеть на
чтении) и клиент кладёт строку в `errors`, возвращает `payload=None`, а на
экране подтверждения пользователь видит ошибку. Инвайт при этом уже потреблён:
повторный тап Apply получает `410 Gone`, и получатель заперт до нового инвайта
от админа. Тот же исход даёт и таймаут на чтении ответа, там ошибки разбора нет
вовсе, а инвайт всё равно сгорел.

Первопричина не в разборе, а в том, что claim это одноразовая мутация без
идентификации клиента: сервер не может отличить «тот же человек повторяет
попытку» от «ссылку переслали дальше», поэтому закрывается для обоих. Весь путь
онбординга при этом не был покрыт ни одним тестом.

## Что сделано

1. **Ключ клиента.** Claim идёт с заголовком `X-Claim-Id` (16 случайных байт,
   base64url). Хаб запоминает его в новом поле `claim_id` инвайта рядом с
   `consumed_at` и отдаёт тот же payload на повтор с тем же ключом, пока инвайт
   не истёк. Чужой ключ, повтор без ключа и отозванный инвайт (revoke ключ
   снимает) по-прежнему получают `410 Gone`. Пустой и длиннее 128 символов
   ключи не запоминаются: первый совпал бы у всех, второму нечего делать в
   файле инвайта.
2. **Ключ на клиенте.** Лежит файлом `claim-id` рядом с кэшем пресетов, поэтому
   переживает перезапуск приложения: повторить Apply можно и после обновления,
   которое чинит разбор. Если ключ не сохранился, это отдельная строка в
   `errors`, иначе потеря повтора выглядела бы как обычная ошибка сети.
3. **Тесты.** Хаб: шесть тестов на claim (повтор со своим ключом, с чужим, без
   ключа, отзыв, истёкший срок, многоразовый инвайт). Ядро: онбординг против
   хаба-заглушки на живом TCP (битое тело на первой попытке и целое на второй,
   уникальность ключа между установками, штатный проход с пресетом и
   TOFU-ключом). Раньше на этом пути не было ни одного теста.
4. **Дока.** Раздел 5.3 `ARCHITECTURE.md`: заодно поправлено описание ручек
   инвайта, там `GET /invite/:token` числился отдающим полный payload.

Половинки проверяются раздельно: тесты ядра сверяют, что claim несёт стабильный
ключ, тесты хаба, что по этому ключу повтор проходит. Общего живого стенда
приложение плюс хаб в тестах нет, его закрывает сценарий проверки.

## Проверка красноты и мутации

`regcheck --base main --inline xr-hub/src/api/invites.rs,xr-core/src/onboarding.rs
-- cargo test -p xr-hub -p xr-core` проходит («тест краснеет на main и проходит
на текущем коде»), но краснота там компиляционная: на main нет поля `claim_id`,
и тестовый регион просто не собирается. Настоящую проверку дала прогонка
мутациями, каждая ловится хотя бы одним тестом:

| Мутация | Кто краснеет |
|--------|--------------|
| потреблённый инвайт всегда 410 (исходный баг) | `repeat_claim_with_same_key_returns_payload` |
| ключ не запоминается при потреблении | `repeat_claim_with_same_key_returns_payload` |
| повтор пускают без сверки ключа | `repeat_claim_with_foreign_key_is_gone` |
| пустой ключ принимается | `blank_key_is_not_remembered` |
| длина ключа не ограничена | `key_of_128_is_remembered_and_129_is_not` |
| граница длины сдвинута внутрь (`> 128` -> `>= 128`) | `key_of_128_is_remembered_and_129_is_not` |
| граница длины сдвинута наружу (`> 128` -> `> 129`) | `key_of_128_is_remembered_and_129_is_not` |
| revoke не снимает ключ | `revoked_invite_is_gone_for_its_claimer` |
| срок проверяется после ветки повтора | `expired_invite_is_gone_for_its_claimer` |
| инвайт не пишется на диск при потреблении | `repeat_claim_with_same_key_returns_payload` |
| claim уходит без ключа | `claim_carries_a_stable_client_key` |
| ключ не сохраняется на диск | `claim_carries_a_stable_client_key` |
| сохранённый ключ не перечитывается | `claim_carries_a_stable_client_key` |
| ключ одинаковый у всех установок | `client_key_is_unique_per_install` |

## Сценарий проверки

Пользовательский: серверную половину (шаги 1-4) агент гоняет сам, но до
пользователя правка доезжает только с новым APK, поэтому итог подтверждается
шагом 5 на телефоне. Шаги 1-4 поднимают хаб на временном состоянии, живой прод
не трогают.

1. Собрать хаб и поднять его на временном каталоге с одним одноразовым
   инвайтом (`config.toml` с `bind = "127.0.0.1:18216"` и своим `data_dir`,
   файл `invites/<token>.json` с `one_time: true` и сроком в будущем).
2. `curl -s -o body -w '%{http_code}' -X POST -H 'X-Claim-Id: key-A'
   http://127.0.0.1:18216/api/v1/invite/<token>/claim`. Ожидаемо `200` и
   payload в теле.
3. Тот же запрос ещё раз. Ожидаемо снова `200` и тот же payload (до правки был
   `410 invite already used`), а в `invites/<token>.json` появился
   `"claim_id": "key-A"`.
4. Тот же запрос с `X-Claim-Id: key-B` и без заголовка вовсе. Ожидаемо `410` и
   `invite already used` в обоих случаях.
5. На телефоне: выпустить одноразовый инвайт в админке хаба, применить его в
   приложении, дождаться подключения. Ожидаемо инвайт применяется как раньше
   (ключ ничего не сломал), в админке он помечен потреблённым, а попытка
   применить тот же инвайт на другом устройстве отбивается как использованный.

### Прогон шагов 1-4 (локально, до выката)

```
1. первый claim с ключом A:      200  {"server_address":"203.0.113.10","server
2. повтор с тем же ключом A:     200  {"server_address":"203.0.113.10","server
3. повтор с чужим ключом B:      410  invite already used
4. повтор без ключа:             410  invite already used
5. ключ в файле инвайта:           "claim_id": "key-A",
```

## Ревью

- Тест на длину ключа проверяет только заведомо длинный claim_id (129 символов), а не саму границу в 128: мутация сдвига условия claim_id_header (raw.len() > 128 -> >= 128) молча пройдёт все тесты, хотя ключ ровно в 128 символов должен запоминаться, а мутант отбросит и его. Разбор задачи заявляет мутацию длины закрытой (таблица: 'длина ключа не ограничена' -> blank_and_oversized_keys_are_not_remembered), но именно граничное значение не покрыто.: исправлено, тест разделён на пустой ключ и границу длины: 128 символов запоминается и проходит повтором, 129 отбрасывается; мутации в обе стороны (>= 128 и > 129) краснеют
