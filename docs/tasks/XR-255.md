# XR-255: Метаданные файлов шары: агент пишет источник и канал при импорте по URL, отдаёт клиенту, дозаполняет по уже скачанным

Задача цели [XR-253](XR-253.md), фундамент для экрана информации о файле
(XR-257) и группировки по источнику (XR-258). Пункт 2 постановки: у
понравившегося ролика негде посмотреть, откуда он скачан, и нет ссылки на канал
автора.

## Текущее состояние

Всё, что агент знает о файле, это `ShareManifestEntry` из
[xr-proto/src/share.rs:34](../../xr-proto/src/share.rs#L34): путь, размер,
mtime, sha256. Манифест подписан ключом агента (XR-046), клиент проверяет
подпись пиннингованным `agent_pubkey`, так что любое новое поле листинга должно
въезжать под ту же подпись, иначе MITM правит его свободно.

Импорт по URL ([LLD-29](../lld/29-share-url-import.md), реализован в XR-141)
знает про файл гораздо больше: исходный URL держит сама джоба, а плагин yt-dlp
на выходе знает заголовок, канал, его адрес и дату публикации. Сейчас из этого
на диск доезжает только имя файла, всё остальное умирает вместе с джобой
([xr-share/src/import.rs](../../xr-share/src/import.rs), публикация в
`publish_files`).

## Что сделать

1. **Модель метаданных.** Минимальный набор, который закрывает постановку:
   исходный URL страницы, название источника (для видео это канал), адрес
   страницы канала, дата публикации, заголовок из метаданных. Поля
   необязательные: у файла, залитого руками, не будет ни одного.
2. **Хранение на стороне агента.** Метаданные переживают перезапуск агента и
   принадлежат файлу, а не устройству. Развилки, которые задача закрывает сама:
   сайдкар в служебном пространстве шары против записи в общий индекс, и
   ключ метаданных (путь против sha256, у первого проблема переименования, у
   второго склейка одинаковых файлов). Выбранное решение с обоснованием отказа
   от альтернативы кладётся в этот файл, а факты о формате в
   [ARCHITECTURE.md](../ARCHITECTURE.md) той же задачей. Служебные имена
   агента живут в зарезервированном префиксе `.xr-`, и обход манифеста такие
   файлы уже пропускает.
3. **Запись при импорте.** Джоба знает URL с самого начала; из плагина
   вытаскивается то, что он отдаёт (у референсного yt-dlp это `--print` или
   sidecar-json, конкретику выбирает исполнитель, не ломая песочницу и
   передачу URL литералом). Метаданные ложатся рядом с публикацией файла тем
   же атомарным порядком: недоехавшая джоба не оставляет метаданных без файла.
   Пустой ответ плагина это не отказ импорта, а файл без метаданных.
4. **Отдача клиенту.** Метаданные доезжают до Android тем же путём, что
   листинг, под подписью манифеста, и видны в `xr-core` и через JNI (там
   `ShareManifestEntry` уже ездит JSON-ом,
   [xr-android-jni/src/lib.rs:1336](../../xr-android-jni/src/lib.rs#L1336)).
   Раздувать манифест целиком незачем: если метаданные едут отдельной ручкой,
   контур доверия у неё должен быть тот же, и это тоже решение задачи.
5. **Дозаполнение по уже скачанным.** Разовый проход по файлам шары, который
   достаёт то, что ещё вытаскивается. Для ютуба это суффикс `[<id>]` в имени
   (его же прячет `displayFileName` в проводнике): из него собирается ссылка на
   ролик. Канала в имени нет, и выдумывать его нельзя: поле остаётся пустым, а
   экран информации показывает честную пустоту. Проход запускается сам при
   старте агента один раз и не ходит в сеть.

Форматы ломать можно, парк тестовый: слои совместимости со старым манифестом не
закладывать.

## Сценарий проверки

Агентский, на харнессе `xr-share` из тестов крейта плюс живой прогон:

1. `cargo test --workspace` зелёный, и в нём есть тест на то, что импорт
   положил метаданные с URL и каналом, тест на файл без метаданных и тест
   дозаполнения по имени с суффиксом `[<id>]`.
2. Живой прогон на локальном агенте: поднять шару с плагином-заглушкой вместо
   yt-dlp (он отдаёт заранее заданные канал и URL), запустить импорт, дождаться
   `done` и получить листинг с метаданными в ответе. В файл задачи кладётся
   реальный вывод команд, а не пересказ.
3. Файл, положенный в шару руками до старта, после перезапуска агента показан
   в листинге без метаданных, а файл с именем вида `Название [dQw4w9WgXcQ].mp4`
   получил ссылку на ролик и пустой канал.

## Ход работы

- Исполнение: субагент opus/high по вердикту pick (квота: week_all 18%, снимок 40м назад, сдвига нет), 2026-08-04.

### Решения по развилкам

**Транспорт: внутри манифеста.** У `ShareManifestEntry` появилось
необязательное поле `meta` типа `FileMeta` (`url`, `source`, `source_url`,
`published`, `title`; пустые поля на провод не едут, у файла без источника нет и
самого поля). Отдельная ручка отвергнута: манифест это единственное, что
потребитель проверяет по пиннингованному `agent_pubkey`, и своя ручка
потребовала бы второго домена подписи, второго запроса и второго режима отказа
ради того же самого. Внутри манифеста канал и ссылка становятся такими же
неподделываемыми, как хеш, и это закреплено тестами
`manifest_signature_covers_the_origin_too` и
`fetch_manifest_carries_file_origin`. Раздувания не случилось: у шары без
импорта манифест байт в байт прежний.

**Хранение: индекс на шару, ключ путь.** JSON-файл `.xr-meta.json` в корне шары
(`xr-share/src/meta.rs`), ключ это относительный путь файла, тот же, каким его
зовёт манифест. Сайдкар у каждого файла отвергнут по цене чтения: листинг
строится на каждом обходе папки и обязан оставаться мгновенным (XR-039), а это
open на файл против одного чтения маленького JSON; вдобавок сайдкары засоряют
папки владельца. Ключ sha256 отвергнут потому, что листинг сознательно не
хеширует, и у только что импортированного файла хеша ещё нет, то есть строка
была бы невидима ровно тогда, когда она интереснее всего; сверх того один хеш
склеивает два одинаковых файла и теряется при переупаковке. Плата за путь это
переименование мимо агента: роута переименования у агента нет, свои `PUT` и
`DELETE` строку снимают сами, осиротевшие подметает проход при старте.

**Канал от плагина: файл `.xr-meta.tsv` в джоб-папке.** Плагин кладёт строку на
выходной файл, поля через табуляцию. Референсный yt-dlp пишет их сам через
`--print-to-file after_move:...`. `--print` не взят сознательно: он тянет за
собой `--quiet` и погасил бы разбор прогресса, который у агента идёт со stdout.
Скрытое имя в зарезервированном неймспейсе публикацией не подхватывается, так
что в шару служебный файл не попадает.

### Сделано

- `xr-proto`: тип `FileMeta`, поле `meta` у строки манифеста.
- `xr-share`: модуль `meta.rs` (индекс, разбор выхлопа плагина, сбор источника
  по имени, разовый проход), подстановка источника в оба билдера манифеста,
  запись при публикации импорта, снятие строки на `PUT`/`DELETE`, проход при
  старте агента, новые аргументы в референсном блоке `[import]` и в
  `configs/share.toml`.
- `xr-core`: источник доезжает до потребителя под подписью (Android-часть в
  XR-257, JNI отдаёт манифест JSON-ом и поле в нём уже есть).
- Дока: раздел «Откуда взялся файл (XR-255)» в `ARCHITECTURE.md`, контракт
  плагина в LLD-29 п. 2.3 и 2.4.

### Стыки

Референсный блок `[import]` бутстрапится заново только на конфиге без него, так
что на уже настроенном агенте новые аргументы yt-dlp владелец дописывает сам
(или сносит блок и повторяет `share --import`). У живого yt-dlp
`--print-to-file` не проверялся: под рукой его нет, заглушка проверяет контракт
агента. Шара из одного файла источника не носит: индексу негде лежать, и
импорта в неё нет.
