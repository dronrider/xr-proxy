# XR-285: Подмена DNS у провайдера кладёт сайт раньше перехвата: nftables выпускает 53 и 853 из LAN открытыми, dnsmasq ходит на Quad9 голым UDP, и без адреса LAN-клиент не открывает TCP, перехватывать нечего. Заблокированный по DNS сайт лежит на всех устройствах сети при живом туннеле, обход только уходом на мобильный интернет. Android иммунен: FakeDns в xr-core резолвит через VPS

## Что происходит

2026-08-28, домашняя сеть за роутером с xr-client: rutracker.org не
открывается. Диагностика с Mac показала подмену DNS у провайдера: на
UDP-запрос приходит NXDOMAIN с флагом aa даже «от» публичных резолверов
Cloudflare и Google, тот же запрос по TCP отдаёт настоящие адреса, а HTTPS
с подставленным вручную адресом работает (TLS 1.3, настоящий сертификат).
Роутерная часть xr-proxy DNS не трогает: nftables исключает порты 53 и 853
из перехвата (xr-client/src/redirect.rs:286-288), решение о проксировании
принимается по SNI уже открытого TCP (xr-client/src/proxy.rs:192-197), а
установщик лишь переводит dnsmasq на Quad9 обычным UDP:53
(xr-setup/src/openwrt.rs:59-87), который перехватывается так же, как
провайдерский.

Без адреса LAN-клиент не открывает TCP-соединение, и xr-client нечего
перехватывать: заблокированный через DNS сайт лежит на всех устройствах сети
несмотря на работающий туннель, а снаружи это неотличимо от «прокси не
работает». Обещание README про доступ без настройки на устройствах для таких
сайтов не выполняется.

Разбор 2026-08-28 подтвердил все три места по коду и добавил четвёртое: на
Android этой болезни нет. `FakeDns` в `xr-core/src/dns.rs` отвечает приложению
адресом из служебного диапазона RFC 2544, настоящего резолва в LAN не происходит вовсе, а имя
достаётся из таблицы на SYN и уезжает на VPS в Connect. Резолвит домен сервер,
и провайдеру подменять нечего.

С мака в момент разбора подмена не повторилась: запрос rutracker.org
по UDP к публичному резолверу Cloudflare отдал настоящие адреса и NOERROR,
Quad9 тоже. Мак в тот момент стоял за
вторым роутером, и плавает ли подмена сама, пока неизвестно. На ход задачи это
не влияет: нехватка структурная, DNS роутера уходит из LAN открытым UDP всегда,
и подставить туда что угодно провайдер может в любой момент. Из сайтов пока
попадался только rutracker.org, обхода в домашней сети нет никакого, помогает
единственно уход на мобильный интернет.

## Чего хотим

Сайт, заблокированный у провайдера на уровне DNS, открывается с любого
LAN-клиента без настройки на самом устройстве.

## Границы

Задача про роутер. Android уже закрыт `FakeDns` в `xr-core` и трогается только
если решение окажется переносом того же механизма на роутер.

## Развилки

Каким путём уводить DNS из-под перехвата: локальная заглушка xr-client с
резолвом через туннель на VPS, https-dns-proxy перед dnsmasq или перенос
Fake-IP из xr-core (Android уже так живёт) на роутер?

## DoD

- Резолв роутера не уходит из LAN открытым UDP:53, и стенд с подложным
  резолвером, отвечающим NXDOMAIN с флагом aa, это показывает: dnsmasq всё
  равно отдаёт настоящий адрес.
- rutracker.org открывается с LAN-устройства за роутером без единой настройки
  на самом устройстве.
- Раскладку делает автоматика: шаг `xr-setup` ставит и проверяет новое
  состояние сам, ручной правки файлов на роутере не остаётся.
- Отказ виден снаружи: если защищённый резолв не поднялся, это ложится строкой
  в лог, а не молчанием с откатом на провайдерский DNS.
- Решение и его причина оседают в `docs/ARCHITECTURE.md`.

## Ранг

`50+8+3+0+2 = 63`, P1.

- Серьёзность 50: заблокированный по DNS сайт лежит на всех устройствах сети,
  обход у пользователя есть, но болезненный, «только через мобильный интернет
  если».
- Ценность 8: обход блокировок это то, ради чего продукт и заведён, а
  подмена DNS сейчас не закрывается вообще ничем.
- Неопределённость 3: три пути из вопроса черновика (заглушка xr-client с
  резолвом через туннель, https-dns-proxy перед dnsmasq, перенос Fake-IP из
  xr-core) расходятся и по цене, и по последствиям, выбор не сделан.
- Поправка на баг 0: DNS в перехват не входил никогда, это нехватка, а не
  регресс.
- Рычаг 2: закрытый резолв на роутере снимает целый класс будущих блокировок,
  но чужой работы за ним не стоит.

## Приёмка

- вид: mixed
- барьер «доступ»: подмену ставит провайдер домашней сети, с машины агента её
  не увидеть. Стенд с подложным резолвером агентскую половину закрывает,
  человеку остаётся открыть сайт с LAN-устройства за живым роутером.

## Ход работы

- Из черновика XR-285 «поддельный NXDOMAIN провайдера кладёт сайт раньше перехвата прокси»: записан 2026-08-28, оформлен 2026-08-29.
- Разработка: подпроцесс glm-5.3/high по вердикту pick (квота: window5h_all 15%, week_all 20%, снимок 16м назад, сдвига нет), 2026-08-31 15:29-15:31.
- Развилка закрыта 2026-09-04 в пользу форвардера в `xr-client` с резолвом
  через туннель по DoT. `https-dns-proxy` отпал: пакет из opkg ставить надо в
  сети со сломанным резолвом, а DoH он шлёт с роутера напрямую, мимо туннеля,
  и резолвер блокируется по адресу. Перенос Fake-IP из `xr-core` отпал по
  устройству клиента: движок Android живёт на TUN, где через него идёт весь
  трафик, а `xr-client` работает по TPROXY, и рядом с ним `bypass_ips`,
  `bypass_rules` и UDP relay, куда служебный адрес отдавать некуда.
- Сделано: секция `[dns]` в конфиге клиента с сухой проверкой, модуль
  `xr-client/src/dns.rs` (UDP и TCP на петле, одно DoT-соединение на все
  запросы, свои идентификаторы на проводе, SERVFAIL вместо молчания и вместо
  отката), шаг `xr-setup` `dnsmasq:tunnel` с единственным апстримом
  `127.0.0.1#5353`, порт одной константой на конфиг и раскладку, проверка
  форвардера в `diagnose.sh`, раздел 5.4 в `ARCHITECTURE.md`.
- Стенд по DoD живёт в юнитах `xr-client/src/dns.rs`: рядом с форвардером
  поднимается резолвер, отвечающий NXDOMAIN с флагом `aa`, проверяется сперва,
  что он и правда подделывает, потом что форвардер отдаёт настоящий адрес.
- Прогоны 2026-09-04: `cargo test --workspace` зелёный без warnings,
  `cross build --release --target aarch64-unknown-linux-musl -p xr-client`
  прошла (rustls на ring под musl собирается).
- За границей задачи осталось: LAN-устройство с прописанным вручную внешним
  резолвером спрашивает мимо dnsmasq и получает ту же подделку. Перехват
  LAN-запросов на 53 в сторону dnsmasq это отдельная задача.
