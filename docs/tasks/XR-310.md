# XR-310: Общий пул WAN и выбор прокси по устройству и ресурсу

## Что происходит

На OpenWRT подключены два независимых провайдера. Пользователь хочет выбирать
провайдера и способ выхода по устройству LAN и ресурсу. Например, компьютер
выходит напрямую через быстрый канал, а телевизор использует прокси через
другой канал. Для отдельных ресурсов нужны исключения из политики устройства.

Текущий xr-client выбирает direct/proxy/block, но общий пул mux не разделён
по провайдерам. После перехвата исходящий сокет создаёт роутер. Правила
OpenWRT только по исходному IP устройства уже не определяют путь этого
сокета. Внутри одного TCP-туннеля нельзя развести стримы по разным WAN.

На живой сети 2026-10-21 проверены два временных сценария для одного Samsung
и одного тестового ресурса. Прямой выход через второй WAN подтверждён внешним
IP и счётчиками. Затем отдельный xr-client под непривилегированным UID
открыл туннели через второй WAN. Пользователь увидел IP VPS, журнал и сокеты
подтвердили цепочку. Основной клиент и первый WAN продолжали работать.

Программная блокировка обоих VPS только для тестового процесса привела к
ошибке запроса. После снятия блокировки запрос прошёл. Физический обрыв WAN,
скорость канала, правила по доменам и постоянная настройка ещё не проверены.

## Чего хотим

Один xr-client обслуживает несколько профилей выхода. Профиль задаёт
провайдера, direct/proxy/block, пул прокси-серверов и допустимый резерв.
Туннели разных профилей изолированы внутри одного процесса. Пулы можно
разделять по совместимости параметров выхода, но запрос не должен попасть
в туннель другого WAN из-за повторного использования соединения.

Устройство получает маршрут по умолчанию и исключения по ресурсам. Ресурс
задаётся доменом или IP/подсетью. Порядок правил и поведение неизвестного
устройства определены в конфиге и описаны с примерами. Выбор провайдера
отделён от выбора прокси-сервера. Резервный провайдер и прямой выход при
отказе прокси разрешаются независимо и только явной настройкой.

В диагностике видны совпавшее правило, профиль, фактический WAN, прокси-сервер
и причина отказа. Конфигурация и её раскладка воспроизводимы средствами
проекта. Ручные временные правила из эксперимента заменяются штатной настройкой.

Пример желаемого поведения без привязки к синтаксису будущего конфига:

| Устройство | По умолчанию | Исключение по ресурсу |
|---|---|---|
| Компьютер | Быстрый WAN, напрямую | Выбранный домен через прокси на быстром WAN |
| Телевизор | Второй WAN, через прокси | Выбранный видеосервис через прокси на быстром WAN |
| Остальные устройства | Текущая общая политика | Существующие доменные правила |

## Границы

- Реализация и раскладка на OpenWRT входят в задачу. Отдельный LLD не является
  обязательным результатом. Сначала выбрать минимальное изменение текущего кода.
- По уточнению пользователя 2026-10-22 в задачу входит общий взвешенный пул
  двух WAN для одновременных соединений с сохранением всей конфигурации
  ресурсов xr-client и хаба. Сложение полос внутри одного TCP-соединения и
  новый интерфейс управления в задачу не входят.
- XR-080 выбирает VPS для устройств. Здесь выбирается ещё и локальный WAN;
  согласовать модели без дублирования таблиц правил. XR-297 касается сигнала
  потери аплинка; учитывать его для конкретного WAN, не замораживать здоровые
  профили вместе с потерянным каналом. Жёсткой зависимости от этих задач нет.
- Поле outbound на сервере относится к серверному выходу. Не смешивать его
  с новым выбором провайдера на клиенте.
- Общие изменения firewall и закрытие обнаруженных внешних служб не входят
  в эту задачу. Существующие WireGuard, NAS-исключения, UDP relay, DNS,
  пробросы портов и доступ администратора должны сохраниться.
- Живые адреса, доступы, резервные копии и команды временных тестов лежат
  в локальной записке по ID задачи в local-docs. Перед выкатом перечитать её
  и проверить текущее состояние. Тестовые процессы и правила имеют срок жизни.

## DoD

1. Один процесс xr-client применяет политики минимум двух устройств и двух
   ресурсов. Для direct и proxy независимо выбирается WAN. Ресурсное
   исключение устройства имеет документированный приоритет над его маршрутом
   по умолчанию. Старый конфиг сохраняет прежнее поведение.
2. Исходящие direct-сокеты, mux, переподключения и фоновые проверки серверов
   используют выбранный выход. Пулы, здоровье серверов и состояние аплинка
   разделены там, где этого требует использование разных WAN. Отказ одного
   профиля не переводит остальные на другой выход и не рвёт их сессии без
   необходимости.
3. При отказе WAN или всех серверов профиля нет незаданного выхода через
   другой WAN или напрямую. Разрешённый резерв проверен отдельно. Недоступный
   выбранный маршрут не заменяется основным маршрутом ОС. Поведение уже
   открытых соединений и новых запросов явно определено.
4. Разобраны пути DNS, UDP relay, QUIC и IPv6. Неподдержанная комбинация
   ограничений отклоняется до изменения сети либо блокируется явно. DNS и
   IPv6 не создают обход политики конфиденциальности. Для доменов описаны
   ограничения DNS/SNI, ECH, собственных резолверов и общих адресов CDN.
5. validate проверяет ссылки на профили, допустимый резерв и параметры
   выхода без изменения сети. Установщик применяет настройку до подключения
   второго роутера. Его порт исключён из LAN; чужие DHCP и IPv6 RA не меняют
   домашнюю сеть. Метки, маски, приоритеты и таблицы согласованы с TPROXY.
6. Обновление, перезапуск и восстановление после сбоя воспроизводимы.
   Удаление или откат снимают только правила этой функции. Диагностика
   показывает выбранный и фактический выход без ключей и токенов в журнале.
7. Входная инструкция содержит настройку двух WAN, политики устройств,
   ресурсные исключения, резерв и проверку результата. Факты внесены в
   ARCHITECTURE.md, пример конфига обновлён. На роутере владельца выполнен
   сценарий ниже; временный второй xr-client больше не нужен.

## Ранг

25+8+3+0+2 = 38, P2.

- Серьёзность 25: нужная маршрутизация пока требует отдельных процессов и
  ручных правил; основной прокси работает.
- Ценность 8: пользователь управляет провайдерами и конфиденциальностью
  каждого устройства и ресурса из одной конфигурации.
- Неопределённость 3: схема проверена отдельным процессом, остаются разделение
  пулов и интеграция с маршрутизацией, DNS и UDP.
- Поправка на баг 0: добавляется новая возможность клиента.
- Рычаг 2: упрощается дальнейшая настройка домашней сети.

## Приёмка

- вид: mixed
- барьер «событие»: проверка с браузера реального телефона и физическое
  отключение второго провайдера требуют участия владельца.
  - эмулятор: годится для проверки правил и запросов, не подтверждает
    физическое подключение и поведение телефона в домашней Wi-Fi-сети.
  - синтетическая среда: годится для отказов и независимости профилей,
    не заменяет физический обрыв второго WAN.
  - вторая машина контура: годится для наблюдения внешних адресов и пакетов,
    не заменяет телефон и доступ к кабелю провайдера.

Стенд с подменой сети обязателен для автоматических проверок, после него
остаётся живая проверка двух провайдеров вместе с владельцем.

  - В конфиге три опциональные секции. `[[wan]]` задаёт канал провайдера

    `on_server_down` и `fallback_wan`. `[[device]]` задаёт политику
    устройства полями `name`, `ips` с адресами или подсетями LAN,
    `default_exit` и вложенными `[[device.rule]]` с `domains`, `ip_ranges`
    и `exit`. Без новых секций клиент ведёт себя по-прежнему, маршрут
    выбирает `[routing]`.
  - Устройство ищется по source IP LAN, берётся первое совпавшее. Внутри
    устройства побеждает первое совпавшее правило ресурса по SNI или адресу
    цели, без совпадения действует `default_exit`. Неизвестное устройство
    живёт по `[routing]` с прежним пулом. Правила устройств выбирают только
    выход, доменные группы пресета остаются в `[routing]` и не
    дублируются.
  - Исходящие сокеты привязываются к каналу через SO_BINDTODEVICE по имени
    интерфейса. Имя переживает обновление DHCP-аренды второго роутера и не
    требует своих `ip rule` и таблиц, поэтому метка fwmark 0x200 и таблица
    201 у TPROXY не затрагиваются. Мёртвый канал даёт быстрый отказ
    (ENETUNREACH), основной маршрут ОС не подставляется.
  - Пулы делятся по ключу из интерфейса канала и подмножества серверов.
    Совпадающие ключи делят один пул, у каждого пула свой health_loop и
    своё здоровье. Профиль без `wan` с полным пулом использует прежний пул
    по умолчанию. Прямые соединения, туннели и пробы здоровья профиля идут
    через выбранный канал.
  - Резерв включается полем `fallback_wan`. После отказа всех серверов
    профиля те же серверы опрашиваются через резервный канал, без поля
    перехода на другой канал нет. `on_server_down` в профиле по умолчанию
    block и разрешает прямой выход только через канал самого профиля.
  - Признака аплинка на роутере нет (XR-296/XR-297), пулы разделены по
    каналам, поэтому смерть одного канала роняет здоровье только его

    серверов, XR-310 выбирает сам пул.

## Отказ основного провайдера, 2026-10-23

Авария провайдера выявила два пропущенных сценария. Первый WAN сохранял
Ethernet-подключение, но не получал DHCP-адрес. Второй провайдер работал.

и устройства с обходом пула остались без основного маршрута. DNS ожидал
недоступный пул и завершался с SERVFAIL до попытки через рабочий канал.

Временные маршруты к VPS восстановили туннельный DNS. Резервный маршрут
для основного трафика вернул доступ компьютеру администратора. Пользователь
подтвердил обычные сайты и прокси с телефона, затем переключил компьютер
с мобильного интернета на Cudy. Доступ из соседней сети через WireGuard
проверен отдельно.

Постоянное исправление должно пройти следующие проверки:

1. При потере DHCP первого WAN без потери Ethernet-подключения DNS продолжает
   работать через защищённый туннель второго WAN в пределах своего таймаута.
2. Зависший пул DNS не задерживает рабочий пул; при отказе всех пулов
   возвращается SERVFAIL без выхода к провайдерскому резолверу.
3. Служебный трафик и устройства с обходом пула используют доступный резерв,
   а после восстановления первого WAN возвращаются на него.
4. Явно закреплённые выходы сохраняют свой канал. Локальные сети, VPN,
   сетевые метки и правила direct/proxy/block продолжают действовать.
5. Автоматика восстанавливает резервирование после запуска сервиса без
   временных маршрутов. Удаление пула сохраняет чужие маршруты и правила.
6. Регрессионные тесты падают на прежнем коде и проходят на исправленном.
   На роутере проверяются DNS, HTTPS с компьютера администратора, обычный
   и проксируемый трафик из LAN, доступ к веб-интерфейсу через WireGuard.

Прямые соединения устройств с обходом пула проверяются отдельно от сайтов.
Прозрачный прокси открывает исходящий сокет на роутере, поэтому успешная
загрузка страницы не подтверждает NAT обычного LAN-трафика. Дополнительный
регрессионный тест проверяет TCP и UDP без метки пула, а живая проверка
использует SSH с компьютера администратора к VPS.

Первой повторной попытки DNS оказалось недостаточно. Общая пауза
переподключения немедленно завершала свежие запросы с SERVFAIL. Теперь
они ждут её окончания в пределах исходного срока. Отмена прерывает ожидание,
а истёкший срок не допускает нового подключения.

В чистом двухминутном замере после переключения получены 189 корректных
ответов DNS, включая NXDOMAIN. SERVFAIL и тайм-аутов нет. Медиана составила
77 мс, 95-й процентиль 207 мс, максимум 471 мс. Независимая проверка
подтвердила свежие DNSKEY и NXDOMAIN, Direct, Proxy и неизменность прежней
части конфигурации. Изменился только добавленный раздел DNS.

Для WireGuard сохранены штатные параметры OpenWRT: `nohostroute=1`,
отдельная метка внешнего транспорта и правило выбора таблицы 218 до
source-rule второго WAN. При тестовом отказе первого канала VPN восстановился
через второй примерно за 15 секунд. После возврата первого повторный отказ
второго VPN не прервал. Проверены реальный внешний адрес пакетов, внутренние
VPN-маршруты, TPROXY и обратный веб-доступ к роутеру.

### Восстановление маршрутов после изменения интерфейса

После отключения и включения WAN пропал default из таблицы 210, хотя адрес,
маршрут провайдера и Ethernet-подключение восстановились. Прежний watcher
сравнивал только состояние провайдера. Его проверки шли через ту же таблицу
без рабочего маршрута и не позволяли вернуть канал в пул.

Теперь watcher отдельно сравнивает свои маршруты и правила, восстанавливает
их до проверки WAN и проверяет результат настройки перед сохранением снимка.
На стенде прошли 12 проверок watcher и 16 проверок настройки. Четыре
регрессионных сценария упали на старом коде и прошли на исправлении.
Независимое ревью завершилось без замечаний. На Cudy удалённое правило
восстановилось за 4 секунды, маршрут за 6 секунд. За следующие 12 секунд
стабильного состояния повторной настройки не было.
Исправление установлено и закреплено без перезапуска xr-client.

Повторная проверка поочерёдного отказа каналов начиналась только при двух
работающих WAN, а следующий отказ допускался после восстановления обоих.
При отказе первого WAN свежие DNS-запросы, Direct и WireGuard прошли через
второй канал. Proxy с компьютера администратора сбросил соединение примерно
через 10 секунд. При отказе второго WAN все четыре проверки прошли.
Оба канала восстановлены. Сбой Proxy требует отдельного исправления;
полная проверка резервирования пока не завершена.
