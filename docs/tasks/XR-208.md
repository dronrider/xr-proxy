# XR-208: UDP relay сервера шлёт ответы последнему написавшему роутеру, а не владельцу потока: router_addr это один Mutex, перезаписывается любым расшифровавшимся пиром. Два роутера на одном VPS получают чужой UDP, устройство со знанием ключа угоняет входящий трафик чужого роутера

## Разбор корня

`ServerState` в [udp_relay.rs](../../xr-server/src/udp_relay.rs) держит адрес
роутера одним полем `router_addr: Mutex<Option<SocketAddr>>`. Цикл приёма пишет
туда `peer_addr` любого пакета, который расшифровался, а таск потока при ответе
из интернета читает это же поле. Адресат ответа получается не тот, кто завёл
поток, а тот, кто написал последним: два роутера на одном VPS (ключ обфускации
общий) перетирают поле друг другу, и входящий UDP уходит вперемешку. Отсюда же и
угон: устройство, знающее ключ, шлёт на relay-порт один валидный пакет и
переводит на себя ответы чужих потоков.

Вторая половина корня в ключе таблицы: `flows: HashMap<u16, Flow>` ключуется
только `src_port`. Два роутера с приставкой на одном порту (3074) делят один
поток, и наружу их пакеты уходят через общий сокет, а обратно все ответы идут
одному. Поэтому чинится не только адресат, но и то, чей это поток: пир входит в
ключ, а его адрес живёт в самом потоке.

## Требования

- Поток принадлежит паре (пир, `src_port`), потоки разных пиров не смешиваются.
- Ответ из интернета уходит тому пиру, который поток завёл, независимо от того,
  кто писал на relay-порт последним.
- Keepalive по-прежнему отвечает написавшему.
- Снятие протухшего потока и неудачный bind работают как раньше (гарантии XR-200
  не ломаются): владелец сокета один таск, слот снимает он же, второго сокета на
  тот же ключ не заводится.
- Журнал по-прежнему называет подъём и снятие потока, пир в строке различим.
- Формат `RelayPacket` не трогаем (клиентская половина того же механизма
  закрывается XR-201).
- Регрессионный тест ловит исходную поломку: поток заведён пиром A, следом на
  relay-порт пишет пир B, ответ из интернета обязан уйти A. Тест обязан краснеть
  на старом коде, проверять `regcheck` либо руками возвратом поломки.
- `cargo test --workspace --exclude xr-client --exclude xr-hub` зелёный, без
  warning'ов.

## Что сделано

Таблица потоков ключуется парой (пир, `src_port`): `flows: Mutex<HashMap<FlowKey,
Flow>>`, где `FlowKey = (SocketAddr, u16)`. Пир входит в ключ, поэтому приставки
двух роутеров на одном порту 3074 больше не делят поток и не уходят наружу через
общий сокет. Адрес пира едет в таск потока вместе с ключом и живёт там, а поле
`router_addr` на весь сервер убрано целиком: ответ из интернета таск шлёт тому,
кто поток завёл, и перетереть адресата чужим пакетом больше нечем. Keepalive
по-прежнему отвечает написавшему, он и раньше брал адрес из самого пакета в цикле
приёма.

Гарантии XR-200 остались нетронутыми: сменился только ключ таблицы, а модель
прежняя. Пакет из туннеля кладётся под локом таблицы в очередь своего потока,
приём сразу идёт за следующим, bind выполняет таск потока, слот снимает он же (по
неудачному bind сразу, по простою с перепроверкой очереди под тем же локом), и
владелец сокета один.

Наблюдаемость. В журнале пир теперь различим: `UDP relay: bound source port <N>
for <адрес>` на подъёме и `UDP relay: released port <N> of <адрес> (<M> active)`
на снятии. Строка `UDP relay server: router at <адрес>` из цикла приёма ушла
вместе с общим полем: она называла последнего написавшего и в разборе чужого
трафика только путала. Переполненная очередь пишет в debug `flow <N> of <адрес>
queue full, packet dropped`.

Формат `RelayPacket` не трогали, клиентская половина механизма закрывается
XR-201. Дока: разделы 4.4 и 5.2 `ARCHITECTURE.md` и дизайн-решение в `CLAUDE.md`
переписаны на поток как пару (пир, `src_port`).

## Проверка красноты и мутации

Регрессионный тест `response_goes_to_flow_owner_not_last_writer` заводит поток
пиром-владельцем, следом пишет тем же `src_port` вторым пиром и требует, чтобы
ответ из интернета пришёл владельцу, а второму пиру не досталось ничего.
Соседний `same_src_port_of_different_peers_gives_two_flows` держит вторую
половину корня: у одного `src_port` двух разных пиров два разных сокета наружу и
две записи в таблице.

```
$ regcheck --base main --inline xr-server/src/udp_relay.rs -- cargo test -p xr-server udp_relay
тест краснеет на main и проходит на текущем коде, регрессия закрыта (тесты: xr-server/src/udp_relay.rs)
```

Краснота на main ложная, это несобираемость: тестовый регион переносится на
базу, а там `handle_data_packet` без параметра пира, `ServerState` с полем
`router_addr` и никакого `FlowKey`. Прогон на базе даёт 58 ошибок компиляции
(`E0061` про 4 аргумента вместо 5, `E0063` про пропущенный `router_addr`,
`E0425`/`E0277` про `FlowKey`), до запуска тестов дело не доходит. Настоящая
проверка красноты сделана возвратом поломки (мутация M1), она же первый шаг
сценария.

Мутации по правке, каждая гонялась отдельно с восстановлением файла:

| Мутация | Кто краснеет |
|--------|--------------|
| M1: адрес пира снова общий на весь сервер, ответ уходит написавшему последним (возврат исходной поломки) | `response_goes_to_flow_owner_not_last_writer` |
| M2: ключ таблицы снова только `src_port`, пир едет в таск отдельно | `same_src_port_of_different_peers_gives_two_flows`, `packet_queued_at_retire_is_not_lost`, `idle_flow_releases_socket` |
| M3: неудачный bind не снимает слот | `failed_bind_releases_slot` |
| M4: протухший поток не снимает слот | `idle_flow_releases_socket` |
| M5: снятие протухшего потока без перепроверки очереди | `packet_queued_at_retire_is_not_lost` |
| M6: приём снова ждёт bind | `slow_bind_does_not_block_other_flows` |

Тесты завязаны на время и гонки, поэтому проверены на устойчивость: 30 прогонов
`cargo test -p xr-server udp_relay` подряд, красных нет. Полный прогон
`cargo test --workspace --exclude xr-hub` зелёный, warning'ов нет (`xr-hub` на
маке требует собранного `admin-ui/dist`).

## Сценарий проверки

Шаги 1 и 2 агентские и выполнимы до выката, шаг 3 агентский после выката, шаг 4
пользовательский: два роутера с живым UDP с машины агента не изобразить. Первый
шаг воспроизводит исходную поломку.

1. Агентский, воспроизведение поломки. Вернуть в `xr-server/src/udp_relay.rs`
   общее поле с адресом последнего написавшего:

   ```sh
   python3 - <<'EOF'
   p='xr-server/src/udp_relay.rs'; s=open(p).read()
   s=s.replace("    obfuscator: Obfuscator,\n    flow_timeout: Duration,",
               "    obfuscator: Obfuscator,\n    last_peer: Mutex<Option<SocketAddr>>,\n    flow_timeout: Duration,")
   s=s.replace("        obfuscator,\n        flow_timeout:", "        obfuscator,\n        last_peer: Mutex::new(None),\n        flow_timeout:")
   s=s.replace("ModifierStrategy::PositionalXorRotate),\n            flow_timeout,",
               "ModifierStrategy::PositionalXorRotate),\n            last_peer: Mutex::new(None),\n            flow_timeout,")
   s=s.replace("    let mut flows = state.flows.lock().await;\n    let tx = match flows.get(&key) {",
               "    *state.last_peer.lock().await = Some(peer);\n    let mut flows = state.flows.lock().await;\n    let tx = match flows.get(&key) {")
   s=s.replace("                if let Err(e) = relay_socket.send_to(&wire, peer).await {",
               "                let peer = state.last_peer.lock().await.unwrap();\n                if let Err(e) = relay_socket.send_to(&wire, peer).await {")
   open(p,'w').write(s)
   EOF
   cargo test -p xr-server -- --exact udp_relay::tests::response_goes_to_flow_owner_not_last_writer
   ```

   Тест обязан упасть на `ответ обязан уйти тому, кто завёл поток`. После
   `git checkout xr-server/src/udp_relay.rs` тот же прогон обязан пройти.
   Прогнано:

   ```
   test udp_relay::tests::response_goes_to_flow_owner_not_last_writer ... FAILED
   panicked at xr-server/src/udp_relay.rs:593:14:
   ответ обязан уйти тому, кто завёл поток: Elapsed(())
   test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 11 filtered out

   $ git checkout xr-server/src/udp_relay.rs
   test udp_relay::tests::response_goes_to_flow_owner_not_last_writer ... ok
   test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 11 filtered out
   ```
2. Агентский. `cargo test --workspace --exclude xr-hub` зелёный, а
   `cargo test --workspace --exclude xr-hub 2>&1 | grep "warning:" | grep -v
   generated` пустой. Прогнано, тесты `xr-server` зелёные (12 из 12), вывод
   грепа пустой.
3. Агентский, после выката на обоих VPS. `systemctl is-active xr-proxy-server`
   обязан ответить `active`, а строки подъёма потока в журнале обязаны называть
   пира: `journalctl -u xr-proxy-server --since "10 min ago" | grep -c "bound
   source port [0-9]* for "` обязан совпасть с `grep -c "bound source port"` по
   тому же окну (безымянных строк не осталось).
4. Пользовательский, после выката. Погонять UDP через роутер (игровая приставка,
   VoIP или DNS через туннель) и посмотреть журнал `xr-server`: на подъёме
   потока строка `UDP relay: bound source port <N> for <адрес роутера>`, на
   снятии `UDP relay: released port <N> of <адрес роутера> (<M> active)`, адрес
   в обеих строках это адрес того самого роутера. Ответы при этом доходят по
   назначению, как раньше.
