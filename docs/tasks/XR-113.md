# XR-113: fleet-status: сводка по флоту одной командой (версии/md5 xr-client, xr-server, xr-hub по всем машинам, статус сервисов, exit-IP с роутеров, latest обоих хабов) для пост-деплойной проверки и инцидентов

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 66%, снимок 46м назад, протух, сдвига нет), 2026-08-08.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 67%, снимок 17м назад, сдвига нет), 2026-08-08.

## Что сделано

Заведён [scripts/fleet-status.py](../../scripts/fleet-status.py): опрос всего
флота одной командой и сводка, которую можно судить кодом возврата. Каждая
машина опрашивается одним ssh, все машины разом (пул потоков), потому что
самая долгая часть это роутер за океаном, а не разбор ответа.

Что попадает в сводку:

- бинари: md5, размер и время файла. Версий из бинарей не берём, `--version`
  есть только у `xr-setup`, поэтому личность сборки это md5. Сам по себе он ни
  о чём не говорит, работает сравнением, и сравнение делает сам скрипт:
  одинаковое имя бинаря с разным md5 на двух машинах уходит в проблемы;
- юниты systemd: `is-active`, время последнего запуска, число перезапусков;
- роутер: процесс `xr-client` с pid и RSS, таблицы nftables (`xr_proxy` по
  умолчанию, список задаётся конфигом), хвост `/etc/xr-proxy/crash.log`;
- exit-IP роутера через `cdn-cgi/trace` (curl, на OpenWRT откат на
  `uclient-fetch`) со сверкой с ожидаемым. Живой HTTP-ответ ничего не
  доказывает, Direct отдаёт те же 200, поэтому судим по адресу, который видит
  интернет;
- релиз приложения у обоих хабов: изнутри машины с Host-хедером (оба хаба живут
  под одним именем сайта, публичное имя ведёт только на один) и по публичному
  адресу. Разный `version_code` это проблема: приложение ходит на общее имя и
  попадает то на один хаб, то на другой.

Роль машины (`hub`, `server`, `router`) решает, что спрашивать; `units`,
`binaries` и `nft_tables` в секции перекрывают набор роли целиком, так что
хаб с `xr-web` и `xr-relay` описывается одной строкой.

Адреса флота в репозиторий не едут: конфиг лежит в гитигнорнутом
`local-docs/fleet.ini` (путь переопределяется `FLEET_CONF`), запуск без него
печатает готовый шаблон и останавливается с кодом 2. Формат ini, а не `.env` по
образцу `release.env`, потому что машин у флота произвольное число и у каждой
свой набор ключей, а `configparser` есть в стандартной библиотеке. Зависимостей
у скрипта нет, гоняется и с макбука, и с любой машины флота.

Наблюдаемость. Недоступная машина не выпадает из таблицы молча: она печатается
строкой `НЕДОСТУПНА` с причиной от ssh (шум про known_hosts отбрасывается,
берётся первая содержательная строка), попадает в список проблем и роняет код
возврата. Остальной флот при этом опрашивается до конца. Проблемы называются по
имени машины и предмета, в конце строка `fleet status: ok` либо
`fleet status: проблемы (N)`, код 0 или 1. Есть `--only` для одной машины и
`--json` для машинного разбора.

## Тесты

[scripts/fleet_status_test.py](../../scripts/fleet_status_test.py), 18 тестов,
стенд из заглушек по образцу `xr-hub/tests/release_apk_script.rs`. Заглушка ssh
запускает собранный скрипт снимка настоящим `sh`, а `systemctl`, `nft`,
`pidof`, `curl` и `uname` отвечают из каталога своей машины на стенде, поэтому
проверяется не текст скрипта, а сводка после прогона. md5 и размер считаются
по-настоящему: файлы бинарей на стенде лежат, а заглушки `md5sum` и `stat`
нужны только потому, что на макбуке нет ни GNU-шного `stat -c`, ни `md5sum`.

Проверяются зелёный флот целиком, шаблон при отсутствии конфига (и то, что
шаблон разбирается самим скриптом), недоступная машина, расхождение сборки
между хабами, расхождение релиза, хаб без релиза, мёртвый юнит, пропавшие
бинарь, таблица nftables и процесс, exit-IP не из ожидаемых и невыясненный,
`--only`, `--json`, доставка порта и ключа из конфига до ssh. Плюс юниты на
чистые функции: разбор манифеста, разбор снимка с посторонним выводом машины,
откат ожидаемых exit-IP на адреса серверов, дефолты ролей, вычитание шума из
причины ssh.

Краснота проверена мутациями: снятие строки про неответившую машину роняет
`test_unreachable_machine_is_named` и `test_json_report`, отключение сверки
сборок и релизов роняет свои два теста. Первый прогон стенда сам поймал
подмену: расхождение сборки искалось по имени бинаря, а на стенде второй файл
лежал под другим именем, и мутация проходила зелёной.

## Сценарий проверки

Гонять с машины владельца, там лежат адреса флота.

```
cd ~/projects/xr-proxy

# 1. Тесты стенда.
python3 scripts/fleet_status_test.py
# ожидается: Ran 18 tests ... OK

# 2. Запуск без конфига печатает шаблон и не делает вид, что всё хорошо.
FLEET_CONF=/tmp/нет-такого.ini python3 scripts/fleet-status.py; echo "код: $?"
# ожидается: «ОШИБКА: нет ... Завести его по шаблону», шаблон с секциями
# [hub-primary]/[vps-de]/[router-ru], код 2

# 3. Завести local-docs/fleet.ini по этому шаблону: два хаба (адреса и
# SECONDARY_HOST_HEADER берутся из local-docs/release.env), exit-VPS с их
# exit_ip, оба роутера с expect_exit_ip.

# 4. Сводка по живому флоту.
python3 scripts/fleet-status.py; echo "код: $?"
# ожидается: секция на каждую машину с md5 бинаря, «юнит xr-hub: active»,
# «процесс xr-client: pid ...», «таблица nftables ip xr_proxy: есть»,
# «exit-IP: <адрес> (ожидаемый)», «latest изнутри машины: <версия> (code N)» у
# обоих хабов с одинаковым code, в конце «fleet status: ok» и код 0

# 5. Роутер отдельно и машинный вид.
python3 scripts/fleet-status.py --only <имя-роутера>
python3 scripts/fleet-status.py --json | python3 -m json.tool | head -40
# ожидается: в JSON поля machines[].reachable и problems

# 6. Наблюдаемость: недоступная машина обязана быть видна. Подменить у одной
# машины порт на заведомо глухой и прогнать снова.
FLEET_CONF=<копия конфига с port = 22222 у одной машины> \
    python3 scripts/fleet-status.py; echo "код: $?"
# ожидается: «НЕДОСТУПНА: ssh: connect to host ... » у неё, «машина не
# ответила» в проблемах, остальные машины опрошены, код 1
```

## Ревью

- scripts/fleet-status.py:231 в snapshot_script host_header из конфига вставляется в одинарные кавычки sh-скрипта без shlex.quote (в отличие от binaries/units/nft_tables, которые все через shlex.quote). Значение с апострофом ломает генерируемый скрипт и позволяет впрыснуть команды, выполняемые на удалённой машине по ssh: host_header = evil'; touch /tmp/pwned; echo ' даёт в snapshot_script строку resp=$(curl -sk --max-time 15 -H 'Host: evil'; touch /tmp/pwned; echo '' https://127.0.0.1/..., и команда touch выполнится на целевой машине. Завернуть host_header в shlex.quote() как остальные значения.
- scripts/fleet-status.py:225-226,273-274 хвост crash.log (tail -1 | cut -c1-160) кладётся в printf 'crash\t%s\n' без вычитки табов, в отличие от latest-ответа хаба, где явно стоит tr -d '\n\t'. Если в последней строке crash.log (там dmesg OOM и фрагмент logread, где табы обычны) встретится литеральный таб, parse_snapshot возьмёт только часть до первого таба (parts[2]), остаток сообщения молча потеряется. Показал на parse_snapshot('crash\tok\tOOM убил xr-client\tсвободно 12MB\n') -> snap['crash'] == 'OOM убил xr-client', вторая половина пропала. Вычищать табы на стороне снимка так же, как это сделано для latest.
