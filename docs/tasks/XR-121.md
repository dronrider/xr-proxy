# XR-121: Ошибки инвайт-шар не логируются и текст 410 сырой: nativeInviteShares возвращает json_error без journal_log (в отличие от манифеста), FilesViewModel кладёт ошибку только в UI-message. Логировать в журнал + человеческий текст на 410 (инвайт истёк/отозван, переприменить), различать 410 от прочих

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 87% профицит, снимок 1ч 25м назад, протух, сдвига нет), 2026-08-03.
- Ревью: субагент sonnet/high по вердикту pick (маппинг sonnet, корректор: профицит week_all; квота: week_all 93% профицит, снимок 4м назад), 2026-08-03.

## Причина

`Java_com_xrproxy_app_jni_NativeBridge_nativeInviteShares` (`xr-android-jni/src/lib.rs`)
на ошибке `list_invite_shares` сразу отдаёт `json_error(&e)`, без записи в
журнал. Соседний `nativeFetchManifest` на той же развилке (`Ok(Err(e)) |
Err(e)`) пишет `journal_log("WARN", "files", ...)` - у инвайт-шар этого шага
никогда не было, поэтому «список по инвайту не грузится» было нечем
диагностировать в журнале.

На стороне Kotlin `FilesViewModel.refreshHub` берёт `it.message` из
`Result.failure` как есть и кладёт в `message` без прогона через `humanError`
(в отличие от путей манифеста и скачивания, которые уже используют
`humanError`). Сырой текст ошибки это `http_<код>` (формат из
`xr-core/sync.rs`, `list_invite_shares`: `Err(format!("http_{}", ...))`), 410
от прочих кодов ничем не отличался ни в логике, ни в тексте.

## Исправление

- `xr-core/src/sync.rs`: `pub fn is_invite_gone(err: &str) -> bool` рядом с
  `list_invite_shares` - `true` только для `http_410`, различие вынесено в
  одну тестируемую функцию (переиспользует приватный `http_status`).
- `xr-android-jni/src/lib.rs`: ветка ошибки `nativeInviteShares` пишет
  `journal_log` - `WARN` на `is_invite_gone` (истёкший/отозванный инвайт это
  штатный исход), `ERROR` на всё остальное (сбой хаба, битый ответ - раньше
  об этом не было ни строки в журнале).
- `FilesViewModel.kt`: `humanError` получил ветку `e == "http_410" ->
  "инвайт истёк или отозван, примените его заново"`; `refreshHub` теперь
  прогоняет ошибку через `humanError` вместо сырого `it.message` (как уже
  делают пути манифеста и скачивания).

## Проверка

- Юнит `xr-core`: `sync::tests::is_invite_gone_matches_only_410` -
  `http_410` да, `http_403`/`http_500`/`network: ...`/`parse: ...` нет.
  `cargo test -p xr-core is_invite_gone` зелёный.
- Мутационный разбор `is_invite_gone` (правки временные, откачены):
  `Some(410) -> Some(400)` роняет тест; `==` на `!=` роняет тест; тело на
  `false` роняет тест (падает на `assert!(is_invite_gone("http_410"))`).
- `cargo test --workspace --exclude xr-client` зелёный (141 тест в
  `xr-core`, полный воркспейс без варнингов); `sync::tests::
  test_upload_roundtrip` один раз мигнул флаком на параллельном прогоне и
  тут же прошёл в одиночном запуске - существовавшая до правки флакующая
  проба сети, к `is_invite_gone` отношения не имеет.
- Kotlin-часть: `xr-android/build.sh` не гонялся (полная сборка APK, файл
  сам просит запускать её вне сессии Claude Code ради памяти) - правка
  просмотрена вручную, синтаксис и стиль соответствуют соседним веткам
  `humanError`.

## Границы

Только консьюмер (`xr-core` + `xr-android-jni` + Android UI), хаб и агент
не тронуты - `http_410` уже отдаётся хабом (LLD-19 п. 9.5), задача про то,
что с ним делает клиент.
