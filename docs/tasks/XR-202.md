# XR-202: Хендшейк xr-server без общего дедлайна: timeout на каждый read по отдельности, slow-loris держит permit из max_connections, 256 таких коннектов запирают приём

## Что происходит

У хендшейка xr-server нет общего дедлайна: timeout стоит на каждый read
по отдельности. Slow-loris клиент, подающий байты с паузами, держит permit
из max_connections, 256 таких коннектов запирают приём новых туннелей.

## Чего хотим

Хендшейк идёт под общим дедлайном: не договоривший вовремя клиент теряет
коннект и permit, приём свободен. Задача из состава цели XR-286, конвейер
идёт по её файлу.

## DoD

- Общий дедлайн на весь хендшейк xr-server; при превышении коннект
  закрывается и permit из max_connections освобождается сразу, а не по
  сумме покомпонентных timeout.
- Интеграционный тест: медленный клиент, не договоривший хендшейк,
  отваливается по дедлайну и не занимает слот приёма.

## Ранг

25+4+2+0+2 = 33, P2, размер S.

- Серьёзность 25 (Major). Приём новых туннелей на сервере запирается, но
  только под целенаправленной атакой: атакующему нужен туннельный порт
  и терпение капать байты, в спокойной жизни ничего не ломается. Обход
  дешёвый и очевидный, перезапуск сервера возвращает приём.
- Ценность 4. Заметное усиление, которого просит цель XR-286. Слот приёма
  перестаёт быть расходником для медленного клиента, сервер держит
  внешний напор без участия дежурного.
- Неопределённость 2. Подход задан постановкой, место правки известно.
  Развилки остались в деталях: где провести границу дедлайна в коде
  хендшейка и что делать с покомпонентным таймаутом read. Решилось
  обёрткой всего пути до релея и снятием внутреннего таймаута.
- Поправка на баг 0. Новая граница защиты, ничего работающего
  не сломалось.
- Рычаг 2. Небольшая своя польза. Закрытие открывает XR-204, отмеченную
  «после XR-202», и держит жёсткость сервера для соседних задач цели.

## Ревью

- Тест deadline_releases_connection_slot_for_next_client зелёный на старом коде. Проверено прогоном обоих новых тестов на копии main с возвращённым покомпонентным таймаутом read и снятым общим дедлайном. slow_drip на ней краснеет, deadline_releases проходит. Причина в самом тесте: медленный клиент шлёт два чанка по 64 байта и замолкает. Замолкший read рвётся покомпонентным таймаутом примерно через секунду, слот освобождается тем же путём, честный коннект обслуживается. Различает непрерывное капанье до прихода честного клиента. На старом коде permit при нём занят, try_acquire отвергает честного, ConnectAck не приходит. Отдельно про ворота: regcheck красил базу ошибкой компиляции. Сплайс переносит в base только тестовый регион, а тесты зовут serve_connection и read_first_frame в новой арности, которых в базе нет. Прогон новых тестов против старого кода ворота не делали. Опора в ручной перепроверке, она покрыла только slow_drip. Прошу перевести медленного клиента на непрерывное капанье до обслуживания честного: исправлено, медленный клиент в тесте слота каплет циклом по 64 байта с паузой 50 мс до самого конца теста; оба теста прогнаны против старой семантики (копия ветки с возвращённым покомпонентным таймаутом read и снятым общим дедлайном), deadline_releases на ней красный: permit занят, честный коннект не получает ConnectAck, слот отличён именно от замолкшего клиента.
- Корневой server.toml остался со старым комментарием. Строка 18 трекаемого с первого коммита шаблона всё ещё называет connection_timeout_sec «Idle connection timeout (seconds)». Сам шаблон подписан «Place this file at /etc/xr-proxy/server.toml on your VPS». Ветка переописала то же поле в configs/server.toml, xr-proto/src/config.rs и ARCHITECTURE.md как общий дедлайн хендшейка. Читающий корневой шаблон настроит поле под исчезнувшее поведение. Прошу поправить комментарий той же веткой: исправлено, строка 18 корневого server.toml переописана как «Общий дедлайн хендшейка (секунды), XR-202», тем же текстом, что configs/server.toml.

Второй проход, 2026-08-29, по коммитам f4036242, 10a795dc и e1a03b89. Оба замечания закрыты, новых нет. Медленный клиент в тесте слота каплет циклом по 64 байта с паузой 50 мс в фоновой таске до конца теста, запись идёт через into_split. ## Сценарий проверки

Агентский, после выката. Выкат рестартует xr-server на обеих VPS, короткий
провал приёма это сам рестарт, сценарий больше сервер не трогает: одна
проба держит ровно одно соединение. Ключ обфускации не нужен, зонд
недоговороспособен по построению.

1. Прочитать настроенный дедлайн на машине командой `ssh <vps> grep
   connection_timeout_sec /etc/xr-proxy/server.toml`. Отсутствующая строка
   означает умолчание 300 секунд.
2. С машины с выходом в интернет открыть TCP на туннельный порт VPS и
   отправить семь байт (любых) по одному с паузой 30 секунд. Семи байт
   мало для разбора заголовка кадра. Сервер не может ни принять кадр,
   ни отвергнуть его как чужой, обязан ждать и закрыть зонд должен только
   по дедлайну. Замерить время от connect до закрытия соединения сервером
   (EOF на чтении).
3. Критерий. Соединение закрывается через срок, равный значению из шага 1
   (плюс-минус пара секунд). Жить неограниченно долго зонд не вправе: на
   старом коде каждый байт обновлял таймаут read, и он висел бы вечно.
4. Повторить шаги 2-3 на второй VPS.
5. Убедиться, что приём жив: после закрытия пробы честный коннект клиента
   (любой рабочий роутер или телефон с приложением) поднимается и ходит
   через туннель как обычно.
