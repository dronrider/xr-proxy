# XR-305: Исходящий выход нельзя проверить на боевом пути: канарейка XR-299 говорит старым протоколом, а выбор выхода не пишется в журнал

## Что происходит

Разбирая «утечку» ChatGPT мимо резидента (XR-299, 2026-10-16), я упёрся в три
дыры наблюдаемости гарантии. Живой путь нельзя проверить штатной канарейкой,
а результат применения правила не виден в журнале.

1. Роутеры ходят на сервер муксом, соединения LAN-устройств в журнале
   xr-server это строки `sid=N -> домен`. Канарейка `.devkit/canary-tunnel.sh`
   с бинарём `/tmp/xr-canary` говорят старым протоколом, один кадр Connect, и
   проверяют handler.rs. Боевой путь mux_handler.rs живьём не проверяет никто.
   Юниты гоняют его с фейковым SOCKS5, интеграционный outbound_resident.rs
   тоже ходит старым протоколом. Путь мукса случайно доказали журнальные WARN
   об отказе резидента, строки `outbound ... failed` рядом с `sid=`, но удачное
   прохождение в журнале не видно вовсе.
2. Выбор выхода не пишется в журнал. Строка стрима называет цель, но не
   говорит, ушёл он через резидента или напрямую. В разборе пришлось судить по
   косвенным уликам, conntrack и сокетам процесса. Вывод «утечки нет»
   опирается на совпадение нескольких фактов, одной журнальной строки для
   него нет.
3. Совет проверки из задачи XR-299 не работает. «Открой api.ipify.org с
   устройства в LAN» показывает домашний IP, потому что решение первым
   принимает клиент роутера и домен без правила пускает напрямую, проверил
   curl с мака за роутером 2026-10-16. До мукс-пути боевого трафика совет не
   достаёт.

## Чего хотим

Канарейка исходящего выхода говорит муксом и прогоняет цель через боевой путь
mux_handler.rs. У чувствительного домена эхо-ответ несёт адрес резидента, у
домена без правила адрес сервера. Выбор выхода виден в журнале строкой стрима
или соседней строкой, по журналу одного сервера понятно, через что прошла
каждая цель с outbound-правилом. Сценарий проверки задачи XR-299 заменяет
совет «открой с устройства в LAN» на мукс-канарейку, интеграционный тест
гоняет чувствительную цель муксом с фейковым резидентом.

## DoD

- Мукс-канарейка против боевого туннеля возвращает резидентский IP для
  чувствительного домена и адрес сервера для домена без правила.
- Интеграционный тест в xr-server открывает чувствительную цель муксом и
  видит её выход через фейковый SOCKS5, не напрямую.
- В журнале xr-server выбор выхода виден и без отказа, строка стрима или
  соседняя называет выход для целей с outbound-правилом.
- Сценарий проверки исходящего выхода в доке ссылается на мукс-канарейку,
  совета «открой домен с устройства в LAN» больше нет.

## Ранг

`25+6+2+0+2 = 35`, P2.

- Серьёзность 25 (Major). Гарантия работает, но единственная штатная проверка
  ходит не тем код-путём, а результат применения правила не виден в журнале.
  Следующая регрессия выхода всплывёт таким же разбором на полдня.
- Ценность 6. Наблюдаемость гарантии, ради которой покупался резидент.
- Неопределённость 2. Мукс-протокол и фейковый SOCKS5 уже в дереве, канарейка
  повторяет существующий бинарь другим кадром, открыта только форма записи
  выбора выхода в журнал.
- Поправка на баг 0. Новая проверяемость, чиненого дефекта нет.
- Рычаг 2. Журнальная строка выхода пригодится любому следующему
  чувствительному правилу.
