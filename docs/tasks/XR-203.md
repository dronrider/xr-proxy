# XR-203: UDP relay клиента и сервера без единого теста: keying флоу, спуф-сокеты IP_TRANSPARENT, разбор cmsg IP_ORIGDSTADDR и очистка по таймауту не покрыты

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 66%, снимок 46м назад, протух, сдвига нет), 2026-08-08.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 67%, снимок 36м назад, сдвига нет), 2026-08-08.

## Что было

Строка доски заведена, когда relay не был покрыт вовсе. За это время XR-200,
XR-201 и XR-208 принесли свои тесты: таблица флоу клиента с NAT по туннельному
порту, очередь на поток и ключ `(пир, src_port)` на сервере уже гоняются
юнитами. Непокрытым остался тот слой, что сцеплен с сокетами и с ядром: разбор
ancillary data `IP_ORIGDSTADDR`, сборка `sockaddr_in` для спуфящего сокета и
`sendto`, отбор перехваченного (`source_ips`, исключённые порты, LAN и
рассылки), ответ на keepalive и переполнение очереди потока.

## Что сделано

Чистая часть выделена из тел циклов, чтобы её можно было звать юнитом:

- `should_relay` в [xr-client/src/udp_relay.rs](../../xr-client/src/udp_relay.rs)
  вместо четырёх `continue` в цикле upstream;
- `origdst_from_cmsg` там же: проход по списку cmsg отдельно от `recvmsg`.
  Адресат без порта считается отсутствующим cmsg (раньше то же самое решалось
  сравнением с нулём после разбора);
- `sockaddr_in_v4` и `socket_addr_v4`: сборка и разбор адреса ядра одним местом
  на `do_sendto`, `create_spoof_socket` и `do_recvmsg`;
- `handle_datagram` в [xr-server/src/udp_relay.rs](../../xr-server/src/udp_relay.rs):
  разбор датаграммы и ветка keepalive выехали из тела цикла приёма.

Поведение при этом не менялось, кроме текста ошибки про отсутствующий cmsg
(в нём было длинное тире).

Покрыто тестами: отбор перехваченного вместе с границей 172.16/12, порядок байтов
в адресе ядра, живой `sendto` и отказ на IPv6, разбор `IP_ORIGDSTADDR` (в том
числе когда нужный cmsg лежит за чужими), отсутствие cmsg как названная причина,
keepalive-ответ написавшему, мусор на relay-порту без ответа и без потока,
переполнение очереди потока, посадка на соседний порт при занятом.

Под Linux дополнительно гоняются два теста, которым нужно настоящее ядро:
`recvmsg_reads_origdst_from_kernel` (ancillary data приходит от ядра, а не из
собранного тестом буфера) и `spoof_socket_binds_to_foreign_address` (без
CAP_NET_ADMIN судит только отказ). На маке они не компилируются и пропускаются.

## Сценарий проверки

Агентский, машина разработчика, ничего выкатывать не надо.

1. Клиентская половина (на маке она не входит в прогон рабочей области):

   ```
   cargo test -p xr-client udp_relay
   ```

   Ожидание: `test result: ok`, 31 тест. Покрывают таблицу флоу с туннельным
   портом, кэш спуфящих сокетов, отбор перехваченного, адреса ядра и разбор cmsg.

2. Серверная половина:

   ```
   cargo test -p xr-server udp_relay
   ```

   Ожидание: `test result: ok`, 14 тестов. Покрывают очередь на поток, ключ
   `(пир, src_port)`, keepalive, мусор на порту, переполнение очереди и bind.

3. Рабочая область целиком и нулевые warnings:

   ```
   cargo test --workspace --exclude xr-client
   cargo test --workspace --exclude xr-client 2>&1 | grep "warning:" | grep -v "generated"
   ```

   Ожидание: все крейты зелёные, второй командой пусто.

4. Два теста под Linux-гейтом. Прогнать их на маке нечем, поэтому в контейнере
   (Docker, ядро настоящее, эмуляции нет):

   ```
   docker run --rm -v "$PWD":/w -w /w -e CARGO_TARGET_DIR=/tmp/t rust:1-slim \
     cargo test -p xr-client udp_relay
   ```

   Ожидание: `test result: ok`, 33 теста вместо 31, среди них
   `recvmsg_reads_origdst_from_kernel` и `spoof_socket_binds_to_foreign_address`.
   Второй без CAP_NET_ADMIN судит отказ, и это ожидаемо: контейнеру такого права
   не дают.

5. Сборка под боевую цель роутера (нужен Docker, идёт долго):

   ```
   cross build --tests --target aarch64-unknown-linux-musl -p xr-client
   ```

   Ожидание: `Finished`, без warnings. `cross test` на этой цели не идёт, qemu не
   поднимает статический musl-бинарь, поэтому прогон гейтов остаётся за шагом 4.
