# XR-284: UDP приложений пропадает в туннеле Android без следа

записан 2026-08-25

## Черновик

### Ситуация

Найдено 2026-08-25 при разборе поломки MAX (XR-283). Разбор пакетов из TUN в
`xr-core/src/engine.rs:648-657` отдаёт `try_handle_dns` только UDP/53 IPv4,
всё остальное складывает в общую очередь; переписывание адресов ниже идёт
только при `protocol == 6` (`engine.rs:666`), а пакет любого протокола
безусловно уходит в smoltcp (`engine.rs:740`). UDP-сокет в стеке не заводится
ни разу: `IpStack::add_udp_socket` (`ip_stack.rs:282`) не вызывается нигде по
репозиторию. Интерфейс поднят с `set_any_ip(true)`, поэтому пакет принимается
за свой и умирает внутри стека. Наружу мимо туннеля он тоже не уходит: маршрут
`0.0.0.0/0` забран VpnService (`XrVpnService.kt:451`).

### Осложнение

Всё, что живёт на UDP, на телефоне с поднятым туннелем не работает и молчит
об этом. Звонки WebRTC не соединяются вовсе: сигналинг по TCP жив, медиа-поток
нет, выживают только клиенты с TURN over TLS. QUIC откатывается на TCP по
таймауту, то есть каждая такая сессия платит задержкой. Приложение со своим
UDP-транспортом просто висит. В логах клиента о выброшенных пакетах не остаётся
ни строки, так что пользователь приходит с «не работает», а не с причиной.

### Вопрос

Заворачивать UDP в туннель (в протоколе релей уже есть, `xr-proto/src/udp_relay.rs`,
но `xr-core` его не использует) или на первом шаге хотя бы выпускать UDP мимо
туннеля через protected-сокет? Второе дешевле и чинит звонки, но уводит их из
защиты и показывает реальный IP.

### Гипотеза

UDP-трафик приложений на телефоне доходит до адресата, а не тонет в стеке; если
его куда-то не пускают, это видно в логе клиента.
