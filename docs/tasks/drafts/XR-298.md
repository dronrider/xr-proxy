# XR-298: второй хаб публично лежит две недели, сторож молчит

записан 2026-09-28
приоритет: высокий

## Черновик

### Ситуация

Замечено 2026-09-28 на выкате XR-296. Упал шаг «проверка latest на втором
хабе» скрипта scripts/release-apk.sh. Curl изнутри машины второго хаба на
https://127.0.0.1 с подставленным Host отдал код 000, файла ответа не
появилось. Разбор на месте показал мёртвый nginx. `systemctl status nginx`
говорит `failed` с 13 сентября, в журнале
`nginx: [emerg] bind() to 0.0.0.0:443 failed (98: Address already in use)`.
Сейчас на 80 и 443 не слушает вообще никто. Конфиг валиден, `nginx -t`
чистый. Сервис поднимается штатным `systemctl start nginx`. Сам xr-hub жив:
юнит active, `/healthz` отвечает ok, релиз 0.112.0 лежит на месте и отдаётся
на 127.0.0.1:8080.

### Осложнение

Второй хаб две недели недоступен снаружи. Приложение не получает с него ни
обновлений, ни ответов API. Вся нагрузка идёт на первичный хаб, а резерва,
ради которого второй хаб держат, нет. Заметить это было нечем. Сторож
crash-loop `deploy/xr-service-alert.sh` (XR-226) смотрит три юнита,
xr-proxy-server, xr-relay и xr-hub. Nginx в этот список не входит. Сводка
`scripts/fleet-status.py` (XR-113) судит юниты и релиз у обоих хабов. Релиз
второго хаба она спрашивает изнутри машины с подставленным Host, то есть мимо
nginx. Падение фронта ей не видно. Молчание неотличимо от штатной работы.
Всплыло это случайно, на постороннем выкате.

### Вопрос

Чем судить фронт: добавить nginx в список юнитов сторожа, спрашивать хаб
снаружи настоящим запросом по HTTPS, или и то и другое? Второй хаб публично
недоступен по адресу первичного. Внешняя проверка с машины владельца упирается
в тот же Host-подлог, которым ходят release-apk.sh и fleet-status.py.

### Гипотеза

Падение фронта у любого хаба флота видно в тот же час строкой алерта.
`fleet-status.py` даёт по такой машине ненулевой код с названной причиной.
