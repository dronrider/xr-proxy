# XR-109: скрипт релиза APK одной командой

Релиз APK сейчас это цепочка ручных шагов, которую агент повторяет в каждом
релизном чате: clean + `build.sh --release`, подпись `xr-hub sign-release` с
проверкой подписи, staging-заливка на первичный хаб с бэкапом манифеста и
проверкой `latest`, заливка на второй хаб (rsync --partial) с проверкой через
Host-хедер. Шаги детерминированные, но каждый прогон съедает десятки
tool-вызовов и токенов на логи gradle/scp, а пропуск шага (staging, бэкап
манифеста) выясняется только на устройстве. Прецедент упаковки такого флоу уже
есть: `scripts/release-xr-share.sh`.

## Что делает скрипт

`scripts/release-apk.sh`, запуск с мака из корня репозитория. Шаги:

1. Префлайт: ключ подписи на месте, env-файл прочитан, версия в
   `build.gradle.kts` совпадает с ожидаемой (versionName/versionCode берутся из
   gradle, не передаются руками).
2. Сборка: clean + `xr-android/build.sh --release`, versionCode/pubkey через
   `ORG_GRADLE_PROJECT_*`. Полный лог сборки в файл, в stdout только итог.
3. Подпись: `xr-hub sign-release` локально, следом проверка подписи манифеста.
4. Первичный хаб: бэкап текущего манифеста, файлы в staging-каталог, атомарный
   mv, проверка `latest` по HTTPS.
5. Второй хаб: rsync --partial, проверка `latest` локально через Host-хедер.
6. Итоговая сводка одним блоком: versionName/versionCode, sha256 APK, ответы
   `latest` обоих хабов. Агенту для верификации достаточно этого блока.

Падение на любом шаге останавливает прогон (`set -euo pipefail`). Для
перезапуска с середины (сборка долгая) флаги вида `--skip-build` /
`--only-upload`.

## Конфигурация

Адреса, порты, пути на хабах и путь к ключу живут в гитигнорнутом
`local-docs/release.env`, скрипт его source'ит. В коммитируемом скрипте только
роли (первичный хаб, второй хаб), без IP и доступов.

## Что остаётся за агентом и владельцем

Скрипт не решает, когда и что релизить: бамп versionName/versionCode в gradle,
запись в доску и device-verify остаются как были.

## DoD

- `scripts/release-apk.sh` проходит весь путь от сборки до проверенного
  `latest` на обоих хабах одной командой.
- Секреты и адреса только в `local-docs/release.env`, скрипт коммитится чистым.
- Частичный перезапуск после падения без повторной сборки.
- Строка про скрипт в разделе Scripts проектного `CLAUDE.md`, чтобы агент
  находил его вместо ручной цепочки.

## Сценарий проверки

Выпустить очередную версию APK этим скриптом: один запуск, по сводке видно
версию и sha256, оба хаба отдают новый `latest`, приложение на устройстве
видит обновление.

## Что сделано

`scripts/release-apk.sh` гоняет весь путь: префлайт, сборка, подпись, заливка на
оба хаба, проверка `latest`. Адреса, порты, путь к ключу и Host второго хаба
живут в гитигнорнутом `local-docs/release.env` (путь переопределяется
`RELEASE_ENV`), запуск без файла печатает готовый шаблон и останавливается. В
коммит уехали только роли машин.

Расхождение с постановкой одно: версию из `build.gradle.kts` взять негде, её там
нет by design (`versionCode` без гредл-проперти равен единице). Поэтому версия
приходит флагами `--version`/`--version-code`, а скрипт судит её по живому
релизу: код обязан расти, иначе приложение обновление не предложит и прогон
останавливается до сборки. `--bump` избавляет от ручного счёта, беря код живого
релиза плюс единицу и имя версии по нашему соглашению `0.<код>.0`.

Проверка подписи была самой ручной частью цепочки, поэтому появилась команда
`xr-hub verify-release`: берёт либо ответ `/api/v1/app/latest` целиком
(`--signed -`), либо локальную пару `manifest.json`/`manifest.sig`, проверяет
подпись публичной половиной и сверяет версию, код и sha256 с ожидаемыми. С
`--key` публичная половина выводится из приватного ключа, и на этом стоит
префлайт: подпись живого манифеста своим ключом это единственный доступный
способ узнать, что ключ не перепутан, а перепутанный ключ означает OTA, которое
установленные приложения отвергнут.

Заливка идёт не поверх живых файлов: файлы уезжают в `.staging-<версия>` рядом с
`releases/`, прежняя пара манифестов копируется в `*.bak.<ts>`, и только потом
всё переезжает переименованием, APK раньше манифеста. Так хаб ни секунды не
отдаёт манифест на ещё не доехавший APK. Заливка идёт `rsync --partial
--inplace`, обрыв на медленном канале второго хаба докатывается
`--only-upload` без повторной сборки (для этого случая равенство версии живой
считается нормой, для нового релиза оно ошибка).

Проверяется прогон стендом `xr-hub/tests/release_apk_script.rs`: заглушки ssh,
rsync и curl вместо настоящих, хабы это два каталога, а подпись и проверка идут
настоящим `xr-hub`. Тесты смотрят не на текст скрипта, а на то, что после
прогона лежит на «хабах»: новый APK и манифест с нужным кодом, бэкап прежней
пары, убранный staging, старый APK на месте. Отдельно проверены отказ на
неросущем коде, отказ на чужом ключе (оба до сборки), `--only-upload` без
пересборки, сухой прогон, который не трогает ни хабы, ни сборку, и печать
шаблона без env-файла. Краснота стенда проверена мутациями: снятый бэкап роняет
первый тест, пропущенный второй хаб роняет три.

Дока: строка в разделе Scripts проектного `CLAUDE.md`, раздел «Всё это одной
командой» в `docs/HUB-DEPLOY.md` перед ручной цепочкой (она осталась описанием
того, что делает скрипт, и путём на нештатный релиз), упоминание
`verify-release` в `ARCHITECTURE.md` рядом с LLD-12.

Боевого релиза этой веткой не делалось: скрипт проверен сухими прогонами и
стендом.
