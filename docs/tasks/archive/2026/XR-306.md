# XR-306: Apple-домены через резидентский SOCK

## Что происходит

Персональные запросы Apple (Apple ID, iCloud, Siri, App Store) с устройств
LAN выходили наружу с адресов хостинга. В пресете russia лежали только три
домена Apple в группе «AI-сервисы», а в правиле роутинга xr-server их не
было вовсе. Гарантия XR-299 требует от чувствительных доменов пути через
резидента и без живого резидента рвёт соединение. На Apple она не
распространялась.

## Чего хотим

Персональные домены Apple ходят через резидентский SOCK на всех серверах.
Для этого группа «Apple» ложится в пресет russia обоих хабов, а правило с
`outbound = "resident"` раскладывается в /etc/xr-proxy/server.toml всех
VPS. Список доменов собран по доке Apple «Use Apple products on enterprise
networks» (support.apple.com/101555). В него вошли *.apple.com (там
Apple ID, Siri guzzoni, Spotlight smoot, push), *.icloud.com,
*.icloud-content.com, *.me.com, *.cdn-apple.com, *.apple-cloudkit.com,
*.mzstatic.com. *.aaplimg.com в список не попал. Домен несёт громкие
загрузки обновлений ОС, персональных запросов там мало.

## DoD

- Правило Apple с `outbound = "resident"` стоит на всех трёх VPS. Журнал
  каждого называет четыре чувствительных правила строкой Outbound
  guarantee.
- Пресет russia обоих хабов принял группу «Apple» после «Claude», и три
  apple-домена ушли из «AI-сервисы» (timeweb v56, aeza v45).
- Эталон configs/routing-russia.toml несёт ту же группу Apple.

## Сценарий проверки

1. На каждом VPS команда `grep -A4 'name = "Apple"' /etc/xr-proxy/server.toml`
   показывает семь доменов. Журнал xr-server после старта называет четыре
   чувствительных правила строкой Outbound guarantee.
2. GET /api/v1/presets/russia на хабе отдаёт группу «Apple» с теми же семью
   доменами. У timeweb версия 56, у aeza 45.
3. С устройства в LAN команда `curl -sI https://www.apple.com | grep -i geo`
   отвечает `geo=SG`. Apple видит адрес сингапурского резидента на полном
   боевом пути LAN -> роутер -> туннель -> сервер -> резидент.
4. С VPS команда `curl --socks5-hostname <резидент> https://api.ipify.org`
   возвращает адрес резидента. Напрямую тот же curl возвращает адрес
   хостинга.

- Исключение: обкатка (шаги идут на живом флоте по ssh и в LAN, чистое
  дерево их не воспроизводит; все четыре шага прогнаны на боевых машинах
  в этом сеансе, итоги в «Ходе работы»).

## Проверка

Прогон сценария 2026-10-20 21:1x, живой флот. Адреса машин в выводе
заменены ролями, конкретика в local-docs.

Шаг 1. Grep находит блок Apple в конфиге каждого VPS. Журнал xr-server
после рестарта говорит одно и то же на всех трёх:

    Outbound guarantee: 4 sensitive rule(s), direct exit for them is disabled

Шаг 2. GET /api/v1/presets/russia отдаёт группу «Apple» из семи доменов.
Версии: timeweb 56, aeza 45.

Шаг 3. Ноутбук в LAN, полный боевой путь. Публичный адрес ноутбука совпал
с WAN-адресом домашнего роутера, то есть замер шёл через него.
www.apple.com ответил заголовком `set-cookie: geo=SG`. Apple видит адрес
сингапурского резидента.

Шаг 4. Curl с VPS через резидента возвращает адрес резидента. Прямой curl
возвращает адрес хостинга.

## Ранг

`25+2+2+0+1 = 30`, P2.

- Серьёзность 25 (Major). Гарантия XR-299 не покрывала Apple. Персональные
  запросы выходили с адресов хостинга.
- Ценность 2. Один резидентский IP для Apple-запросов всех устройств LAN.
- Неопределённость 2. Механизм XR-299 готов, работа раскладочная.
- Поправка на баг 0.
- Рычаг 1.
