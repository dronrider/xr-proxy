# XR-209: Одна ошибка accept() убивает листенер целиком в xr-server и xr-client (result?), транзиентный EMFILE при всплеске fd рвёт прокси для всех сразу; в xr-relay тот же случай обработан паузой, надо повторить

## Разбор корня

Accept-цикл xr-server в [main.rs](../../../../xr-server/src/main.rs) выходил из `main`
по любой ошибке accept (`let (stream, addr) = result?;`), а xr-client в
[proxy.rs](../../../../xr-client/src/proxy.rs) точно так же ронял `run_proxy`
(`listener.accept().await?`). Ошибки accept при этом бывают разного веса.
Нехватка дескрипторов (EMFILE, ENFILE, ENOBUFS) приходит на всплеске соединений
и проходит сама за миллисекунды, а обрыв соединения между SYN и accept
(ECONNABORTED) вообще штатное дело на нагрузке. Реакция на них была одна: процесс
умирает, и вместе с ним умирает прокси для всех устройств LAN сразу, хотя мешало
одно лишнее соединение. Дальше всё держалось на перезапуске снаружи (procd на
роутере, systemd на VPS), то есть на секундах простоя там, где хватило бы паузы
в сто миллисекунд.

Про xr-client это особенно обидно: на роутере лимит дескрипторов невысокий, а
BitTorrent на одном LAN-устройстве уже приводил к сотням открытых сокетов (см.
комментарий про 845 fd в `handle_connection`).

Эталон обработки в [xr-relay](../../../../xr-relay/src/lib.rs) был, но неполный: там
любая ошибка, включая закрытый под ногами дескриптор, давала `warn` и паузу, то
есть цикл крутился бы вечно, а прок от него нулевой.

## Что сделано

1. **Общий цикл.** Появился [accept.rs](../../../../xr-proto/src/accept.rs) в xr-proto:
   `accept_loop(name, accept, handle)` крутит accept, отдаёт принятые соединения
   обработчику и разбирает ошибки по errno. Проходящая (EMFILE, ENFILE, ENOBUFS,
   ENOMEM, ECONNABORTED, ECONNRESET, EINTR, EAGAIN, EPERM, EPROTO, ETIMEDOUT и
   сетевые ENETDOWN, ENETUNREACH, EHOSTUNREACH) даёт строку `warn` с номером
   ошибки подряд и паузу 100 мс, после чего цикл живёт дальше.
2. **Фатальные не глушим.** Список белый: незнакомый errno считается фатальным, и
   цикл выходит с ошибкой. Закрытый дескриптор (EBADF), не-сокет (ENOTSOCK),
   листенер без listen (EINVAL) сами не починятся, крутить на них цикл значит
   молча притвориться работающим. Второй выход из цикла это сто проходящих
   ошибок подряд: дескрипторы за десять секунд не освободились, значит дело не
   во всплеске, и процесс лучше отдать супервизору. Счётчик сбрасывается любым
   принятым соединением, поэтому редкие EMFILE в течение суток до порога не
   копятся.
3. **Наблюдаемость.** Каждая проходящая ошибка это строка `warn` с именем
   листенера (`server accept failed (3 in a row): Too many open files`), выход
   по фатальной и по исчерпанному терпению это `error`. Молчаливого режима у
   цикла нет: раньше про EMFILE в журнале не было ничего, процесс просто исчезал.
4. **Три вызова.** На общий цикл переведены xr-server (в его случае accept живёт
   в `tokio::select!` с сигналом завершения, поэтому acceptor отдаёт `None` на
   сигнале и цикл штатно кончается `Ok`), xr-client и xr-relay. У relay при этом
   сохранился backpressure: пермит семафора берётся ожиданием прямо в
   обработчике, а цикл его дожидается, поэтому обработчик у `accept_loop`
   асинхронный.
5. **Крах виден снаружи одинаково у всех трёх** (по замечанию ревью). Фатальный
   выход цикла доходит до кода возврата процесса: xr-server пробрасывал его и
   раньше, xr-client теперь отдаёт `Err` из `run()` (правила файрвола к этому
   моменту уже сняты, поэтому падение объявляется в самом конце, а `main` пишет
   `FATAL` в `crash.log` и уходит с кодом 1), xr-relay возвращает результат
   листенера из `main`. Разбор итога задачи прокси в клиенте вынесен в
   `proxy_failure` и покрыт тестами: до правки читался только `JoinError`, а
   `io::Result` из `run_proxy` терялся, и мёртвый листенер выглядел для procd
   штатной остановкой.

Дока: раздел 4.1 `ARCHITECTURE.md` (список модулей xr-proto) описывает разбор
ошибок и оба выхода из цикла.

## Проверка красноты и мутации

Живой прогон на xr-server (шаги 1-4 сценария) на коде main и на коде ветки. На
main сервер умирает первой же нехваткой дескрипторов:

```
opened 31
after burst FAILED: [Errno 61] Connection refused
Error: Os { code: 24, kind: Uncategorized, message: "Too many open files" }
```

На ветке тот же всплеск переживается, и после него сервер отвечает как ни в чём
не бывало:

```
opened 37
after burst: b'HTTP/1.1 200 OK\r\nCon'
WARN server accept failed (1 in a row): Too many open files (os error 24)
```

Юнит-тесты цикла лежат рядом с ним (`xr-proto/src/accept.rs`), прогонка
мутациями, каждая ловится:

| Мутация | Кто краснеет |
|--------|--------------|
| проходящая ошибка выходит из цикла (исходный баг) | `transient_error_keeps_listener_alive` |
| паузы между попытками нет | `transient_error_pauses_before_retry` |
| фатальных нет, всё считается проходящим | `fatal_error_stops_the_loop` |
| ничего не считается проходящим | `transient_error_keeps_listener_alive` |
| счётчик подряд идущих ошибок не сбрасывается на успехе | `accepted_connection_resets_the_streak` |
| граница терпения сдвинута (`>=` -> `>`) | `endless_transient_errors_give_up` |
| мёртвый листенер не считается отказом клиента (замечание ревью) | `dead_listener_is_a_failure` |
| упавшая задача прокси не считается отказом | `panicked_task_is_a_failure` |
| отказом считается и штатная остановка | `clean_stop_is_not_a_failure` |

Код возврата проверен живьём на xr-relay: держим 250 соединений при
`ulimit -n 40`, листенер десять секунд сидит на EMFILE и сдаётся. До правки
процесс уходил с кодом 0 при `ERROR xr-relay listener is dead`, после правки с
кодом 1 и той же строкой. У xr-client тот же путь на маке не воспроизводится
(обработчик закрывает соединения сразу, дескрипторы не кончаются), поэтому его
половина закрыта тестами `proxy_failure`.

## Сценарий проверки

Агентский: шаги 1-4 выполняются с машины агента и итог виден кодом возврата и
строками журнала, шаги 5-6 после выката читают состояние прода, ничего на нём не
меняя.

1. Собрать сервер (`cargo build -p xr-server`) и завести конфиг во временном
   каталоге: `listen = "127.0.0.1"`, `port = 18443`, ключ любой валидный base64,
   `fallback.enabled = true`, `logging.level = "info"`.
2. Запустить его с урезанным лимитом дескрипторов:
   `(ulimit -n 40; ./target/debug/xr-server -c <конфиг> > server.log 2>&1 &)`.
3. Устроить всплеск: открыть из питона до 200 одновременных TCP-соединений на
   127.0.0.1:18443, подержать секунду, закрыть все.
4. Открыть новое соединение и послать в него `GET / HTTP/1.1`. Ожидаемо ответ
   начинается с `HTTP/1.1 200 OK` (фальшивая страница fallback), процесс сервера
   жив, а в `server.log` есть строки `server accept failed (N in a row): Too many
   open files` и нет `Error: Os { code: 24`. На коде до правки этот шаг падает с
   `Connection refused`, процесса уже нет.
5. После выката на VPS: сервис xr-server в состоянии `active`, а в его журнале за
   последние полсотни строк нет `accept failed fatally`.
6. Прокси проверяется по exit-IP, а не по коду ответа: запрос своего адреса через
   туннель отдаёт IP VPS, а не провайдерский.
7. Код возврата на исчерпанном терпении (локально, xr-relay): поднять релей с
   временным конфигом под `ulimit -n 40` и держать к нему 250 соединений
   четырнадцать секунд. Ожидаемо в журнале сто строк `relay accept failed`,
   затем `ERROR xr-relay listener is dead`, а процесс уходит с кодом 1.

### Прогон шагов 1-4 и 7 (локально, до выката)

```
opened 37
after burst: b'HTTP/1.1 200 OK\r\nCon'
строк "accept failed" в журнале: 7
последняя строка журнала: XR Proxy Server stopped

шаг 7: opened 257
       строк "accept failed" в журнале: 100
       ERROR xr-relay listener is dead: Too many open files (os error 24)
       relay exit=1
```

### Прогон шагов 5-6 (прод, после выката)

Оба VPS несут свежие бинари (`xr-server` md5 `5bb5b902`, `xr-relay` md5
`e73f1ea6`), сервисы подняты:

```
=== Timeweb ===            === Aeza ===
active                     active
active                     active
fatal server: 0            fatal server: 0
fatal relay: 0             fatal relay: 0
```

Шаг 6 снят с ноутбука в LAN за роутером DE. Запросы к проксируемым доменам
доходят, и роутер видит их именно как проксируемые, а сервер как свои стримы:

```
google: 204
youtube: 200
xr-client: <ноутбук> -> ... :443 [SNI: www.google.com] => Proxy
xr-client: <ноутбук> -> ... :443 [SNI: www.youtube.com] => Proxy
xr-server: <роутер DE> sid=77 -> www.google.com:443
```

Голого exit-IP тут не снять: на роутере `default_action = "direct"`, и сервисы
отражения адреса под правила пресета не попадают, они честно уходят прямым
путём. Доказательством тракта поэтому служит пара строк выше: решение `Proxy` на
роутере и тот же самый запрос в журнале сервера.

## Ревью

- Фатальный выход accept_loop пробрасывается в код завершения процесса только у xr-server (outcome? в main.rs), а у xr-client и xr-relay гасится: в xr-client main.rs:268 'if let Err(e) = result' проверяет только JoinError, внутренний io::Result из run_proxy не читается; xr-relay main.rs после tracing::error! всё равно возвращает Ok(()). Restart=always в deploy/*.service скрывает разницу для перезапуска, но по коду выхода и systemctl status один и тот же фатальный обрыв листенера выглядит крахом только у сервера, а у клиента и релея как чистая остановка: исправлено
