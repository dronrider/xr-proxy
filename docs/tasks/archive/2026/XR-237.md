# XR-237: Диагностика движка на телефоне никуда не попадает: xr-core и xr-proto пишут через tracing в stdout процесса (Android его выбрасывает), а лента приложения наполняется только из xr_core::journal, моста между ними нет. Любой warn движка (отказ разбора, деградация) для пользователя и для разбора инцидента невидим. iOS: повод (Android глотает stdout) android-специфичен, мост в ленту нужен и на iOS

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 19%, week_max 21%, снимок 15м назад, сдвига нет), 2026-08-11.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 19%, week_max 21%, снимок 27м назад, сдвига нет), 2026-08-11.

## Решение

Мост это слой `tracing_subscriber` в `xr-core`
([journal_bridge.rs](../../../../xr-core/src/journal_bridge.rs)), а не обвязка в JNI:
повод (Android выбрасывает stdout процесса) android-специфичен, а нужда общая,
поэтому iOS-порт получает мост тем же вызовом. Слой кладёт события в тот же
`Journal`, из которого лента приложения читает хвост, так что сообщение движка
попадает в ленту, в файл журнала и в его экспорт разом.

Что проходит в ленту:

- `WARN` и `ERROR` от любого источника. Это события, про которые пользователю
  есть что сказать, и их немного.
- `INFO` только с явно перечисленных target (`with_info_targets`, сравнение по
  префиксу). Список по умолчанию пуст: `info!` в движке стоит на каждом
  выбранном пути соединения, и лента утонет в них за минуту, а по-настоящему
  важное на INFO обвязка и так пишет в журнал напрямую.
- `DEBUG` и `TRACE` не проходят никогда, это developer-логи.

Строка ленты выглядит как `xr_core::session: текст, поле=значение`. Target
остаётся в тексте, потому что тег `[source]` журнала различает только крейт
(`core`, `proto`, всё прочее `trace`), а при разборе инцидента нужно место в
коде точнее.

Шум держат две вещи. Одинаковые подряд записи сворачивает сам журнал счётчиком
повторов, это было и раньше. Цикл повторов с меняющимся текстом свёрткой не ужимается и
вытеснил бы из хвоста всё остальное, поэтому у моста есть потолок 20 записей в
секунду. Придержанное не пропадает молча: в следующем окне мост пишет строку с
их числом.

Рекурсия отсекается флагом потока (`ReentryGuard`), взведённым на всё время
обработки события, включая разбор полей: `Debug` чужого типа тоже может позвать
`warn!`. Вложенное событие через тот же `Dispatch` не прошло бы и без флага, это
делает сам `tracing`, но запись в журнал ходит в файловую систему, и событие
оттуда может прийти другим подписчиком.

Мост видно и когда событий нет: при установке в ленту идёт строка «мост
диагностики движка включён», а `journal_bridge::counters()` отдаёт, сколько
событий доставлено и сколько придержано за жизнь процесса.

Подписчика на Android ставит `nativeJournalInit`, то есть вместе с журналом и до
старта движка, иначе первые предупреждения движка теряются. Слой `fmt` там
остался соседом: на телефоне он бесполезен, но `.so` собирают и гоняют не только
на телефоне. `nativeStart` зовёт ту же инициализацию страховкой, на случай
старта движка без журнала.

## Сценарий проверки

Агентский сценарий, машина не нужна:

1. `cargo test -p xr-core --lib journal_bridge` даёт 11 зелёных тестов: `WARN`
   доходит до журнала с уровнем и полями, `DEBUG` с `INFO` отсеиваются, `INFO`
   проходит с перечисленного target и не проходит с чужого, потолок частоты
   придерживает всплеск и отчитывается о придержанном, флаг рекурсии закрывает
   мост для себя, `announce` отмечается в ленте.
2. Краснота мутацией: заменить в `passes_filter` условие `*level <= Level::WARN`
   на `false` и повторить прогон. Падают 5 тестов из 11, включая
   `warn_reaches_journal`, то есть на коде без моста тесты красные. Мутацию
   вернуть.
3. `cargo test -p xr-android-jni` зелёный: `tracing_bridge_feeds_journal`
   проверяет саму обвязку, то есть что поставленный вместе с журналом
   подписчик доводит `warn!` до ленты и отмечается в ней строкой установки.
4. `cargo test --workspace --exclude xr-client` зелёный, предупреждений нет
   (`xr-client` на маке не собирается, это не про эту правку).
5. `cd xr-android && ./gradlew :app:compileDebugKotlin` собирается: Kotlin не
   менялся, но JNI трогали.

На телефоне мост виден так: после запуска приложения на вкладке Log первой
строкой стоит `INFO [trace] мост диагностики движка включён`, а любое
предупреждение движка (например, отказ разбора правил при живом туннеле)
появляется там же строкой с тегом `[core]` и своим target.

Прогон 2026-08-11 после слияния в main: шаг 1 дал 11 зелёных, шаг 3 дал 29
зелёных, шаг 4 без единого warning, шаг 5 BUILD SUCCESSFUL. Краснота мутацией
(шаг 2) гонялась в ветке исполнителем и ревьювером независимо, 5 падений из 11,
мост с тех пор не менялся.

## Ревью

- xr-core/Cargo.toml: комментарий у tracing-subscriber в [dependencies] говорит, что крейт «переехал из dev-зависимостей в обычные», но строка tracing-subscriber с фичей env-filter в [dev-dependencies] осталась нетронутой (и не используется нигде в xr-core, включая тесты) - переезда не было, крейт просто задублирован с разными наборами фич. Поправить комментарий по факту либо снести неиспользуемую dev-зависимость.: исправлено, dev-зависимость tracing-subscriber снесена, в xr-core её не использует ни один тест (git grep: только journal_bridge, и ему env-filter не нужен); cargo test -p xr-core и cargo test --workspace --exclude xr-client зелёные без warnings
