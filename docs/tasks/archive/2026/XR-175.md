# XR-175. Очередь импортов по URL в приложении

## Мотивация

Пока идёт импорт, второй запустить нельзя: приложение отвечает «Импорт уже
идёт, дождись или отмени его». Диалог при этом открывается и URL принимает,
отказ приходит уже после отправки. Накидать несколько ссылок и уйти не
получается, а это основной сценарий импорта видео.

## Что сейчас

Очередь на стороне агента уже есть: в [import.rs](../../../../xr-share/src/import.rs)
один воркер, одна активная джоба, до четырёх в ожидании, при переполнении 429.
Импорты разных пользователей агент и сейчас складывает в одну очередь.
Ограничение чисто клиентское: [FilesViewModel](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt)
держит ровно одну `ImportJob` в состоянии экрана и второй запуск гейтит.
Комментарий у гейта честный: вторая джоба осиротела бы на агенте, её нельзя
ни отследить, ни отменить. Чинится трекингом списка, а не снятием гейта.

## Что сделать

1. **Список джоб вместо одиночной.** В `FilesViewModel` вместо `importJob`
   список (jobId, шара, прогресс, состояние queued/running), гейт и сообщение
   убрать. Запуск нового импорта просто добавляет строку.
2. **Опрос всех активных.** Один цикл раз в 2 секунды обходит все джобы
   списка: done убирает строку и обновляет листинг, failed показывает текст
   ошибки, потери сети терпятся как сейчас (3 промаха подряд на джобу).
3. **UI.** Строка на джобу с прогрессом и крестиком отмены, как нынешняя
   одиночная. Джоба в состоянии queued подписывается «в очереди», а не висит
   с пустым прогрессом.
4. **429 от агента** (очередь полна) переводить в человеческий текст, а не
   показывать сырую сетевую ошибку.
5. **Глубина очереди агента.** Четыре места на всех пользователей шары может
   оказаться мало, когда импортируют несколько человек сразу. Вынести глубину
   в блок `[import]` конфига агента, дефолт оставить как есть. Единственная
   Rust-часть задачи, едет с тестом; клиентская часть это Android, автотестов
   там нет по правилам проекта.

## Развилки

- **Чужие джобы.** Каждый видит только запущенное им самим; чтобы показать,
  что шару сейчас грузит кто-то ещё, агенту нужен листинг джоб
  (`GET /{id}/import`). В первый заход не берём, при живом спросе отдельная
  задача.
- **Жизнь за пределами экрана.** Джобы живут в состоянии экрана и забываются
  при закрытии шары, на агенте при этом докачиваются до конца. Минимум для
  этой задачи: не терять список при повороте и уходе в другую шару в рамках
  живой ViewModel. Переживание смерти процесса не требуется.

## Тексты UI (согласовать до реализации, урок XR-049)

- подпись очереди у строки джобы: «в очереди»;
- ответ на переполнение очереди агента: «Очередь импорта заполнена, попробуй
  позже».

## Решение

- **Глубина очереди агента.** `ImportConfig.queue_depth` в
  [config.rs](../../../../xr-share/src/config.rs) с прежним дефолтом 4,
  `ImportManager::enqueue` берёт её из живого конфига (без блока `[import]`
  остаётся константа `QUEUE_DEPTH`, там джобы всё равно не принимаются), так
  что горячая перезагрузка конфига меняет глубину на лету. Ключ описан в
  [configs/share.toml](../../../../configs/share.toml), покрыт тестом
  `queue_depth_comes_from_the_config` в
  [import.rs](../../../../xr-share/src/import.rs).
- **Список джоб.** В `FilesViewModel` вместо `importJob` поле
  `importJobs: List<ImportJob>`, у джобы появился признак `queued`. Гейт на
  второй запуск и его сообщение убраны, `startImport` просто дописывает строку.
  Закрытие шары список больше не чистит: опрос ходит за конфигом по `shareId`
  джобы, поэтому уход в соседнюю шару и возврат назад строки не теряют.
- **Опрос всех активных.** Один цикл `ensureImportPolling` раз в 2 секунды
  обходит весь список (`pollImportJob` на джобу): done убирает строку и
  обновляет листинг, failed показывает текст агента, промахи сети считаются по
  каждой джобе отдельно (`importPollFailures`), прежний предел 3 подряд.
  Цикл заводится один и живёт, пока список не опустеет.
- **UI.** В [FilesScreen.kt](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesScreen.kt)
  строка `ImportRow` рисуется на каждую джобу открытой шары, крестик отменяет
  свою (`cancelImport(cfg, jobId)`). Джоба в очереди подписана
  «Импорт: в очереди», работающая показывает проценты.
- **429.** `humanImportError` переехал из `FilesViewModel` в
  [ShareErrorText.kt](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/ShareErrorText.kt)
  к соседней раскладке ошибок и переводит категорию `queue_full` в «Очередь
  импорта заполнена, попробуй позже»; остальные категории по-прежнему
  показывают человеческий хвост из Rust. Это чистая Kotlin-логика, поэтому
  покрыта JVM-юнитом.
- **Снятие шары.** `removeShare` выкидывает её джобы из `importJobs` и счётчики
  промахов рядом с тем, как уже чистил `queue` и `failed`: конфига под такую
  джобу больше нет, опрос по ней ничего не меняет, а строка держала бы цикл
  живым вхолостую.

## Сценарий проверки

Агентская часть:

1. `cargo test -p xr-share import::tests::queue_depth_comes_from_the_config`:
   глубина 1 отбивает вторую джобу, глубина 6 принимает шесть, без конфига
   остаётся прежняя четвёрка. Краснота проверена мутацией (вернуть в `enqueue`
   жёсткую `QUEUE_DEPTH`, тест падает).
2. `cd xr-android && ./gradlew :app:compileDebugKotlin :app:testDebugUnitTest`:
   `ShareErrorTextTest` судит текст переполненной очереди и хвосты остальных
   категорий импорта.

Пользовательский, на проде:

1. Открыть шару с правом импорта, запустить импорт длинного видео.
2. Не дожидаясь конца, запустить ещё два импорта другими ссылками. Ожидаемо:
   отказа «Импорт уже идёт» нет, видны три строки, вторая и третья подписаны
   «в очереди».
3. Отменить крестиком одну из ожидающих: остальные продолжаются как ни в чём
   не бывало.
4. Дождаться конца: два файла появились в листинге без ручного обновления,
   отменённого нет.

Прогон 2026-08-11 после слияния. Агентская часть в main: тест глубины
зелёный, gradle зелёный. Пользовательская часть на эмуляторе со стендом
(локальные хаб и агент шары, инвайт со scope import, приложение из main,
шара добавлена через UI по ссылке инвайта): три импорта без отказа «Импорт
уже идёт», вторая и третья строки подписаны «Импорт: в очереди», отмена
ожидающей не тронула остальные (лог агента: cancelled у снятой, done у двух),
после конца в листинге два файла без ручного обновления, отменённого нет.
Плагин импорта на стенде заглушка с ограниченной скоростью (SSRF-гейт агента
не пускает локальный источник в настоящий качальщик), сама механика очереди,
отмены и опроса боевая.

## Ревью

- removeShare() (FilesViewModel.kt ~434-457) не чистит importJobs удаляемой шары. pollImportJob (~1361) на такой джобе делает store().get(job.shareId) ?: return и молча ничего не меняет, поэтому строка остаётся в importJobs навсегда, а ensureImportPolling, обещающий гаснуть на пустом списке, крутится раз в 2 сек уже вхолостую до конца жизни ViewModel. Раньше removeShare это накрывало неявно: closeShare() сбрасывал importJob при уходе с экрана. Нужно чистить importJobs (и importPollFailures) по shareId в removeShare, как это уже сделано там для queue/failed.: исправлено, removeShare чистит importJobs и importPollFailures по shareId рядом с queue/failed, цикл опроса гаснет на опустевшем списке
