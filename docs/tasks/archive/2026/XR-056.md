# XR-056: компактный общий индикатор очереди синка

Общего индикатора прогресса синка по сути нет, а место он занимает много.

## Проблема

Текущий
[ProgressBar](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesScreen.kt#L468)
это Card во всю ширину про один файл: имя + полоса по байтам текущего файла +
скорость, а агрегат «файл N/M» втиснут мелким текстом.

## Что сделать

Компактный общий индикатор очереди: какой файл синкается сейчас, сколько
осталось (X из N), общий прогресс по батчу, стоп всей очереди. Компактно (одна
строка / тонкая полоса), не карточка на пол-экрана. Данные уже приходят в
`Progress` (`filesDone`/`filesTotal`/`file`, движок отдаёт
`files_done`/`files_total`), нужно агрегатное представление вместо по-файлового.
Детали конкретного файла (байты/скорость) из общего индикатора убрать, они
переезжают на строку файла (XR-044). Виден и для фонового синка, не только
foreground.

Смежно с XR-044 (та же панель/экран, прогресс на строках это предпосылка ужать
глобальный), логично делать в один заход.

Код:
[ui/files/FilesScreen.kt:468](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesScreen.kt#L468),
[ui/files/FilesViewModel.kt:38](../../../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt#L38)

## Решение

Общий индикатор это одна строка над списком: имя файла, который едет сейчас,
счётчик «X из N», кнопка «Стоп» и тонкая полоса по батчу под ними
(`SyncQueueBar` в `FilesScreen.kt`). Стоит он и на списке шар, и в проводнике:
очередь одна на все шары. Байты и скорость в него не вернулись, они уже живут на
строке файла после XR-044, там же и отмена одной строки.

Расчёт вынесен из экрана в чистый `ui/files/SyncProgress.kt` (`syncIndicator`,
без Android SDK) и покрыт JVM-юнитом. Прогресс считается по файлам, как и
просили: агрегатных байт на очередь экрана никто не отдаёт, каждый файл едет
своей передачей, а `bytes_total` снимка это либо один файл, либо весь проход
зеркала. Доля текущего файла всё же добавляется дробной частью к пройденным,
иначе батч из одного файла держал бы полосу в нуле до самого конца; берётся она
только у передачи про один файл и только когда снимок называет именно голову
очереди (зеркало могло держать лок и качать своё). Размер батча это пройденные
плюс оставшиеся: счётчик `queueDone` в состоянии растёт на каждом завершённом
файле и обнуляется, когда новый батч встаёт в пустую очередь, поэтому
отменённая очередь не оставляет после себя вранья.

Отмену от завершения воркер отличает по своему же признаку `cancelled` (натив
вернул `cancelled` либо элемента уже нет в очереди), и на отменённой голове
счётчик не двигается: `queueDoneAfter` в `SyncProgress.kt` растит его только на
докачанном или сорвавшемся файле. Батч от отмены укорачивается ровно так же, как
от крестика на файле, который ещё ждал своей очереди: тот уходит из очереди сам,
мимо воркера. Иначе отменённая на закачке голова считалась бы скачанной, и три
отмены подряд уводили бы подпись к «3 из 3» при пустых руках.

Фоновое зеркало считается по своему снимку (`files_done`/`files_total`).
Не показывался индикатор для него не из-за расчёта, а из-за опроса: цикл
`ensureTransferPolling` крутился, пока открыта шара, занята очередь или идёт
перенос хранилища, а на списке шар нет ни того, ни другого, ни третьего, и
`transfer` оставался пустым. Теперь опрос держится всё время, пока вкладка
«Файлы» на экране: `watchTransfers`/`unwatchTransfers` зовёт `DisposableEffect`
экрана, и флаг `screenOpen` входит в условие цикла.

«Стоп» новой механики не завёл: на своей очереди он гоняет по её элементам ту же
`cancelDownload`, что и крестик на строке (снятие с выбора, изъятие из очереди,
адресная отмена нативной передачи), а на фоновом синке с пустой очередью зовёт
существующую `cancelTransfer`. Перенос хранилища остался при своей карточке со
своим стопом, при нём общий индикатор прячется, чтобы не было двух полос разом.

## Сценарий проверки

Агентская часть: `cd xr-android && ./gradlew :app:compileDebugKotlin
:app:testDebugUnitTest`. Ожидание: сборка без новых предупреждений, двенадцать
тестов `SyncProgressTest` зелёные. Краснота проверена мутациями: если убрать
сверку головы очереди с файлом снимка, падает
`mirrorHoldingTheLockDoesNotLendItsProgressToTheQueue`, а если засчитывать
отменённую голову как скачанную, падают
`aCancelledHeadShortensTheBatchInsteadOfCounting` и
`cancellingHeadsInARowDoesNotFinishTheBatch`.

Пользовательская часть, эмуляторный стенд с локальным агентом шары (такой
собирался для XR-175):

1. Поставить в очередь несколько файлов подряд плюсами на строках. Ожидание: над
   списком одна строка с именем текущего файла и «1 из 3», полоса ползёт, по
   мере готовности счётчик идёт «2 из 3», «3 из 3», карточки во всю ширину нет.
2. Нажать «Стоп». Ожидание: очередь пустеет целиком, индикатор пропадает,
   строки файлов возвращаются к плюсу, недокачанное остаётся на диске и плюс
   докачивает с места.
3. Поставить в очередь три файла и отменить крестиком качающуюся голову, потом
   так же вторую. Ожидание: подпись доходит до «1 из 1» на оставшемся файле, а
   не показывает «3 из 3», хотя скачался только он.
4. Выйти из шары на список шар и оттуда включить синк шары с несколькими
   недостающими файлами (или дождаться фонового прохода). Ожидание: та же строка
   индикатора видна и на списке шар, счётчик идёт по файлам прохода зеркала.
5. Начать перенос папки шары на устройстве. Ожидание: карточка переноса на
   месте, второй полосы над ней нет.

Прогон 2026-08-12 после слияния. Агентская часть в main зелёная (12 тестов
SyncProgressTest, сборка без новых предупреждений). Экранная часть на
эмуляторном стенде с локальным агентом шары (4 файла по 160-240 МБ, скорость
придушена): все пять шагов пройдены дословно - строка «X из N» со «Стоп» и
тонкой полосой без старой карточки, счётчик прошёл 1..3, «Стоп» опустошил
очередь и плюс докачал хвост .xrsync-part с места, отмена двух качающихся
голов довела счётчик до «1 из 1», индикатор виден на списке шар и у фонового
прохода зеркала после перезапуска процесса, при переносе папки карточка
переноса одна без второй полосы. Попутно: у агента нет лога отдачи файлов
(доказательства сняты с устройства), скорость 0 Б/с в чужой карточке переноса
это косметика XR-043.

## Ревью

- queueDone растёт не на каждом уходе файла из очереди, а только через worker'ский путь завершения (FilesViewModel.kt:1182-1189: 'queueDone = if (rest.isEmpty()) 0 else st.queueDone + 1', без учёта cancelled). Прямое удаление из очереди (cancelDownload:1041-1050, removeShare:453-459, removeFolder:905-928, deleteFromShare:984-990) queueDone не трогает вовсе. Итог асимметричный: крестик на файле, который ещё ждёт своей очереди, честно уменьшает total (queueDone+queueSize становится меньше). А крестик на файле, который качается прямо сейчас (голова очереди): cancelDownload сразу убирает его из st.queue, но worker-цикл узнаёт об отмене позже, когда suspend-вызов repo.downloadOne вернётся после нативной отмены, и на этом моменте безусловно инкрементит queueDone, как будто файл докачался. При нескольких таких отмен подряд (голова -> голова -> голова) счётчик 'X из N' начинает показывать почти завершённый батч, хотя реально скачался только последний файл, а предыдущие были отменены. Решение задачи прямо обещает 'queueDone растёт на каждом ушедшем из очереди файле' (docs/tasks/XR-056.md) - код этому не соответствует, только один из путей ухода из очереди инкрементит счётчик. Проверить сценарием: очередь A,B,C, отменить A построчным крестиком, пока он качается (не Стоп по всей очереди), дождаться его нативной отмены, затем то же с B - счётчик должен показать что-то около '3 из 3', хотя ни A, ни B не докачались.: исправлено, Воркер отличает отмену от завершения по своему признаку cancelled и на отменённой голове queueDone не растит: расчёт вынесен в чистую queueDoneAfter (SyncProgress.kt), батч укорачивается симметрично отмене ждущего файла. Тесты aCancelledHeadShortensTheBatchInsteadOfCounting и cancellingHeadsInARowDoesNotFinishTheBatch, краснота проверена мутацией.
