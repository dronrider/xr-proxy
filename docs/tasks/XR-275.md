# XR-275: Ревизия бэклога на переносимость в iOS: пометить андроид-специфичное (per-app туннель XR-016, приём ACTION_SEND XR-231, маскировка иконки XR-154), чтобы эталонный UX не закладывал непереносимое

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 18%, снимок 4м назад, сдвига нет), 2026-08-11.
- Разобран весь Backlog доски (119 строк на момент ревизии, `taskctl list --json`). Из них 39 касаются приложения (UI, Android-интеграция, поведение клиента на телефоне) и получили вердикт; серверные, роутерные и чисто Rust-задачи (xr-server, xr-hub, xr-relay, xr-share-агент, xr-proto/xr-core движок без UI-слоя, протокол v2, Max-носитель, taskctl) в ревизию не включались построчно.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 18%, снимок 11м назад, сдвига нет), 2026-08-11.

## Ревизия

### Непереносимое и частичное (помечаются на доске)

- XR-016: андроид-специфично. Per-app туннель средствами `VpnService`, в Network Extension per-app ограничен по API и возможностям, в прежнем виде не доедет.
- XR-231: андроид-специфично. Приём `ACTION_SEND` это Android intent-система, на iOS аналог это Share Extension, другой механизм регистрации и другой UX выбора приложения-источника.
- XR-154: андроид-специфично. Маскировка через activity-alias это Android API, на iOS доступны только ограниченные alternate icons без произвольной подмены имени.
- XR-078: андроид-специфично. Каналы APK и подписанный манифест это OTA-раздача под Android, на iOS дистрибуция идёт через TestFlight/App Store (стык описывает XR-273), сама механика каналов не переносится.
- XR-072: андроид-специфично. Zero-copy завязан на JNI-байты (`nativePushPacket`/`nativePopPacket`), новому мосту (C FFI/UniFFI, см. XR-272) нужна своя схема без лишних копий.
- XR-171: андроид-специфично. Вся задача это отдельная Android-обёртка по SSH для провижининга роутеров, на iOS нужен свой путь провижининга либо задача остаётся вне порта.
- XR-220: частично. Unwind-граница сделана под ~30 JNI extern-функций, на C FFI/UniFFI мосте нужна своя защита от паники ядра, сама идея (не ронять процесс восстановимой ошибкой) переносится.
- XR-237: частично. Повод (Android глотает stdout процесса) android-специфичен, но мост движковых логов в ленту приложения понадобится и на iOS, с другой реализацией (os_log, Network Extension).
- XR-170: частично. SAF-пикер и обёртка `nativePut` это Android API, на iOS свой picker (UIDocumentPicker) и другой мост, сама заливка файла с устройства в шару переносима.
- XR-185: частично. Пикер папок и его действия в приложении завязаны на Android SAF, на iOS свой picker; манифест директорий, mkdir/move/copy на агенте и зеркало в синке переносимы без изменений.
- XR-223: частично. `nativeStop` это конкретно JNI-функция, но риск заблокировать шатдаун общий для любого моста, на C FFI/UniFFI его придётся закрывать заново.
- XR-085: частично. Инструментарий (dhat/flamegraph/tokio-console) заточен под Android-профилирование, на iOS свой путь через Instruments, а находки по оптимизации ядра переносимы.
- XR-068: частично. Doze-aware это Android power management API, у Network Extension своя модель фона и свои ограничения, адаптивный keepalive и меньше tokio-воркеров в ядре переносятся как есть.
- XR-092: частично. strings.xml и ресурсная система это Android-механизм, на iOS свой формат (Localizable.strings, String Catalog), сама идея вынести строки и завести локали переносится.
- XR-088: частично. `protect()` это API `VpnService` для обхода своего туннеля, у Network Extension обход устроен иначе на уровне системы, а сама проблема (claim под живым VPN) и её UX-решение переносимы.
- XR-222: частично. Jetpack ViewModel и её гибель при смахивании из recents это Android-специфика жизненного цикла, на iOS процесс живёт по другим правилам, идея персистить job_id и переприкрепляться к живой джобе переносится.

### Переносимое (не помечается)

- XR-180: снекбар и горячее применение правила это движок и обобщённый UX-паттерн подтверждения, на iOS тот же способ (toast/alert).
- XR-175: очередь джоб с прогрессом и отменой это список и состояние, ни одного Android API не задействовано.
- XR-190: web-страница у агента платформонезависима, экран истории в приложении это обычный список с диффом.
- XR-058: нижняя навигация и шестерёнка настроек это общий UI-паттерн, в SwiftUI решается тем же способом.
- XR-146: локальная зашифрованная БД сообщений и минимальный UI чата не завязаны на Android API.
- XR-261: инвентаризация настроек и экран за шестерёнкой это дизайн приложения, не платформенный механизм.
- XR-147: кворум-модерация и аудит решений в истории это логика и список, UI общий.
- XR-143: скрытие недоступных вкладок по флагам инвайта это обычная навигация.
- XR-148: перенос истории по QR и зашифрованный blob используют камеру и сеть, доступные на обеих платформах.
- XR-149: FTS-поиск и срезы это данные и список, платформенных API не требует.
- XR-012: индикатор соединения это иконка и текст статуса.
- XR-136: индикатор живости шары и probe при обновлении списка это сетевой запрос и иконка.
- XR-150: треды как ленивая подгрузка ответов, обычный список.
- XR-260: баг в выборе кандидата адреса это логика ShareRepository, не платформенный механизм.
- XR-056: компактный индикатор очереди синка это прогресс-бар и текст.
- XR-090: вкладка Log и доступ к полной истории это список и счётчики.
- XR-153: движок тем оформления это токены и палитра, в SwiftUI ложится тем же набором значений.
- XR-151: политика удаления и эфемерность это таймер и пометка в UI.
- XR-152: избранное с папками и тегами это данные и список.
- XR-163: локальный алиас шары без прав на сервере это чисто клиентское поле.
- XR-101: пометка пропавшей шары по ответу сервера это состояние списка.
- XR-096: различение офлайна телефона и недоступного источника это сетевой статус, не платформенный API.
- XR-020: карточка сервера с выбором источника правил и TOFU-ключом это форма и подпись, Android API не требует.

## Сценарий проверки

Агентский, без переключения на глаз:

1. `grep -c 'iOS: ' docs/TASKS.md` печатает число не меньше 16 (могут добавиться пометки других ревизий).
2. Для каждого ID из раздела «Пометить на доске» проверяется приписка ровно на строке этой задачи, якорь на начало строки таблицы (`^| ID |`), а не подстрокой по всему файлу, иначе матчатся чужие строки: заголовок самой XR-275 упоминает XR-016/XR-231/XR-154 и сам содержит `iOS: `, а строка XR-272 («Смежно с XR-085») даёт ложный `ok` для XR-085. Команда такая:
   `for id in XR-016 XR-231 XR-154 XR-078 XR-072 XR-171 XR-220 XR-237 XR-170 XR-185 XR-223 XR-085 XR-068 XR-092 XR-088 XR-222; do grep -Eq "^\| $id \|.*iOS: " docs/TASKS.md && echo "$id: ok" || echo "$id: MISSING"; done`
   Все 16 строк обязаны напечатать `ok`.
3. Отрицательный контроль проверяет тем же якорем, что ни одна строка из раздела «Переносимое» не получила приписку `iOS:`, команда такая:
   `for id in XR-180 XR-175 XR-190 XR-058 XR-146 XR-261 XR-147 XR-143 XR-148 XR-149 XR-012 XR-136 XR-150 XR-260 XR-056 XR-090 XR-153 XR-151 XR-152 XR-163 XR-101 XR-096 XR-020; do grep -Eq "^\| $id \|.*iOS: " docs/TASKS.md && echo "$id: НЕОЖИДАННАЯ пометка" || true; done`
   Команда не должна ничего напечатать.

## Ревью

- Сценарий проверки, шаг 2, ложноположительный: grep по ID матчит не только строку задачи, а любую строку с этой подстрокой. Строка XR-275 (её собственный заголовок «переносимость в iOS: пометить...(...XR-016...XR-231...XR-154)») уже содержит и ID, и iOS: , поэтому XR-016/XR-231/XR-154 дадут ok независимо от того, поставлена ли настоящая приписка на их строках (104/57/155). Так же XR-272 («Спайк iOS: сборка... Смежно с XR-085») даёт ложный ok для XR-085 (строка 93) через свою строку 117. Проверено: grep -n "XR-085" docs/TASKS.md сейчас матчит и 93, и 117, а 117 уже содержит iOS: . Нужен якорь на начало строки (например ^| $id |), иначе минимум 4 из 16 проверок ничего не гарантируют.: исправлено, якорь на начало строки
