# XR-250: Удалить файл из шары через приложение: действие в проводнике поверх DELETE агента (JNI-обёртка над sync::delete_file), локальная копия и строка манифеста уходят следом. Пункт 5 цели XR-249

Пункт 5 цели [XR-249](XR-249.md). Импорт по URL в проводнике есть, а обратного
действия нет: файл, залитый по ошибке или отсмотренный, убирается только с
машины агента (`xr-share rm`). Держателю write-инвайта с телефона деваться
некуда.

## Что уже готово

- Агент: `DELETE /{id}/file/{*rel}` со скоупом `share:write`, гейтами
  (`404` нет шары, `403` шара не writable или safepath, `401`/`403` токен) и
  оптимистическим `If-Match` (LLD-28, карта в
  [ARCHITECTURE.md](../ARCHITECTURE.md), раздел про запись в шару).
- Ядро: [`sync::delete_file`](../../xr-core/src/sync.rs) поверх
  `direct_then_relay`, проверяет `share:write` в скоупе гранта до сети и
  транслирует ожидаемый хеш в `If-Match`.
- Десктоп: `xr-share rm` ходит тем же путём.

Не хватает двух звеньев: обёртки в [xr-android-jni](../../xr-android-jni/src/lib.rs)
(там сейчас только чтение и импорт: `nativeFetchManifest`, `nativeDownloadFile`,
`nativeSyncShare`, `nativeImport*`) и самого действия в приложении.

## Что делать

1. JNI-функция удаления по образцу `nativeImportUrl`: грант собирается из
   адресов (`importAddrArg`), токена и relay-плеча, `expected_hash` берётся из
   `sha256` строки манифеста. Разбор аргументов и сборка гранта покрываются
   тестами в Rust, как у соседних обёрток.
2. `external fun` в [NativeBridge](../../xr-android/app/src/main/java/com/xrproxy/app/jni/NativeBridge.kt)
   и вызов в [FilesViewModel](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt):
   после успеха убирается локальная копия (механика `removeLocal` уже есть) и
   перезапрашивается манифест, чтобы строка ушла из списка сразу, а не после
   ручного обновления.
3. Показывать действие только когда в скоупе токена есть `share:write` (образец
   это `canImport` в [Share.kt](../../xr-android/app/src/main/java/com/xrproxy/app/model/Share.kt)),
   и спрашивать подтверждение: удаление необратимо и видно всем держателям
   шары.
4. Отказы агента доезжают текстом через `humanError`, а не сырой строкой:
   `403` нет права записи, `404` файла уже нет, `412` файл на агенте изменился.

Главный риск это путаница двух удалений. Минус в строке файла уже занят
удалением локальной копии, и второе действие рядом обязано отличаться словами и
подтверждением, иначе повторяется история XR-044, где одна кнопка несла два
смысла.

Дока: раздел про запись в шару в [ARCHITECTURE.md](../ARCHITECTURE.md)
перечисляет потребителей `delete_file`, приложение туда добавляется той же
веткой.

## Сценарий проверки

Агентский, на эмуляторе (AVD `xr-test`, снапшот `xr-ready`, приёмы в памяти
проекта). Адрес шары и инвайт берутся из `local-docs`.

1. Собрать и поставить APK, открыть шару с write-грантом.
2. Импортом по URL или заливкой с агента положить в шару файл-жертву, обновить
   список: строка видна.
3. Долгим нажатием по строке открыть карточку файла, нажать «Удалить из шары»,
   в подтверждении нажать «Удалить». Ожидание: тост «Файл удалён из шары»,
   строка исчезает из списка без ручного обновления, локальной копии на
   устройстве нет.
4. Снять манифест шары мимо приложения (`curl` к агенту с токеном либо
   `xr-share pull`): файла нет и на агенте.
5. Негатив: в шаре без `share:write` в карточке файла кнопки «Удалить из шары»
   нет вовсе.

## Ход работы

- Исполнение: субагент opus/high по вердикту pick (квота: week_all 11%, снимок 19м назад, сдвига нет), 2026-08-04.
- JNI-обёртка `nativeDeleteFile` поверх `sync::delete_file`: грант собирается
  тем же `grant_from_parts`, что у импорта, хеш строки манифеста уходит в
  `If-Match`. Пустое имя файла и пустой хеш разбираются до сети
  (`check_delete_path`, `optional_hash`), на них и на сборку гранта есть тесты в
  `xr-android-jni`; типовые мутации (перепутанный порядок кандидатов, снятая
  проверка на пустой ввод, пустой возврат) проверены прогоном, каждая краснит
  тест.
- Место действия в UI: карточка файла по долгому нажатию, а не вторая кнопка в
  строке. Минус в строке уже снимает локальную копию, и две похожие кнопки бок
  о бок повторили бы путаницу XR-044; карточка показывает «Удалить из шары»
  только при `share:write` в скоупе токена (`ShareConfig.canWrite`) и просит
  подтверждение отдельным диалогом.
- По успеху приложение снимает файл с закачки, убирает локальную копию, выкидывает
  строку из списка и перезапрашивает манифест (заодно перезаписывается кэш
  листинга, иначе удалённый файл вернулся бы при офлайн-заходе). Отказы агента
  переведены на человеческий в `humanDeleteError`: `not_found`, `http_403`,
  `http_412`, `no_write_scope`.
- Тесты: `cargo test --workspace --exclude xr-client` зелёный (596 тестов, ноль
  warnings), APK собран локально (`xr-android/build.sh`, BUILD SUCCESSFUL).
  Экранный сценарий на эмуляторе не гонялся, он остаётся на проверку после
  выката.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 11%, снимок 33м назад, сдвига нет), 2026-08-04.

## Ревью

- deleteFromShare (FilesViewModel.kt) вызывает maybeCancelNative и сразу repo.deleteLocal, не дожидаясь ухода нативного райтера: nativeCancelTransfer лишь просит остановиться «на следующем чанке» (комментарий в lib.rs), а removeFolder рядом в этом же файле именно поэтому вставляет awaitWriterLeft между отменой и удалением локальных копий. Карточка файла с долгим нажатием доступна и для строки, что качается прямо сейчас (isHead или фоновый bgFetch), поэтому сценарий реален: пользователь жмёт «Удалить из шары» по файлу в процессе закачки, агент подтверждает удаление, репо чистит путь и .part раньше, чем писатель успел отреагировать на отмену, писатель дописывает и переименовывает файл уже после чистки, и на диске остаётся осиротевшая копия удалённого из шары файла (withLocalOnly потом покажет её строкой при следующем обновлении списка, хотя файла в шаре больше нет).
