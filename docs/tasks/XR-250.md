# XR-250: Удалить файл из шары через приложение: действие в проводнике поверх DELETE агента (JNI-обёртка над sync::delete_file), локальная копия и строка манифеста уходят следом. Пункт 5 цели XR-249

Пункт 5 цели [XR-249](XR-249.md). Импорт по URL в проводнике есть, а обратного
действия нет: файл, залитый по ошибке или отсмотренный, убирается только с
машины агента (`xr-share rm`). Держателю write-инвайта с телефона деваться
некуда.

## Что уже готово

- Агент: `DELETE /{id}/file/{*rel}` со скоупом `share:write`, гейтами
  (`404` нет шары, `403` шара не writable или safepath, `401`/`403` токен) и
  оптимистическим `If-Match` (LLD-28, карта в
  [ARCHITECTURE.md](../ARCHITECTURE.md), раздел про запись в шару).
- Ядро: [`sync::delete_file`](../../xr-core/src/sync.rs) поверх
  `direct_then_relay`, проверяет `share:write` в скоупе гранта до сети и
  транслирует ожидаемый хеш в `If-Match`.
- Десктоп: `xr-share rm` ходит тем же путём.

Не хватает двух звеньев: обёртки в [xr-android-jni](../../xr-android-jni/src/lib.rs)
(там сейчас только чтение и импорт: `nativeFetchManifest`, `nativeDownloadFile`,
`nativeSyncShare`, `nativeImport*`) и самого действия в приложении.

## Что делать

1. JNI-функция удаления по образцу `nativeImportUrl`: грант собирается из
   адресов (`importAddrArg`), токена и relay-плеча, `expected_hash` берётся из
   `sha256` строки манифеста. Разбор аргументов и сборка гранта покрываются
   тестами в Rust, как у соседних обёрток.
2. `external fun` в [NativeBridge](../../xr-android/app/src/main/java/com/xrproxy/app/jni/NativeBridge.kt)
   и вызов в [FilesViewModel](../../xr-android/app/src/main/java/com/xrproxy/app/ui/files/FilesViewModel.kt):
   после успеха убирается локальная копия (механика `removeLocal` уже есть) и
   перезапрашивается манифест, чтобы строка ушла из списка сразу, а не после
   ручного обновления.
3. Показывать действие только когда в скоупе токена есть `share:write` (образец
   это `canImport` в [Share.kt](../../xr-android/app/src/main/java/com/xrproxy/app/model/Share.kt)),
   и спрашивать подтверждение: удаление необратимо и видно всем держателям
   шары.
4. Отказы агента доезжают текстом через `humanError`, а не сырой строкой:
   `403` нет права записи, `404` файла уже нет, `412` файл на агенте изменился.

Главный риск это путаница двух удалений. Минус в строке файла уже занят
удалением локальной копии, и второе действие рядом обязано отличаться словами и
подтверждением, иначе повторяется история XR-044, где одна кнопка несла два
смысла.

Дока: раздел про запись в шару в [ARCHITECTURE.md](../ARCHITECTURE.md)
перечисляет потребителей `delete_file`, приложение туда добавляется той же
веткой.

## Сценарий проверки

Агентский, на эмуляторе (AVD `xr-test`, снапшот `xr-ready`, приёмы в памяти
проекта). Адрес шары и инвайт берутся из `local-docs`.

1. Собрать и поставить APK, открыть шару с write-грантом.
2. Импортом по URL или заливкой с агента положить в шару файл-жертву, обновить
   список: строка видна.
3. Удалить файл действием проводника, подтвердить. Ожидание: строка исчезает из
   списка без ручного обновления, локальной копии на устройстве нет.
4. Снять манифест шары мимо приложения (`curl` к агенту с токеном либо
   `xr-share pull`): файла нет и на агенте.
5. Негатив: в шаре без `share:write` действие удаления не показывается.
