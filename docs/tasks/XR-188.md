# XR-188: Реализация LLD-33 фаза 1 (агент): опт-ин share --git, репозиторий вне рабочей папки с updateInstead, авто-коммит по watcher'у, smart HTTP спавном git, подписанный HEAD с long-poll; проверяется штатным git-клиентом

## Что происходит

Синк шары строго однонаправленный, зеркало агент -> устройство, а запись это
явные PUT и DELETE с If-Match. Локальная правка в папке потребителя наверх не
едет и затирается зеркалом. При отказе 412 нечем мириться, кроме ручного
переноса правок. Совместного редактирования текстовых шар нет вовсе, и дизайн
его согласован в [LLD-33](../lld/33-share-git-sync.md) с настоящим git как
движком синка. Реализация режется на три фазы, эта первая, агентская. Без неё
фазам 2-3 нечем кормиться.

## Чего хотим

Опт-ин git-контур у агента по LLD-33 п. 2.1-2.4 и 2.6.

- Флаг `share --git` допустим только вместе с `--writable` и только для
  директории. При включении проверяется git в PATH и создаётся репозиторий
  `<state_dir>/git/<share_id>` с `core.worktree` на папку шары, рабочая папка
  остаётся чистой.
- Авто-коммит watcher'ом с debounce и страховочным сканом. Служебный
  неймспейс `.xr-*` и файлы сверх колпака `git_max_file_mb` (default 10) в
  историю не попадают, но манифестом раздаются как раньше.
- Smart HTTP спавном `upload-pack`/`receive-pack --stateless-rpc`. Гейты по
  LLD-33 п. 2.3, весь транспорт включая fetch живёт под `share:write`.
- Подписанный HEAD (`git_head_signing_bytes` в xr-proto, домен
  `xr-share-git-head`) с long-poll поверх `tokio::sync::watch`.

Харнесс `xr-share sync` и web-морда это фазы 2-3 (XR-189, XR-190), сюда не
входят.

## Ревью

- major: pre-receive-хук режет и самый первый пуш в шару, пустовавшую на момент включения git. На unborn main проверка чистоты звенит сама о себя: git diff-index --cached HEAD без коммитов выходит с 128 (fatal: bad revision HEAD), восклицание даёт true, и пуш отклоняется с лживым текстом про незафиксированные правки. Проверил живьём репро с хуками из gitrepo.rs: пустая папка при share --git, клон у коллеги проходит, первый пуш падает с pre-receive hook declined; окно закрывается, только когда владелец положит в папку первый файл и авто-коммит его заберёт. Жду: хук не судит о чистоте, пока HEAD не резолвится (выход раньше проверки), и тест на путь пустая папка при opt-in и первый пуш от клиента проходит
- major: pre-receive прикрывает только грязь по отслеженным файлам, а post-receive своим read-tree -u --reset молча затирает untracked-файлы владельца на путях, приехавших в пуше. Репро: у владельца свежий untracked e.txt с черновиком, коллега пушит коммит с тем же путём, хук пускает (diff-files untracked не видит), после материализации в папке лежит версия коллеги, черновик пропал. updateInstead, чью семантику хуки заменяют, ровно этот случай отказывает. Окно шире двухсекундного дебаунса: файлы сверх колпака и пути .xr-* исключены из истории навсегда и стоят в зоне поражения постоянно, а при молчащем watcher (сетевая ФС) untracked копятся до пятиминутного скана. Жду: pre-receive отказывает, когда пути пуша пересекаются с untracked и ignored файлами рабочей папки, и тест на такую коллизию
- minor: настройки git-контура застывают на старте агента. GitManager::new зовётся один раз в main, перечитывание конфига зовёт только rebuild с картой, а ветка reconfigured в rebuild сравнивает old.settings с self.settings, которые после старта уже не меняются: правка git_author или git_max_file_mb в конфиге на живом агенте молча не применяется, хотя комментарий в rebuild обещает рестарт цикла по смене настроек. Жду: свежие GitSettings едут в rebuild вместе с картой и смена настроек перезапускает контур, либо в README и конфиге прямо сказано, что эти ручки требуют рестарта
- minor: два решения из раздела Решения не прикрыты тестами. Сериализация пуша с авто-коммитом: снятие op_lock из receive-ветки git_rpc ни один тест не замечает, я проверил мутацией, воркспейс зелёный; детерминистский вариант есть: удержать op_lock в тесте, послать receive-pack и убедиться, что до отпускания лока спавна git не было. receive.maxInputSize: тест проверяет лишь наличие настройки в config репозитория, но не формулу восемь колпаков плюс 64 МиБ в байтах и сам факт отказа на слишком большом pack. Жду: по одному тесту на сериализацию и на значение потолка в байтах
