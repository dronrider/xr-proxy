# XR-188: Реализация LLD-33 фаза 1 (агент): опт-ин share --git, репозиторий вне рабочей папки с updateInstead, авто-коммит по watcher'у, smart HTTP спавном git, подписанный HEAD с long-poll; проверяется штатным git-клиентом

## Что происходит

Синк шары строго однонаправленный, зеркало агент -> устройство, а запись это
явные PUT и DELETE с If-Match. Локальная правка в папке потребителя наверх не
едет и затирается зеркалом. При отказе 412 нечем мириться, кроме ручного
переноса правок. Совместного редактирования текстовых шар нет вовсе, и дизайн
его согласован в [LLD-33](../lld/33-share-git-sync.md) с настоящим git как
движком синка. Реализация режется на три фазы, эта первая, агентская. Без неё
фазам 2-3 нечем кормиться.

## Чего хотим

Опт-ин git-контур у агента по LLD-33 п. 2.1-2.4 и 2.6.

- Флаг `share --git` допустим только вместе с `--writable` и только для
  директории. При включении проверяется git в PATH и создаётся репозиторий
  `<state_dir>/git/<share_id>` с `core.worktree` на папку шары, рабочая папка
  остаётся чистой.
- Авто-коммит watcher'ом с debounce и страховочным сканом. Служебный
  неймспейс `.xr-*` и файлы сверх колпака `git_max_file_mb` (default 10) в
  историю не попадают, но манифестом раздаются как раньше.
- Smart HTTP спавном `upload-pack`/`receive-pack --stateless-rpc`. Гейты по
  LLD-33 п. 2.3, весь транспорт включая fetch живёт под `share:write`.
- Подписанный HEAD (`git_head_signing_bytes` в xr-proto, домен
  `xr-share-git-head`) с long-poll поверх `tokio::sync::watch`.

Харнесс `xr-share sync` и web-морда это фазы 2-3 (XR-189, XR-190), сюда не
входят.

## Решения (развилки закрывал сам, пользователя рядом не было)

- `updateInstead` не работает с bare-style топологией. `receive-pack` с
  путём-аргументом резолвит worktree своих детей в сам `GIT_DIR`, и
  `diff-files` всегда видит «изменения» в сервисных файлах репозитория,
  отказывая каждому пушу. Вместо конфиг-переключателя стоят
  `receive.denyCurrentBranch = ignore` и receive-hook'и: `pre-receive` режет
  пуш в грязную папку, `post-receive` материализует `main` через
  `read-tree -u --reset HEAD`. Семантика та же, что обещал LLD, поведение
  проверено вручную на живом стенде до перевода в тесты.
- Заменяя `updateInstead`, `pre-receive` обязан повторять его семантику
  целиком. Первая половина: первый пуш в шару,
  пустовавшую при `share --git`, проходит, unborn main не считается грязью,
  сравнивать не с чем. Вторая: пуш поверх локального файла вне истории
  отклоняется, материализация не имеет права молча затирать черновик
  владельца, которого авто-коммит ещё не забрал. Существование файла
  проверяется сравнением двух списков имён от git: дерево пуша (`ls-tree`) и
  локальные файлы вне истории (`ls-files --others`), оба с quotepath=false.
  Имя с кавычкой или control-символом git печатает C-цитированием даже с
  quotepath=false, но с обеих сторон одинаково, поэтому строки сравниваются
  буквально. cwd хука это `GIT_DIR`, шелловский `test -e` смотрел бы мимо
  рабочей папки. Оба случая нашло ревью, оба закрыты тестами и шагом стенда.
- `git_author` и `git_max_file_mb` перечитываются hot-reload конфига.
  Настройки едут параметром `rebuild`, неизменённые шары сохраняют живой
  экземпляр и канал HEAD, изменившаяся настройка перезапускает контур и
  доезжает до репозитория (колпак пуша пересчитан) без рестарта агента.
- Единица `receive.maxInputSize` это байты. Голое «144» означало 144 байта
  и резало любой pack. Значение собирается из `git_max_file_mb`
  как `8x кап + 64` МиБ.
- Push сериализуется с циклом авто-коммита через `op_lock` шары
  (`OwnedMutexGuard` в финализаторе rpc), иначе материализация и авто-коммит
  могли бы гоняться за папку.
