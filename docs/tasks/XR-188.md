# XR-188: Реализация LLD-33 фаза 1 (агент): опт-ин share --git, репозиторий вне рабочей папки с updateInstead, авто-коммит по watcher'у, smart HTTP спавном git, подписанный HEAD с long-poll; проверяется штатным git-клиентом

## Что происходит

Синк шары строго однонаправленный, зеркало агент -> устройство, а запись это
явные PUT и DELETE с If-Match. Локальная правка в папке потребителя наверх не
едет и затирается зеркалом. При отказе 412 нечем мириться, кроме ручного
переноса правок. Совместного редактирования текстовых шар нет вовсе, и дизайн
его согласован в [LLD-33](../lld/33-share-git-sync.md) с настоящим git как
движком синка. Реализация режется на три фазы, эта первая, агентская. Без неё
фазам 2-3 нечем кормиться.

## Чего хотим

Опт-ин git-контур у агента по LLD-33 п. 2.1-2.4 и 2.6.

- Флаг `share --git` допустим только вместе с `--writable` и только для
  директории. При включении проверяется git в PATH и создаётся репозиторий
  `<state_dir>/git/<share_id>` с `core.worktree` на папку шары, рабочая папка
  остаётся чистой.
- Авто-коммит watcher'ом с debounce и страховочным сканом. Служебный
  неймспейс `.xr-*` и файлы сверх колпака `git_max_file_mb` (default 10) в
  историю не попадают, но манифестом раздаются как раньше.
- Smart HTTP спавном `upload-pack`/`receive-pack --stateless-rpc`. Гейты по
  LLD-33 п. 2.3, весь транспорт включая fetch живёт под `share:write`.
- Подписанный HEAD (`git_head_signing_bytes` в xr-proto, домен
  `xr-share-git-head`) с long-poll поверх `tokio::sync::watch`.

Харнесс `xr-share sync` и web-морда это фазы 2-3 (XR-189, XR-190), сюда не
входят.
