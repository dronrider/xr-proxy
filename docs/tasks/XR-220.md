# XR-220: Укрепить границу JNI против паник ядра: ни одна из ~30 extern-функций не защищена, паника в xr-core через block_on аборт-ит весь процесс с живым VpnService. Перевести android-либу на unwind и обернуть входные точки catch_unwind, чтобы восстановимая ошибка ядра не роняла приложение. iOS: unwind-граница под JNI, на новом мосте нужна своя защита от паники

## Что происходит

Разведка основного чекаута 2026-09-01. В корневом Cargo.toml воркспейса
`[profile.release]` стоит `panic = "abort"`, и он наследуется cdylib
xr-android-jni, из которой собрана libxr_proxy.so приложения. Любая паника
в xr-core или в самом мосте вызывает abort процесса, а в этом же процессе
живёт VpnService. Туннель умирает вместе с приложением, Android показывает
«приложение остановилось», и пользователь запускает VPN заново. Ближайший
горячий путь это onboarding-функции с одноразовым рантаймом. Паника футера
проходит через `rt.block_on` в `with_onboarding_runtime` и попадает в
extern-функцию напрямую.

Второй корень это xr-android-jni/src/lib.rs. Все 43 входные точки
объявлены голыми `pub extern "system" fn` без catch_unwind. Ловить панику
обязана сама обёртка до возврата в JNI. Раскрутка наружу extern-функции по
правилам нынешнего rustc кончается abort, даже если вся сборка стоит на
unwind.

## Чего хотим

Восстановимая ошибка ядра не роняет приложение. Паника в любой из входных
точек JNI ловится до возврата в Java. В журнал приложения пишется запись,
ответом служит значение, которое Kotlin читает по конвенции этой функции.
Android-релиз собирается с раскруткой стека, а сервер, клиент,
хаб и релей остаются на abort. Новая входная точка не может появиться мимо
защиты.

## Границы

Моста под iOS в репозитории нет: xr-ios-ffi спроектирован спайком LLD-39 и
не реализован, защищать пока нечего. Требование зафиксировано в
docs/ARCHITECTURE.md, раздел 4.5. Каждой входной точке C FFI будущего
моста нужна такая же граница.

Внутренние локи xr-core (движок, sync, import) на poison-восстановление не
переводились. Их консистентность это работа ядра, а не моста. На стороне
моста переведены локи ENGINE и HEALTH, которые держит сам мост.

Kotlin-сторона не менялась. Запасные ответы легли в существующие конвенции
чтения, проверенные по коду XrVpnService и NativeBridge.

## Развилки

Профиль unwind. Общий release переводить на unwind нельзя, сервер и клиент
хотят abort и платят размером. Переопределение `panic` для отдельного
пакета cargo отвергает на этапе манифеста («`panic` may not be specified in
a `package` profile»), да и не помогло бы. Паника рождается и в
зависимостях, раскрутка нужна всему дереву либы. Выбран отдельный профиль
`android-release`, наследующий release с `panic = "unwind"`. На него
переведены xr-android/build.sh и gradle-таска buildRustRelease.

Форма обёртки. Ручная обёртка каждой функции оставила бы 43 места, куда
новая функция встаёт без защиты незамеченной. Выбран макрос `jni_entry!`
в guard.rs, который объявляет входную точку целиком, вместе с
`#[no_mangle]` и перехватом паники. Голая extern-функция в lib.rs стала
ненужной, и тест инварианта это требует. Прогнать инвариант через regcheck в выносном
integration-тесте не вышло без потерь: rlib рядом с cdylib ради линковки
тест-бинаря ослаблял LTO и растил libxr_proxy.so с 4,1 до 5,1 МБ. Поэтому
crate-type остался cdylib-only, а тест живёт в guard.rs.

Место перехвата. Глобальный panic::set_hook не останавливает раскрутку и
extern-границу не прикрывает. Ловит catch_unwind в каждой точке, что и
реализовано.

Запасные ответы. Они свои у каждой сигнатуры, по конвенции, которую Kotlin
уже читает. JSON-функции отвечают `{"error":".."}`, nativeStart сообщением
об ошибке запуска, потому что null для него означает успех. nativeGetState
отвечает строкой `Error:`, по которой XrVpnService гасит сессию (XR-279).
nativeClassifyPattern отдаёт свой `kind=invalid`, потому что голый `{error}`
UI не опознаёт. Nullable-функции nativeNormalizeSsid и nativePopPacket отдают
null, булевы отвечают false.

## DoD

- Паника в теле любой входной точки JNI не покидает libxr_proxy.so. Java
  получает запасной ответ по конвенции сигнатуры, в журнале приложения
  появляется запись ERROR [jni] с именем функции и текстом паники.
- Паника футера под rt.block_on ловится той же границей.
- Ни одна входная точка не объявлена мимо макроса jni_entry!, инвариант
  проверяет тест покрытия.
- Android-релиз собирается с раскруткой, сервер, клиент, хаб и релей
  остаются на abort.
- Граница описана в docs/ARCHITECTURE.md, раздел 4.5.

## Сценарий проверки

1. Дифференциал panic-стратегии на слитом main. Сборка ядра под android
   профилем либы не передаёт флаг паники, rustc собирает с unwind по
   умолчанию; тот же вызов с обычным release передаёт `-C panic=abort`
   каждому крейту:

   ```
   touch xr-core/src/lib.rs
   ANDROID_NDK_HOME=$HOME/android-tools/sdk/ndk/27.0.12077973 \
     cargo build -p xr-core --target aarch64-linux-android \
     --profile android-release -v 2>&1 | grep -oE '\-C panic=\S+' | sort | uniq -c
   ```

   Ожидание: пустой вывод. Тот же вызов с `--release` вместо
   `--profile android-release` обязан выдать счётчик вида `46 -C
   panic=abort`, это доказывает, что abort остался у остальных целей.

2. Сборка нативной либы через build.sh после слияния, с копированием в
   jniLibs:

   ```
   ANDROID_NDK_HOME=$HOME/android-tools/sdk/ndk/27.0.12077973 cargo ndk \
     -t aarch64-linux-android -o /tmp/xr-jni \
     build -p xr-android-jni --profile android-release
   ```

   Ожидание: строка `Finished \`android-release\` profile` и файл
   /tmp/xr-jni/arm64-v8a/libxr_proxy.so. Это доказывает, что cargo-ndk 4.x
   подхватывает отдельный профиль и раскладывает артефакт так же, как
   прежде с --release.
