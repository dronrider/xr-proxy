# XR-180: Мои правила не действуют на живом туннеле до переподнятия: применять добавленное правило сразу (движок пересобирает merged-роутер при фетче пресета, механика есть), снекбар-обещание убрать. Смежно с XR-174, найдено на проверке XR-118

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 18%, week_max 20%, снимок 10м назад, сдвига нет), 2026-08-11.

## Корень

Правила пользователя доезжали до движка только вместе с конфигом старта:
`VpnViewModel.buildConfigJson` кладёт их массивом `user_rules`, а
`XrVpnService.withFreshUserRules` подменяет массив на каждом поднятии из кэша
(XR-118). Живой туннель не поднимается, поэтому правка списка до него не
доходила совсем, и экран правил честно обещал снекбаром «Правила сохранены.
Применятся при следующем подключении» (`RulesScreen.applyRules`).

При этом механика применения на лету в движке была: активный роутер лежит в
`SessionContext.router` как `RwLock<Arc<Router>>`, и фоновый watch пресета
(LLD-37) на каждой новой версии пересобирает `Router::from_merged(локальные
правила, пресет)` и подменяет `Arc`. Не хватало только второго повода
пересборки и моста к нему из Kotlin.

## Решение

Тот же путь, что у пресета, а не второй параллельный:

- `xr-core/src/engine.rs`: пересборка и подмена роутера вынесены в
  `swap_router` (плюс `build_router` на «пресет есть / пресета нет»), и через
  неё ходят оба повода. Новый `VpnEngine::apply_user_rules(routing)` собирает
  merged-роутер из нового списка и дискового кэша пресета (в сеть не ходит) и
  подменяет `Arc` под write-локом. Живые сессии продолжают со своим `Action`,
  новые решения принимаются по свежим правилам.
- Локальная половина merged-роутера переехала в общее владение
  (`live_overrides: Arc<RwLock<RoutingConfig>>`). Без этого watch пресета
  держал снятую на старте копию, и первая же публикация с хаба откатила бы
  применённое на лету правило.
- `xr-android-jni`: `nativeApplyUserRules(rulesJson, defaultAction)` разбирает
  тот же массив `user_rules`, что уезжает в конфиг старта, через
  `xr_proto::user_rule::to_routing_config` и зовёт движок. Возвращает `false`
  на незапущенном движке (правила уедут ближайшим Connect) и пишет строку в
  журнал приложения, чтобы применение было видно на вкладке Log.
- Kotlin: `VpnViewModel.saveUserRules` после записи файла дёргает мост,
  обещающий снекбар из `RulesScreen.applyRules` убран. Действие по умолчанию
  перестало быть двумя литералами: `DEFAULT_ROUTING_ACTION` один на конфиг
  старта и на применение на лету.

Смена пресета (пикер) снекбар про следующее подключение сохраняет: пресет
живёт в профиле сервера, а профиль без полного реконнекта не переключить.

## Сценарий проверки

Агентская часть, гоняется из корня рабочего дерева:

1. `cargo test --workspace --exclude xr-client` проходит целиком, в том числе
   три теста `xr-core/src/engine.rs`:
   - `user_rule_applies_to_the_live_tunnel`: на запущенном движке добавленное
     правило меняет вердикт роутера сразу, снятое возвращает прямой маршрут;
   - `live_user_rule_overrides_the_cached_preset`: своё правило перебивает
     пресет из дискового кэша, остальные правила пресета остаются;
   - `preset_update_keeps_the_live_user_rule`: пересборка по публикации с
     хаба не откатывает применённое правило.
2. `cargo test --workspace --exclude xr-client 2>&1 | grep "warning:" | grep -v "generated"`
   не печатает ничего.
3. `cd xr-android && ./gradlew :app:compileDebugKotlin :app:testDebugUnitTest`
   проходит.
4. Краснота теста бага на старом поведении: убрать запись нового списка в
   `live_overrides` внутри `apply_user_rules` и прогнать
   `cargo test -p xr-core engine::tests`. Падают все три теста, после чего
   запись вернуть.

Пользовательская часть (эмулятор либо телефон, без него не проверить):
подключить туннель, открыть 2ip.ru и запомнить IP, на экране правил добавить
`*.2ip.ru -> proxy`, снекбара-обещания не появляется, обновить страницу без
переподключения: показан exit-IP VPS. Удалить правило, обновить страницу:
снова реальный IP.
