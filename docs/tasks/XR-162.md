# XR-162: xr-share share того же пути плодит дубль шары вместо обновления записи (заявленная семантика «повторный share без флага выключает» требует дедупа по пути). Найдено на проверке XR-141

  коммиты `fix(share)` и `docs(share)` с ID в subject.
- Ревью: субагент sonnet/high по вердикту pick, 2026-08-02.

## Разбор корня

`share` в [cli.rs](../../xr-share/src/cli.rs) регистрировал путь на хабе и клал
результат в конфиг безусловным `cfg.shares.push(...)`. Список шар агента это
просто вектор, ключа в нём нет, поэтому второй `xr-share share /srv/photos`
заводил вторую запись на ту же папку: новый `share_id` на хабе, ещё один
`[[share]]` в конфиге, две строки в `xr-share list` и две карточки у
потребителя.

Дубль ломает не только опрятность индекса. На нём разъезжается заявленная
семантика флагов записи: README обещает «re-running `share` without the flag
turns write back off», а LLD-28 п. 9 расписывает механику (обычный attach с
`write = false` снимает привязку из `write_share_ids`); LLD-29 п. 2.3 повторяет
то же про `--import`. Держится это на том, что повторный `share` попадает в ту
же запись. Со вторым `share_id` привязка снималась у новой шары, а прежняя, уже
писабельная, оставалась на хабе и в конфиге агента: право записи никуда не
девалось, хотя команда отработала успешно. Найдено на живой проверке XR-141.

## Что сделано

Повторный `share` того же пути обновляет прежнюю запись. Вместо `push` список
проходит через `upsert_share`: запись с тем же путём заменяется целиком (флаги
последнего запуска побеждают), запись нового пути дописывается как раньше.
Вытесненный `share_id` возвращается наверх, и `share` снимает его с индекса хаба
тем же `hub_unshare`, что и `unshare`, best-effort с внятной строкой при отказе
(хаб лежит, запись остаётся, её видно). Отдельной ручки обновления у хаба нет,
поэтому путь получает свежий `share_id`; ссылка, напечатанная прежним `share`
того же пути, перестаёт работать, и это записано в README.

Пути сравниваются канонизированными, как их разрешает сам агент (`safepath`
канонизирует корень шары через `canonicalize`), поэтому хвостовой слеш, симлинк
и ручная правка конфига ведут в ту же запись. Путь, который уже не
канонизируется (папку унесли), сравнивается как записан: иначе две пропавшие
шары схлопнулись бы в одну.

Наблюдаемость: итоговая строка теперь говорит «Шара обновлена», а не «Шара
добавлена», и рядом печатается, что прежняя запись снята с хаба (или почему не
снялась).

Дока: в [xr-share/README.md](../../xr-share/README.md) рядом с обещанием про
`--writable` описано, что повторная шара пути заменяет запись, что флаги
последнего запуска побеждают и что старая ссылка на этот путь умирает.

## Проверка красноты и мутации

Регрессионный тест `cli::tests::share_same_path_updates_its_entry` гоняет
настоящий `share()` против хаба-заглушки на живом TCP (по образцу `FakeHub` из
`xr-core/src/onboarding.rs`): первый прогон с `--writable`, второй без него по
тому же пути. Ожидается одна запись со свежим `share_id`, снятый `writable` и
запрос `share/unshare` со старым id; третьим шагом другой путь заводит вторую
шару, чтобы дедуп не съедал соседей. Соседний
`share_dedups_through_symlinked_path` держит нормализацию: конфиг с путём через
симлинк и `share` настоящего пути это одна шара.

```
$ regcheck --base main --inline xr-share/src/cli.rs -- cargo test -p xr-share
тест краснеет на main и проходит на текущем коде, регрессия закрыта (тесты: xr-share/src/cli.rs)
```

Краснота на main настоящая, не несобираемость: тесты зовут только то, что в
базе уже есть (`share`, `ShareArgs`, `read_config`), база собирается, и прогон
падает на `assertion failed: повторный share того же пути не должен плодить
дубль, left: 2, right: 1`. Проверено отдельно ручной сборкой базы с перенесённым
тестовым регионом.

Мутации по правке, каждая гонялась отдельно с восстановлением файла:

| Мутация | Кто краснеет |
|--------|--------------|
| M1: `push` вместо замены (возврат исходной поломки) | `share_same_path_updates_its_entry`, `share_dedups_through_symlinked_path` |
| M2: пути сравниваются строкой, без `canonicalize` | `share_dedups_through_symlinked_path` |
| M3: вытесненный `share_id` не возвращается наверх | оба теста |
| M4: прежняя запись не снимается с хаба | оба теста |
| M5: новая запись наследует `writable` прежней | `share_same_path_updates_its_entry` |

Полный прогон `cargo test --workspace --exclude xr-client` зелёный, warning'ов
нет (`xr-client` на маке не собирается; `xr-hub` требует собранного
`admin-ui/dist`).

## Сценарий проверки

Агентский, целиком локальный: `xr-share` гоняется на машине агента, хаб для
шагов 2-4 не нужен (заглушка в тестах), для шага 5 нужен живой хаб.

1. Воспроизведение поломки. Вернуть в `xr-share/src/cli.rs` безусловное
   добавление:

   ```sh
   python3 - <<'EOF'
   p='xr-share/src/cli.rs'; s=open(p).read()
   s=s.replace("    match shares.iter().position(|s| same_path(&s.path, &entry.path)) {",
               "    match None::<usize> {")
   open(p,'w').write(s)
   EOF
   cargo test -p xr-share -- --exact cli::tests::share_same_path_updates_its_entry
   ```

   Тест обязан упасть на «повторный share того же пути не должен плодить дубль»
   (две записи вместо одной). Вернуть файл: `git checkout xr-share/src/cli.rs`.

2. Зелёный прогон крейта: `cargo test -p xr-share`.

3. Полный прогон и warning'и:

   ```sh
   cargo test --workspace --exclude xr-client
   cargo test --workspace --exclude xr-client 2>&1 | grep "warning:" | grep -v generated
   ```

4. Справка команды: `cargo run -p xr-share -- share --help` печатает описание
   `--writable` про выключение записи повторным `share` без флага, оно теперь
   правдиво.

5. На живом хабе (после выката): дважды шарить одну папку, первый раз с
   `--writable`, второй без него.

   ```sh
   xr-share share /srv/photos --writable
   xr-share share /srv/photos
   xr-share list
   ```

   Ожидаемо: второй запуск печатает «Шара обновлена» и строку про снятую с хаба
   прежнюю запись, `list` показывает одну строку на папку, в админке хаба тоже
   одна запись, и держатель инвайта видит одну шару без права записи.

## Ревью

- upsert_share снимает старую запись с хаба через hub_unshare, но это заодно отвязывает путь от инвайта, на котором висел старый share_id: resolve_invites берёт explicit --invite вместо cfg.default_invite, и если второй запуск share не повторяет тот же --invite (а default_invite не задан), новая запись ни к одному инвайту не привязывается. До фикса держатель такого инвайта хотя бы читал файл через непотревоженную старую запись (баг был только в том, что запись оставалась и писабельной), теперь же он молча теряет доступ к пути целиком, вывод команды об этом не предупреждает. Сценарий не покрыт тестами: в share_same_path_updates_its_entry и share_dedups_through_symlinked_path invites пустой и default_invite не задан, attach вообще не вызывается, поэтому проверить нечем. Нужно либо явно задокументировать это как принятый риск (README плюс строка в разборе корня), либо добавить тест на эту связку и решить, переносить ли привязку к прежним инвайтам на новую запись
