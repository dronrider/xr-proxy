# XR-259: Онбординг по ссылке не проходит на локальном стенде: parse_invite_link требует https и режет приватные адреса

## Разбор корня

[parse_invite_link](../../xr-proto/src/invite_url.rs) на верхнем уровне принимал
только буквальную схему `https` (иначе `UnsupportedScheme`) и дальше отсекал
приватные/loopback хосты (`PrivateOrLoopbackHost`) независимо от схемы. Оба
запрета осмысленные для боевой ссылки (LLD-04, раздел 3.1: TOFU держится на
доверенном CA, а отказ от приватных хостов страхует от случайного приёма
чьего-то LAN-хаба за production), но у них общая слепая зона - локальный
стенд. `xr-hub` без установленного `nginx`/TLS слушает голым http на LAN-адресе
(`docs/HUB-DEPLOY.md`: "хаб слушает 127.0.0.1:8080, наружу его выводит nginx с
сертификатом") или доступен с эмулятора/устройства через `adb reverse` под
`localhost`. Ссылка с такого стенда это всегда `http://<private-host>/invite/<token>`,
и она падала на самом первом шаге, ещё до сетевого запроса: `http` не входил
в верхний `match` вовсе, до проверки хоста дело не доходило (иначе упала бы
следом на `PrivateOrLoopbackHost`).

## Что сделано

`http://` теперь тоже принимается, но только вместе с приватным/loopback
хостом или `localhost` (для `adb reverse`); публичный хост по http
по-прежнему `HttpRequiresPrivateHost` - решение это не отмена проверки, а
явный разрешённый случай рядом со старой. `https` на публичный хост ведёт
себя как раньше без изменений, `https` на приватный/loopback хост тоже
по-прежнему `PrivateOrLoopbackHost` (это не путь локального стенда, у
приватного IP нет доверенного CA-сертификата, а самоподписанный TOFU в
LLD-04 не предусмотрен). `hub_url` в результирующем `InviteLink` собирается
с реальной схемой из ссылки (`http://` или `https://`), а не захардкожен на
`https://`, иначе последующие запросы `xr-core::onboarding` (обычный
`reqwest` без принудительного TLS) стучались бы по TLS туда, где сервер
говорит только plain HTTP, и падали бы уже на сетевом шаге.

`xr-android-jni` и `xr-hub` зовут `parse_invite_link` без изменений сигнатуры
(JSON-форма `{"kind":"https",...}` не меняется, Kotlin читает только
`hub_url`/`token`, на `kind` не переключается) - фикс целиком внутри
`xr-proto`.

Дока: `docs/lld/04-onboarding-qr-uri.md` (раздел 3.1, отступление от исходного
дизайна) и `docs/ARCHITECTURE.md` (раздел 4.1, описание `invite_url.rs`).

## Проверка красноты и мутации

Регрессия закрыта тестами `accepts_http_on_private_host` и `accepts_http_on_private_host_with_port`.
На старом коде (верхний `match` без ветки `"http"`) оба падают:

```
called `Result::unwrap()` on an `Err` value: UnsupportedScheme
test result: FAILED. 0 passed; 2 failed
```

На исправленном - зелёные вместе с остальными 28 тестами `invite_url`
(`cargo test -p xr-proto --lib invite_url::`).

Мутации по правке:

| Мутация | Кто краснеет |
|---|---|
| Убрать ветку `"http"` из верхнего `match` (возврат исходной поломки) | `accepts_http_on_private_host`, `accepts_http_on_private_host_with_port` |
| Убрать проверку `scheme == "http" && !private` | `rejects_http_on_public_host` |
| Убрать проверку `scheme == "https" && private` | `rejects_loopback_host`, `rejects_private_host`, `rejects_https_on_localhost` |
| Убрать ветку `localhost` в `is_private_or_loopback` | `accepts_http_on_private_host` (кейс `localhost`), `rejects_https_on_localhost` |
| Захардкодить `hub_url` на `https://` вместо `{scheme}://` | `accepts_http_on_private_host`, `accepts_http_on_private_host_with_port` (сравнение строки `hub_url`) |

`cargo test --workspace --exclude xr-client` зелёный (все наборы, включая
`xr-hub`, `xr-android-jni`, `xr-setup`), grep по `warning:` пуст.

## Сценарий проверки

Агентский, парсинг - чистая функция, реальное устройство и сеть в этой задаче
не участвуют:

```
cargo test -p xr-proto --lib invite_url::tests::accepts_http_on_private_host
```

Тест перебирает `127.0.0.1`, алиас host-машины в Android-эмуляторе, обычный
LAN-адрес и `localhost` - все виды хостов локального стенда. На верхнем
`match` без ветки `"http"` (буквальный откат к прежнему поведению) тест падает
на `UnsupportedScheme` - именно тем сообщением, которое означало «онбординг не
проходит» на стенде; после отката файла обратно тест снова зелёный вместе с
остальными 28 тестами `invite_url`.
