# XR-034: Агент анонсирует приватный LAN-адрес (`192.168.x`), шара недоступна вне домашней сети. При `xr-share share` предупреждать про приватный addr; задокументировать проброс `8443` + публичный IP/DDNS. Полноценный доступ без белого IP это XR-035

## Что происходит

`xr-share share` регистрирует шару адресом, который хаб видит у запроса. Запуск с хоста агента за домашним роутером даёт белый IP провайдера, но порт 8443 на машину агента никто не пробросил. Запуск с другой машины той же сети даёт хабу приватный адрес вроде `192.168.1.10`. В обоих случаях получатель вне домашней сети получает таймаут, а в выводе команды всё выглядит штатно. Наблюдение с первых установок агента у знакомых, весна 2026.

Предупреждение о приватном адресе появилось коммитом b43e320e, но с дырами. Оно печатается и при `via_relay`, когда шара снаружи достижима через relay хаба. В этом случае предупреждение ошибочно. Классификация ловит RFC 1918, loopback и link-local у v4, а CGNAT `100.64.0.0/10` пропускает. У v6 ловит только `::1` и `::`, мимо идут ULA `fc00::/7` и `fe80::`. Текст зашит в `eprintln!`, тестов на него нет. Проброс порта и DDNS описаны только в LLD-19, раздел 2.5. В README агента раздела про доступ снаружи нет.

## Чего хотим

Предупреждение печатается только при приватном адресе без relay, когда шара снаружи и вправду недоступна. Классификация закрывает CGNAT, ULA и `fe80::`. Текст собирает отдельная функция, которую проверяет тест. Вывод `share` называет включённый relay отдельной строкой. В `xr-share/README.md` появляется раздел про доступ снаружи: relay, проброс 8443, `--addr` с публичным IP или DDNS, чем грозит CGNAT.

## Границы

Доступ без белого IP это relay, он сделан в XR-035 и здесь не трогается. Хаб и подстановка адреса по source IP запроса не меняются. Проверка живого проброса с внешней сети остаётся за пользователем, из автотеста её не сделать.

## Ревью

Уровень 2 до 8e25407: неопределённость 2, критичных путей не тронуто: правка вывода xr-share share и раздел README

- [возврат: реализация, 2026-09-05] блокирует: xr-share/src/cli.rs:290 и 592, via_relay считается по cfg.relay.is_some(), про фичу сборки он не знает. Фича relay не входит в default (xr-share/Cargo.toml: default = ["sync"]), а install --token кладёт [relay] в конфиг всегда (cli.rs:216-223). Агент, собранный дефолтом, получает via_relay = true, uplink при этом не поднимается (main.rs:327-336 пишет в лог warn), шара снаружи недоступна, а share вместо предупреждения печатает 'relay: включён (снаружи шара достижима через хаб)'. До правки предупреждение в этом случае было, то есть это регрессия ровно в сценарии задачи. README сам про фичу пишет ('The binary has to be built with --features relay'), код её не проверяет. Чем проверить: cargo build -p xr-share без --features relay, конфиг с [relay], xr-share share на приватном адресе, предупреждение обязано печататься. Правка меняет ожидание теста private_addr_warning_silent_via_relay (дефолтный прогон идёт без фичи), поэтому её должен сделать автор
- [возврат: реализация, 2026-09-05] не блокирует: тем же корнем xr-share/src/cli.rs:343-344 шлёт хабу via_relay = true в сборке без фичи relay, и потребитель уходит пробовать мёртвый relay-путь. Строка вне диффа, но правка замечания 1 закрывает её тем же условием, если считать признак один раз рядом с resolve_via_relay
- [возврат: реализация, 2026-09-05] не блокирует: addr_is_private (xr-share/src/cli.rs:566) не разворачивает IPv4-mapped IPv6, и адрес вида `::ffff:` с приватным v4-хвостом, переданный через --addr, проходит как публичный. Лечится строкой: у V6 сначала ip.to_ipv4_mapped() и рекурсия в ветку V4. Хаб такой адрес не подставит (client_ip берёт x-real-ip от nginx), так что случай только ручной
- [возврат: правила, 2026-09-05] не блокирует: xr-share/README.md, раздел Reaching a share from outside, пункт 1 говорит 'share prints a relay: включён line when the leg is on' и 'It does not fire when the share goes through the relay'. Строка печатается по наличию дескриптора в конфиге, а не по поднятому uplink. После правки замечания 1 текст станет правдой, но проверить его стоит вместе с ней
