# XR-189: Реализация LLD-33 фаза 2 (харнесс): xr-share sync на libgit2 за фичей sync, авто-коммит и fetch/merge/push, конфликт-копии при пересечении строк, relay-мост с pinned identity-TLS, колпак размера. Зависит от фазы 1

## Что происходит

Фаза 1 (XR-188) дала агентскую половину git-контура: репозиторий вне рабочей
папки, авто-коммит по watcher'у, smart HTTP и подписанный HEAD с long-poll.
Соавтору от этого пока мало толку. Работать с шарой он может только штатным
git-клиентом руками: клонировать, помнить про fetch, самому решать конфликты
и самому повторять push, если кто-то успел раньше. Обещанного в
[LLD-33](../lld/33-share-git-sync.md) сценария «оба правят в своих редакторах,
синк и разрешение конфликтов происходят сами» нет, и без второй половины
контура он не появится. Фаза 3 (XR-190, web и приложение) стоит за этой.

## Чего хотим

Харнесс `xr-share sync` по LLD-33 п. 2.5 целиком, за cargo-фичей `sync`
(по умолчанию включена, `--no-default-features` оставляет агента без libgit2).

- Команда `xr-share sync --invite <t> --share <id|имя> <папка> [--name]
  [--once]`. Пустая или несуществующая папка клонируется. Непустая посторонняя
  даёт отказ с названной причиной. Грант без `share:write` отбивается до сети.
- Цикл симметричен агентскому. Watcher с дебаунсом и страховочным сканом
  коммитит локальные правки, long-poll HEAD поднимает fetch, merge и push.
  Отвергнутый push это сигнал повторить. Колпак `git_max_file_mb`
  и неймспейс `.xr-*` те же, что у агента.
- Merge через git2 диффом по строкам. Непересекающиеся правки сливаются сами.
  Пересечение кладёт встречную версию рядом конфликт-копией с автором и
  коротким SHA в имени, оба варианта входят в один merge-коммит.
- Транспорт перебирает адреса как `pull` и `push`, LAN раньше публичного,
  relay последним. На relay-пути loopback-мост несёт байты identity-TLS-стримом
  с пиннингом на ключ агента. Сам libgit2 остаётся без TLS-бэкендов вовсе.

## Ревью

Уровень 3 до 4521b2b: неопределённость 2 из вердикта pick плюс два да триажа: правка это сам DoD-путь (харнесс sync целиком) и трогает доступы/секреты (Basic auth, share:write гейты, identity-TLS pinning) -> третий уровень

- не блокирует: xr-share/src/sync_cmd.rs:471 (commit_local) харнесс всегда использует константу GIT_MAX_FILE_MB (10 МБ) для колпака, не читает настроенный владельцем git_max_file_mb (xr-share/src/config.rs:70, effective_git_max_file_mb). InviteShareDto (pull.rs) этот параметр не передаёт вовсе. При нестандартном колпаке агента (не 10 МБ) харнесс либо закоммитит то, что владелец явно исключает из истории (cap меньше дефолта), либо наоборот отсечёт то, что владелец разрешает (cap больше дефолта). README (xr-share/README.md, раздел «Co-editing a share») формулирует безусловно: «The size cap ... are the same as on the agent» - при кастомном cap это не так. Тесты (test_sync_size_cap) проверяют только дефолтный cap, разъезд не покрыт. Стоит либо прокинуть эффективный cap в грант/DTO, либо явно задокументировать ограничение (харнесс всегда берёт общий дефолт, а не настройку конкретного агента): исправлено, выбран путь документирования из двух предложенных: README и ARCHITECTURE.md прямо говорят, что харнесс берёт общий дефолт GIT_MAX_FILE_MB, настройка агента ему не видна и грант её не несёт (докой подтверждено 555c29c2)
- решение: прокинуть эффективный колпак через грант нельзя. LLD-33 п. 2.1 держит хаб и минтинг нетронутыми, новых полей у ShareRecord и грантов нет. Ограничение записано честно. README агента и ARCHITECTURE говорят, что харнесс берёт общий дефолт GIT_MAX_FILE_MB. Сдвинувший колпак владелец расходится с соавторами на файлах между двумя значениями. Безусловная формулировка про одинаковый колпак из README убрана.: исправлено, ответ автора на замечание 1, подтверждён диффом 555c29c2
- на заметку: xr-share/src/sync_cmd.rs:resolve_conflicts берёт путь конфликта только с нашей стороны (c.our, иначе c.their/c.ancestor), и по этому же пути кладёт и локальную, и встречную (конфликт-копию) версии. Если конфликт возник из-за rename на встречной стороне (their.path != our.path), встречный блоб уедет под нашим именем, а не под тем, что выбрал автор с той стороны - имя переименования потеряется. LLD-33 сознательно ограничивает дизайн текстовым line-level merge и не разбирает renames отдельно, тестов на этот случай нет. Не блокирует DoD, годится в задачу долга при следующей находке на renames: отклонено, принято ограничением дизайна (LLD-33 line-level merge, rename вне рамки), задача долга не заводится, повод появится по первой живой находке
- решение: принято ограничением. Дизайн LLD-33 line-level, rename-детект вне его рамки. Задачу долга на гипотезу заводить не стал, поводом станет первая живая находка: исправлено, ответ автора на замечание 3, принят
- Вердикт: без замечаний. круг 2 до 555c29c2: сверил доки с диффом 4521b2b..555c29c2 (docs/ARCHITECTURE.md, xr-share/README.md, docs/tasks/XR-189.md) - код sync_cmd.rs не менялся. Замечание 1 (колпак): fixed, безусловная формулировка про совпадение колпака убрана, ограничение честно названо в обеих доках. Замечание 3 (rename в конфликт-копиях): rejected по причине, дизайн-скоуп LLD-33 подтверждён
