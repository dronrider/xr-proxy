# XR-242: фрагментированный ClientHello теряет SNI, соединение уходит в direct

## Симптом

Сайт из списка проксируемых открывается через раз или не открывается вовсе, а в
логе xr-client то же соединение видно как `[SNI: -] => Direct`. Провайдерский
фильтр гасит такой прямой заход, и наружу это выглядит как «зависла вкладка»:
ошибки в туннеле нет, потому что туннель тут вообще не участвовал.

Найдено попутно при разборе XR-241, там записано отдельной строкой в разделе
«Что проверено по пути»: у Signal SNI снимался штатно, поэтому к той задаче
фрагментированный ClientHello не относился.

## Разбор корня (что известно)

Имя снимается ровно с одной порции первых байт клиента, и если ClientHello
пришёл разбитым на несколько TCP-сегментов, разбор видит только первый кусок.
`extract_sni` на обрезанном буфере молча возвращает `None`
([sni.rs](../../xr-proto/src/sni.rs)), дальше `resolve(None, ip)` отдаёт
`default_action`, а в референсных конфигах это `direct`
([configs/routing-russia.toml](../../configs/routing-russia.toml)).

Мест, где снимается имя, два, и лечить надо оба:

- Роутерный клиент: один `client.peek(&mut peek_buf)` на 4 КБ
  ([proxy.rs:137](../../xr-client/src/proxy.rs#L137)). `peek` байты не съедает,
  поэтому дочитать недостающее тут ничего не ломает.
- Ядро (Android): `peek_sni_from_rx` берёт одно сообщение из `data_rx` с
  таймаутом 500 мс ([session.rs:184](../../xr-core/src/session.rs#L184)).
  Прочитанное обязано доехать до релея дословно, для этого уже есть
  `initial_data`.

Почему всплыло сейчас. Браузеры включили постквантовый обмен ключами
(`X25519MLKEM768`), от него key_share распухает больше чем на килобайт, и
ClientHello перестал помещаться в один сегмент. Раньше он в MSS укладывался
почти всегда, поэтому одного чтения хватало.

Через то же чтение проходит ветка про non-80/443 порты
([proxy.rs:168](../../xr-client/src/proxy.rs#L168)): решение «похоже на TLS»
снимается с первого байта, фрагментация ему не мешает, но правку по этому месту
провести всё равно надо.

## Рамки

- Дочитывать до полного ClientHello, а не до фиксированного размера буфера:
  длина рекорда известна из его заголовка, и по ней видно, сколько ещё ждать.
- Клиент, который молчит или шлёт не TLS, платить за ожидание не должен: без
  верхней границы по времени и по объёму прокси превращается в способ подвесить
  соединение.
- Поведение при так и не собравшемся имени остаётся прежним (решение по IP), но
  бесшумным быть перестаёт: сейчас про недособранный ClientHello в логе нет
  ничего, кроме прочерка в поле SNI.

## Что сделано

1. **Длину рекорда видно из заголовка.** В [sni.rs](../../xr-proto/src/sni.rs)
   появился `client_hello_record_len`: по первому байту он отличает handshake от
   всего остального, а по полю длины говорит, сколько байт должно набраться
   всего. Не-TLS даёт `None`, то есть ждать нечего, а объявленная длина
   обрезается по `MAX_CLIENT_HELLO` (предел TLSPlaintext, 16389 байт), иначе
   соврамший заголовок заставил бы ждать байты, которых клиент не пришлёт.
2. **Роутерный клиент досматривает первые байты.** `peek_client_hello` в
   [proxy.rs](../../xr-client/src/proxy.rs) повторяет `peek`, пока рекорд не
   соберётся целиком, растит буфер под объявленную длину и держит два предела:
   полсекунды на хвост и тот же `MAX_CLIENT_HELLO` по объёму. `peek` байты не
   съедает, поэтому релей потом читает их сам, и ни одна из веток дальше по
   коду не поменялась. Ждать приходится по часам с шагом 5 мс: сокет остаётся
   читаемым, пока первые байты в нём лежат, и `peek` возвращается сразу тем же
   куском.
3. **Ядро склеивает сообщения.** `peek_sni_from_rx` в
   [session.rs](../../xr-core/src/session.rs) берёт из `data_rx` не одно
   сообщение, а столько, сколько нужно на рекорд, и всё прочитанное дословно
   уезжает в `initial_data`, как и раньше. На хвост даётся столько же времени,
   сколько на первые байты, и не-TLS выходит из цикла сразу, поэтому сырые
   протоколы за ожидание не платят.
4. **Недособранный рекорд перестал быть бесшумным.** Оба места пишут в `warn`
   строку вида `SNI: ClientHello не собрался, 1400 байт из 6081, маршрут по IP`.
   Решение при этом прежнее, по IP.

Дока: раздел 3 `ARCHITECTURE.md` (модуль `sni.rs`) описывает дочитывание рекорда,
оба предела ожидания и запись в лог.

## Проверка красноты и мутации

Регрессия закрыта тестом ядра `peek_sni_gathers_fragmented_client_hello`:
ClientHello приезжает в канал двумя сообщениями, имя лежит во втором. Правка и
тест в одном файле, отсюда `--inline`:

```
$ regcheck --base main --inline xr-core/src/session.rs -- \
    cargo test -p xr-core peek_sni_gathers_fragmented
тест краснеет на main и проходит на текущем коде, регрессия закрыта (тесты: xr-core/src/session.rs)
```

На старом коде тест видит ровно исходный симптом, имени нет:

```
assertion `left == right` failed
  left: None
 right: Some("chat.signal.org")
```

По роутерному клиенту regcheck не применим: на main нет `peek_client_hello`, и
тест туда не переносится (сборка упала бы, а это ложная краснота). Проверено
руками, возвратом старого поведения (один `peek`, дочитывания нет) при
сохранённой сигнатуре:

```
test proxy::tests::peek_gathers_fragmented_client_hello ... FAILED
assertion `left == right` failed
  left: 1400
 right: 6081
```

Мутации по правке, каждая гонялась отдельным прогоном:

| Мутация | Кто краснеет |
|--------|--------------|
| заголовок рекорда считается четырёхбайтным | `test_record_len_from_header`, `test_sni_needs_full_record` |
| граница набранного заголовка сдвинута на байт | `test_record_len_capped` |
| снята проверка на handshake (ждём хвост у любого протокола) | `test_record_len_from_header` |
| снят предел `MAX_CLIENT_HELLO` | `test_record_len_capped` |
| длина рекорда всегда неизвестна (`None` на любом вводе) | `test_record_len_from_header`, `test_sni_needs_full_record`, `test_record_len_capped` |
| хвост не приклеивается к буферу в ядре | `peek_sni_gathers_fragmented_client_hello` |
| ядро берёт только первое сообщение (исходный баг) | `peek_sni_gathers_fragmented_client_hello` |
| клиент возвращает первую порцию (исходный баг) | `peek_gathers_fragmented_client_hello`, `peek_does_not_consume_bytes` |
| не-handshake тоже ждёт хвоста | `peek_does_not_wait_for_non_tls` |
| буфер не растёт под объявленную длину | все три клиентских теста с крупным рекордом |
| предел ожидания снят | `peek_gives_up_on_missing_tail` |

Одна мутация не ловится и не должна: если первое пустое сообщение из канала
принять за данные, ядро отдаёт тот же пустой буфер и то же `None`, наблюдаемое
поведение не меняется.

Полный прогон на маке: `cargo test --workspace --exclude xr-hub` зелёный
(475 тестов), warning'ов нет. xr-hub на маке требует собранного `admin-ui/dist`
и падает на любой ветке, к правке отношения не имеет. xr-client тут собирается и
тесты его гоняются.

## Сценарий проверки

Шаги 1 и 2 выполняются с машины агента без выката, шаги 3 и 4 после него.

1. Воспроизвести исходный баг: `regcheck --base main --inline
   xr-core/src/session.rs -- cargo test -p xr-core peek_sni_gathers_fragmented`.
   Утилита обязана сказать, что тест краснеет на main и проходит на ветке.
2. Прогнать разбор и оба места съёма: `cargo test -p xr-proto sni`,
   `cargo test -p xr-core peek_sni`, `cargo test -p xr-client peek`. Всё зелёное,
   в клиентских тестах ClientHello едет двумя сегментами через настоящий сокет.
3. После выката xr-client на роутер открыть с LAN-машины проксируемый сайт
   браузером, который просит постквантовый обмен ключами (Chrome шлёт
   `X25519MLKEM768` по умолчанию), и посмотреть `logread -e xr-proxy`: строка по
   этому соединению обязана быть `[SNI: <домен>] => Proxy`, а не
   `[SNI: -] => Direct`. Заодно сверить exit-IP: сайт должен видеть адрес VPS.
4. Android: собрать и поставить APK, открыть в нём тот же сайт и убедиться, что
   в журнале движка есть `через прокси: <домен>:443`. Прочерк вместо домена там
   и был признаком потерянного имени.
