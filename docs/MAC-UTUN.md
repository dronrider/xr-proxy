# Сервис macOS на прямом utun (xr-macos)

Фоновый VPN-сервис для Mac. Весь трафик системы уходит в туннель xr-proxy
через собственный интерфейс utun, сервис работает демоном launchd. Network
Extension не используется, платный аккаунт Apple Developer не нужен. Движок
общий с приложением и роутером (xr-core), с той же обфускацией, правилами
маршрутизации профиля и срезом QUIC (XR-300).

Дальше инструкция для владельца машины, от установки до удаления. Устройство
сервиса описано в [ARCHITECTURE.md](ARCHITECTURE.md), раздел 4.12.

## Быстрый старт

Нужен Mac с установленным Rust (rustup) и чекаутом проекта. Сервис правит
маршруты, DNS и файрвол, на это нужны права администратора: команды
управления идут через sudo, а установочный скрипт поднимает права сам и
только на шаге установки. Сборка идёт от вашего пользователя: тулчейн
rustup стоит в вашем HOME, и сборка под sudo его не находит.

```bash
# 1. Сборка и установка. Профиль это тот же JSON, что получает приложение
#    Android по QR или с хаба. Права администратора скрипт попросит сам
#    на шаге установки.
scripts/install-macos-svc.sh ~/Downloads/profile.json

# 2. Проверить, что поднялось.
sudo /usr/local/bin/xr-macos status
```

Строка `итог: работает` значит, что демон жив, туннель поднялся и kill-switch
взведён. Теперь заблокированный сайт открывается в браузере как обычный,
QUIC срезан и страница уходит по TCP через туннель.

Установка раскладывает файлы по местам.

- Бинарь сервиса лежит в `/usr/local/bin/xr-macos`.
- Плист launchd стоит в `/Library/LaunchDaemons/dev.xr.macos.svc.plist`.
- Профиль читается из `/etc/xr-proxy/profile.json` с правами 0600, внутри
  ключ обфускации.
- Конфиг обвязки читается из `/etc/xr-proxy/macos.toml`, образец это
  `configs/macos.toml`.
- Рабочее состояние (снимок DNS, список маршрутов, ссылка PF, кэш адресов
  серверов, статус) живёт в `/var/db/xr-proxy/macos/`.
- Журнал демона пишется в `/var/log/xr-macos.log`.

## Управление

```bash
sudo /usr/local/bin/xr-macos status    # состояние с вердиктом и причиной
sudo /usr/local/bin/xr-macos stop      # остановить, сеть вернётся как была
sudo /usr/local/bin/xr-macos start     # запустить снова
sudo /usr/local/bin/xr-macos validate  # проверить конфиг и профиль без старта
```

Сервис стартует при загрузке машины сам (RunAtLoad) и перезапускается после
падения (KeepAlive). Сон и пробуждение, смена Wi-Fi на кабель и обратно
обслуживаются сторожем.

Конфиг редактируется в `/etc/xr-proxy/macos.toml`, изменения подхватываются
после `stop` и `start`. Новый профиль кладётся той же командой `install`.
Старый при этом заменяется, сеть откатывается и поднимается заново.

## Диагностика

Первый инструмент это `status`. Он сводит launchd, статус демона, живой
интерфейс туннеля и правила PF, а последней строкой печатает вердикт. Если
вердикт называет проблему, причина напечатана тут же, она же лежит в
`/var/db/xr-proxy/macos/status.json` и повторяется в журнале.

Типовые картины.

- Вердикт «работает». Всё в порядке.
- Причина про чужой VPN. На машине поднят ещё один VPN, и сервис не
  стартует одновременно с ним. Маршруты и kill-switch конфликтуют.
  Отключите чужой VPN, сервис подхватится сам за десятки секунд.
- Причина про профиль. Файл не читается, в нём нет сервера или ключа.
  Проверьте профиль и переложите его командой `install`.
- Состояние Error. Движок не смог соединиться с сервером, причина приходит
  из движка (таймаут, отказ). Kill-switch при этом остаётся взведённым,
  прямого выхода в интернет нет, сеть стоит, пока сервер не ответит или
  сервис не остановить руками. Так задумано, утечка мимо туннеля страшнее
  паузы.
- Вердикт «сервис не установлен или не запущен». Плиста нет или launchd его
  не загрузил, смотрите журнал.

Журнал демона целиком лежит в `/var/log/xr-macos.log`. Свои адреса и ключи
демон в журнал не пишет.

## Восстановление после аварии

Если демон убит, а правки сети остались и весь интернет «пропал», сеть
возвращается одной командой.

```bash
sudo /usr/local/bin/xr-macos recover
```

Команда снимает маршруты сервиса, возвращает DNS всех сетевых сервисов из
сохранённого снимка и разбирает правила kill-switch. Повторный вызов
безопасен, живой демон не нужен. Если и это не помогло, пройдите те же
шаги руками.

```bash
sudo pfctl -a com.apple/xr.svc -F all        # снести анкор kill-switch
sudo networksetup -setdnsservers Wi-Fi Empty # вернуть DNS от DHCP (каждый сервис)
sudo route -n delete 0.0.0.0/1               # и вторая половинка, и ::/1
```

## Удаление

```bash
sudo /usr/local/bin/xr-macos uninstall
```

Команда останавливает демон, откатывает все правки сети и убирает файлы
сервиса (бинарь, плист, профиль, конфиг и рабочее состояние). Сеть машины
возвращается к виду до установки. Профили чужих VPN и их настройки не
трогаются.

## Ограничения

- Сервис не работает одновременно с другим VPN. Запуск отклоняется с
  названной причиной (см. диагностику).
- Без сервера интернет не поднимается напрямую, kill-switch остаётся
  взведённым до ответа сервера. Это же поведение у роутера (fail_closed).
- При пропаже интерфейса туннеля сервис выходит, не открывая прямой выход:
  сеть стоит, пока launchd не поднимет сервис заново (около 10 секунд),
  а руками её возвращает `recover`.
- Адрес туннеля и DNS берутся из внутренней подсети. При необходимости
  меняются в `macos.toml`, секции `[tun]` и `[dnstun]`.
