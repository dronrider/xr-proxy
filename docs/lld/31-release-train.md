# LLD-31. Поезд выката: пакетное слияние мелочи и одна проверка на билд (XR-179)

**Статус:** Реализован (XR-179, коммиты в devkit f291e99..e277ff9), ждёт
обкатки и замера из раздела 6. Отличия реализации от дизайна:

- из развилки раздела 2 выбран вариант (а), git-тег `deployed`; имена команд
  `merge --train` и `ship`;
- тег двигает не только `ship`, а каждая точка выката, включая одиночный
  merge и revert с повторным выкатом: иначе окно поезда тащило бы за собой
  давно выкаченные задачи;
- добавилась защита от осиротевших задач (код в окне выката есть, а строка
  ушла из In progress мимо ship): merge и ship отказывают, status показывает
  аномалию, revert такой задачи не запускает деплой;
- коммит-откат распознаётся по префиксу `revert` либо слову «откат» целиком,
  поэтому своё сообщение отката через `-m` обязано содержать ID и слово
  «откат» (конвенция в README shipctl);
- предел защиты: задача, закрытая в архив мимо ship, для состава невидима,
  поездные задачи закрываются только из Check (README shipctl).
**Область:** devkit (`shipctl`: режим накопления у `merge`, команда выката
поезда, очередь в `status`; `RULES.board.md`: инвариант очереди и критерии
отбора в пачку). Код xr-proxy не меняется, проект даёт боль и обкатку:
бэклог с длинным хвостом мелочи и дорогой выкат приложения.
**Зависимости:** `shipctl` и `taskctl` из devkit (текущий позадачный конвейер),
`RULES.board.md` пп. 5-8 (очередь, Check, провал проверки, автономия).

---

## 0. Проблема

Конвейер устроен позадачно: слияние склеено с выкатом, а `shipctl merge`
требует пустую секцию Check. Пока задача ждёт проверки на проде (а
пользовательская проверка занимает дни), следующая не может даже слиться.
Очередь сериализуется не на работе агента, а на человеке.

Для мелочи это делает полный цикл дороже самой правки. Каждая задача ценой S
тащит фиксированную обвязку: вход агента в контекст репозитория, merge, сборку,
подпись, раскладку APK в канал обновлений, установку на устройство и ручную
проверку. На доске xr-proxy при этом 102 задачи в бэклоге, из них 13 ценой S и
43 ценой M, а 87 лежат в полосе P3 (среди них 8 живых багов). При позадачном
конвейере этот хвост экономически мёртв: до задачи «ошибка обрезается тостом»
руки не дойдут никогда, потому что цикл стоит дороже правки.

Де-факто пачки уже случаются, процесс их просто не признаёт: задачи берутся
в работу группой (XR-118, XR-095, XR-099 «в работу пачкой»), а на доске
goonies в Check одновременно стоят четыре задачи. Инвариант «непроверенная
задача одна» нарушается явочным порядком, и лучше его честно переопределить,
чем закрывать глаза.

## 1. Идея: один непроверенный выкат вместо одной непроверенной задачи

Инвариант очереди ослабляется ровно на один шаг: непроверенным в каждый момент
остаётся **один выкат**, но выкат может нести несколько задач. Разработка и
ревью остаются позадачными (своя ветка, свой раздел «Ревью», свои тесты),
батчатся только три хвостовых шага: слияние-накопление, выкат и проверка.

- Задачи сливаются в main по одной, каждая через полные предусловия merge
  (тесты, ревью без открытых замечаний, ребейз, fast-forward), но без выката.
  Так в main накапливается поезд.
- Один выкат везёт весь поезд: одна сборка, одна подпись, одна раскладка в
  канал. Все задачи поезда разом переходят в Check.
- Проверка идёт на одном билде: одна установка, N сценариев. Агентские
  сценарии агент прогоняет сам, пользовательские человек проходит за одну
  сессию.
- Гранулярность отката сохраняется: коммиты несут ID в subject, провалившаяся
  задача откатывается точечно через `shipctl revert`, остальной поезд остаётся
  на проде.

Что теряется: моментальная атрибуция «что именно сломалось». Её возвращают
позадачные сценарии проверки, а регресс вне сценариев разбирается перебором
ID поезда, поэтому размер поезда ограничен (раздел 3).

## 2. Механика shipctl

Три изменения, всё остальное (предусловия merge, revert, автономия) работает
как сейчас.

1. **`merge <ID> --train`** (имя флага обсуждаемо, вариант `--no-deploy`):
   те же предусловия и шаги, что у обычного merge, кроме двух отличий: выкат
   не выполняется, задача не переводится в Check. Проверка «секция Check
   пуста» для поезда сохраняется: докидывать в поезд, пока прошлый выкат не
   проверен, нельзя, иначе непроверенных выката станет два.
2. **`ship` (новая команда, вариант имени `deploy`)**: катит команду выката из
   `.devkit/deploy.local` один раз и переводит в Check все задачи поезда,
   каждая со ссылкой на свой сценарий. Пустой поезд это чистая ошибка.
3. **`status`** показывает поезд: какие задачи слиты и ждут выката.

Откуда shipctl знает состав поезда. Источник правды это git: задачи поезда
находятся по ID в subject коммитов main после точки последнего выката. Точку
надо где-то держать, развилка такая:

- **(а) git-тег выката** (рекомендуется): `ship` после успешного деплоя
  двигает лёгкий тег (условно `deployed`) на выкаченный коммит и пушит его.
  Состав поезда это ID из `git log deployed..main`. Ничего нового на доске,
  переживает клоны и вторую машину, revert границу не путает.
- (б) пометка в строке задачи на доске (как `[блок: ...]`). Виднее человеку,
  но появляется третье место состояния (доска, git, теперь ещё пометки) и
  правка taskctl.

Мелочь, закоммиченная в main напрямую (без строки на доске, п. 1 правил),
уезжает поездом попутно, как и сейчас между одиночными выкатами.

## 3. Критерии отбора в пачку (уходят в RULES.board.md)

Поезд не отменяет одиночный флоу, а дополняет его. Крупная или рискованная
задача едет одна, как раньше. В поезд берётся то, что удовлетворяет всем
пунктам сразу:

- одно приложение: в монорепо поезд не смешивает Android, сервер и роутерный
  клиент, у каждого свой поезд и свой выкат;
- задачи независимые: не трогают одни и те же файлы и не связаны по смыслу
  (правка A не меняет поведение, которое проверяет сценарий B);
- цена S или M, неопределённость снята; всё, что тянет на ветку с длинной
  историей, в поезд не годится;
- у каждой задачи готов сценарий проверки, желательно агентский: на пачке
  именно агентские сценарии делают проверку дешёвой;
- размер поезда 3-5 задач. Верхняя граница это цена разбора регресса, который
  не покрыт ни одним сценарием: его ищут перебором задач поезда.

## 4. Провал проверки

Как в п. 7 правил, с поправкой на пачку. Если сценарий одной задачи из поезда
провалился, прод чинится сразу: `shipctl revert <ID>` откатывает только её
коммиты и повторяет выкат (в него уезжает остальной поезд, уже проверенный
или ждущий проверки). Задача возвращается в In progress, остальные задачи
поезда живут своим чередом. Очередь (новые слияния в следующий поезд) стоит,
пока прод не починен.

Регресс, не пойманный ни одним сценарием, разбирается перебором ID поезда от
самой подозрительной задачи; на размере 3-5 это терпимо, и это осознанная
плата за пачку.

## 5. Автономный режим

При `autonomous = true` инициатива та же, что в п. 8 правил, плюс решение
«копить или катить»: агент сливает готовые задачи в поезд и запускает `ship`,
когда пачка набрана (критерии раздела 3 исчерпаны: готовых кандидатов в бэклоге
больше нет или поезд достиг верхней границы). Порог не выдерживается ради
порога: единственная готовая задача не ждёт попутчиков, а едет одна, поезд
это оптимизация, не очередь ожидания. `ship` в автономном режиме пушит и
катит сам, как merge сейчас.

## 6. Замер (критерий успеха)

Решение о том, приживается ли механизм, принимается по данным первых двух
поездов, а не по ощущениям:

- расход агента на задачу в поезде против средней одиночной задачи той же
  цены по истории архива (сессии, примерный расход токенов по данным Claude
  Code за сессию);
- число ручных циклов «собери, поставь, проверь» у пользователя: ожидание
  минус 60-80% при поезде из 3-5 задач;
- календарное время от готовности первой задачи пачки до закрытия последней.

Итог замера фиксируется в этом LLD после обкатки.
