## 0. Рамка для тех, кто видит это впервые

Android уже гоняет движок `xr-core` в userspace поверх TUN: `VpnService` отдаёт
сырые IP-пакеты, приложение через JNI (`xr-android-jni`, 43 функции
`Java_..._native*`) кормит их в `PacketQueue`, `smoltcp` держит TCP-стейт-машины,
установленные соединения релеятся в обфусцированный mux-туннель до VPS. iOS
повторяет ровно ту же схему, только вместо `VpnService`+TUN там
`NEPacketTunnelProvider`+`packetFlow` (тот же обмен сырыми IP-пакетами), а вместо
JNI нужен другой мост из Rust в Swift.

Спайк отвечает на три вопроса:

1. Собирается ли `xr-core` под `aarch64-apple-ios` и какие зависимости мешают
   (раздел 1, 2).
2. Какой мост ставить вместо JNI: C FFI или UniFFI (раздел 3).
3. Влезает ли движок в жёсткий лимит памяти Network Extension (раздел 4, это
   ключевая развилка спайка).

## 1. Что проверено на этой машине, а что требует Xcode

Окружение спайка это macOS с установленными только Command Line Tools: полного
Xcode и iphoneos SDK нет. Это разделяет работу на проверяемое здесь и требующее
машины с Xcode.

**Проверено реальными прогонами (вывод в файле задачи `docs/tasks/XR-272.md`):**

- `xcode-select -p` показывает `/Library/Developer/CommandLineTools`,
  `xcrun --sdk iphoneos --show-sdk-path` падает с `SDK "iphoneos" cannot be
  located`. Полного Xcode нет.
- `rustup target add aarch64-apple-ios` и `aarch64-apple-ios-sim` ставятся без
  Xcode (rustup качает только прекомпилированный `rust-std`), exit 0.
- `cargo build -p xr-core --target aarch64-apple-ios --lib` без обхода падает на
  `build.rs` крейта `ring`: его `cc`-шаг зовёт `xcrun --show-sdk-path --sdk
  iphoneos`, а SDK нет. При этом ДО падения успевают компилироваться под
  iOS-таргет `tokio`, `serde`, `tracing`, `der`, `ed25519`, `rand_chacha`,
  `heapless`, `serde_json` и Rust-часть самого `ring`. Барьер не в Rust-коде, а
  в отсутствии iOS SDK для ассемблера `ring`.
- С прозрачным обходом `SDKROOT=$(xcrun --sdk macosx --show-sdk-path)` (даём
  `cc` присутствующий macOS SDK как sysroot, чтобы обойти падающий вызов
  `xcrun` для iphoneos) весь дерево зависимостей И сам `xr-core` компилируются
  под таргет: получается `libxr_core.rlib` на 42 МБ, объекты `ring` это `Mach-O
  64-bit object arm64`. Это доказывает: Rust-несовместимостей у `xr-core` и его
  зависимостей под `aarch64-apple-ios` нет.

Обход через macOS SDK это диагностика совместимости, а не годная iOS-сборка:
объекты собраны против заголовков macOS с iOS-триплетом, платформенные load
commands и availability будут не те. Он доказывает только компиляцию
Rust-исходников под таргет.

**Требует машины с Xcode (здесь непроверяемо, помечено честно):**

- Реальная сборка `ring` (asm + C) под настоящий iphoneos SDK. Риск низкий:
  таргет у `ring` поддержан, на macOS-шиме asm arm64 собрался.
- Финальная линковка `staticlib` `xr-ios-ffi` в таргет Network Extension
  (нужны iOS-библиотеки и линкер из Xcode). Для `--lib` (rlib/staticlib)
  линковки нет, поэтому здесь до неё и не доходит.
- Замер реальной памяти движка в NE (Instruments Allocations, footprint,
  поведение jetsam). Это ключевая непроверяемая часть, см. раздел 4.6.
- Интеграция `NEPacketTunnelProvider`: проводка `packetFlow.readPackets`/
  `writePackets` к `PacketQueue`.
- Генерация C-заголовка (`cbindgen`) и Swift-модуля.

## 2. Зависимости xr-core под iOS

Крипто-бэкенд в дереве `xr-core` это `ring` (через `reqwest` с
`rustls-tls` и через `xr-proto`), а не `aws-lc-rs`. Проверено `cargo tree -p
xr-core -i ring` (даёт цепочку через `rustls`) и `cargo tree -p xr-core -i
aws-lc-rs` (пусто). Это удача: `aws-lc-rs` кросс-компилится под iOS заметно
тяжелее (CMake, свой C-стек), а он в дереве только на серверной стороне
(`xr-relay`/`xr-server`), не у клиента.

| Зависимость | C-код / платформа | Под iOS |
|---|---|---|
| `ring` | asm + C через `cc`, нужен iphoneos SDK | tier-2 таргет, собралось (asm arm64) |
| `rustls` + `rustls-webpki` | чистый Rust поверх `ring` | ок |
| `tokio` | чистый Rust (эпол/kqueue через `mio`, у Darwin kqueue) | ок |
| `smoltcp` | чистый Rust, `default-features=false` | ок |
| `reqwest` (`rustls-tls`, без нативного TLS) | чистый Rust | ок |
| `ed25519-dalek`, `sha2`, `base64`, `rand`, `toml`, `serde(_json)` | чистый Rust | ок |
| `tracing-subscriber` (`std`, `registry`) | чистый Rust | ок |
| `libc` | биндинги POSIX/Darwin | ок, см. ниже |
| `jni` | Android-only | НЕ зависимость `xr-core` |

Подтверждено, что `xr-core` не тянет `jni`: это отдельный крейт `xr-android-jni`
(`crate-type = cdylib`, зависит от `xr-core`), сам `xr-core` про JNI не знает.
Для iOS место `xr-android-jni` займёт `xr-ios-ffi` (раздел 3).

Платформенное в самом `xr-core` (компилируется и семантически валидно на
Darwin):

- `session.rs`: `libc::setsockopt(IPPROTO_TCP, TCP_MAXSEG, ...)` для MSS-клампа
  1220 на исходящих сокетах. `TCP_MAXSEG` есть на Darwin.
- `sync.rs` (клиент файлообмена): `libc::statvfs` и `libc::EXDEV` под
  `#[cfg(unix)]` для проверки места и кросс-девайс rename. POSIX, есть на iOS
  (в песочнице контейнера приложения).
- `journal_bridge.rs`: слой подписчика `tracing`, комментарий в коде уже
  помечает его как общий для Android и iOS (XR-237). Порт берёт его без правок.

Андроид-специфики в ядре нет: единственная точка это `ProtectSocketFn`
(host-callback, раздел 3.5), она инъекция снаружи, а не платформенный код внутри.

## 3. Мост вместо JNI

### 3.1 Что уже есть

`xr-android-jni` это тонкий адаптер: 43 функции `Java_..._native*`, которые в
основном принимают и возвращают JSON-строки и байтовые буферы, а всю логику
(serde-разбор, сеть, движок) держит `xr-core`. Граница уже
«строково-байтовая»: тяжёлое типизирование живёт внутри ядра, через FFI ездят
строки и буферы. Список того, что порт должен пробросить (по группам, из
`xr-android-jni/src/lib.rs`):

- Жизненный цикл движка: `buildConfig`, `start`, `stop`, `onNetworkChanged`,
  `getState`, `getStats`.
- Пакетный путь: `pushPacket`, `popPacket` (горячий, мелкие буферы).
- Онбординг: `parseInviteLink`, `fetchInviteInfo`, `applyInvite`.
- Пресеты и правила: `refreshPreset`, `cachedPreset`, `listPresets`,
  `mergedToml`, `applyUserRules`, `classifyPattern`.
- Здоровье: `healthUpdate`, `healthFreeze`, `healthReset`.
- Журнал: `journalInit`, `journalLog`, `journalTail`, `journalDump`,
  `journalClear`.
- Trusted-сети: `ssidMatches`, `normalizeSsid`.
- Обновление: `checkUpdate`, `verifyApk` (на iOS обновление идёт через App
  Store, эта пара, скорее всего, в порт не поедет).
- Файлообмен: `listShares`, `inviteShares`, `fetchManifest`, `downloadFile`,
  `planSync`, `syncShare`, `importUrl` и остальной блок `sync`.

### 3.2 Решение: C FFI через cbindgen, отдельный крейт xr-ios-ffi

Мост это новый крейт `xr-ios-ffi` (`crate-type = ["staticlib"]`), структурно
параллельный `xr-android-jni` (`cdylib`): тонкие `extern "C"`-шлюзы поверх
`xr-core`, заголовок генерируется `cbindgen`, а на стороне Swift пишется один
тонкий фасад `XrCore.swift`, который прячет весь C-interop (перевод
`String <-> *const c_char`, владение и `xr_free_string`, байтовые буферы) в одном
месте. Оба моста остаются тонкими адаптерами над общим ядром: одна ментальная
модель, вся логика только в `xr-core`.

Контур C-границы:

- Вход строкой: `*const c_char` (UTF-8, владелец Swift), длина по `\0` или явным
  `len` для байтов.
- Выход строкой: `*mut c_char`, владелец Rust, освобождается парной
  `xr_free_string(*mut c_char)`. Ошибки едут тем же JSON-конвертом, что и в JNI.
- Пакетный путь: `xr_push_packet(*const u8, usize)` и
  `xr_pop_packet(*mut u8, usize) -> isize` с явным владением буфера у Swift,
  чтобы на горячем мелкобуферном пути не плодить аллокации на вызов.

Объём: около 43 `extern "C"`-функций плюс `xr_free_string`, плюс один
Swift-фасад. Это тот же порядок, что уже написан для JNI.

### 3.3 Почему не UniFFI

UniFFI генерирует и Rust-скаффолд, и идиоматический Swift по `.udl` или
проц-макросам: типизированные записи, enum-ы, ошибки, callback-интерфейсы,
async. Это настоящие плюсы, и в `xr-core` даже осталась объявленная, но
неиспользуемая optional-зависимость `uniffi` с фичей `uniffi` (задел, который
так и не развернули: `grep` по `xr-core/src` не находит ни одного использования).

UniFFI здесь всё же проигрывает C FFI:

- Горячий пакетный путь (`pushPacket`/`popPacket`, частые мелкие буферы) через
  UniFFI ездит `RustBuffer`-ом с копией на каждый вызов; C-граница даёт явное
  владение буфером без копии.
- Второй кодоген в сборке (UniFFI-биндген) против одного `cbindgen`, который и
  так лёгкий.
- Async-модель UniFFI хочет свой foreign executor и конфликтует с собственным
  `tokio`-рантаймом, который движок поднимает сам (как на Android).
- Главный плюс UniFFI, богатый типизированный marshalling, приглушён: граница
  уже строковая (JSON + serde внутри ядра), типизировать на границе нечего.
- Под жёстким лимитом памяти NE (раздел 4) явный C даёт дисциплину аллокаций,
  которой у сгенерированного UniFFI-слоя (свой object registry, per-call
  аллокации) нет.

Первые два довода не с чужих слов: на игрушечном крейте той же формы
(строковая функция, `Vec<u8>` в обе стороны, callback-интерфейс с
`protect_socket` и `resolve_domain`) UniFFI 0.29.5 собрался и под
`aarch64-apple-darwin`, и под `aarch64-apple-ios`, выдал 771 строку Swift плюс
C-заголовок на 625 строк и modulemap, а колбэк из Rust в Swift отработал живьём,
не только оттипизировался. Там же видна цена: `Vec<u8>` едет не буфером, а
сериализацией побайтовым циклом (сам `uniffi_core` помечает это как «future
work»), то есть три копии на `push_packet` и две на `pop_packet`, и в мобильный
бинарь приезжает 44 транзитивных крейта рантайма. Контрол-плейну на строках это
безразлично, пакетному пути нет, и это главный довод.

Рекомендация по спящей фиче: `uniffi` в `xr-core` вычистить как источник
путаницы (либо развернуть, если однажды решение развернут, но спайк выбирает
C FFI).

### 3.4 protect(): андроид-специфику держим вне ядра

`xr-core` протектит исходящие сокеты через инъекцию `ProtectSocketFn =
Arc<dyn Fn(i32) -> bool + Send + Sync>` (в `session.rs`), которую хост передаёт в
`VpnEngine::start`. На Android это `VpnService.protect(fd)` (сокет туннеля не
должен идти сам в себя). На iOS у `NEPacketTunnelProvider` сокеты, созданные
расширением, по умолчанию идут мимо туннеля, поэтому iOS-хост передаёт
тривиальное замыкание `|_| true`. Ядро менять не нужно: DI-абстракция уже
готова к iOS, а `VpnService.protect` остаётся в андроид-обёртке, как и сейчас
(`onboarding.rs` уже отдельно обсуждает семантику protect для проб онбординга).

## 4. Память Network Extension (ключевая развилка)

### 4.1 Лимит и его неопределённость

`NEPacketTunnelProvider` живёт под жёстким лимитом памяти, который выбивает
процесс через jetsam с причиной `per-process-limit` (не мягкое предупреждение).
По developer-форумам и openradar: iOS 14 и раньше это 15 МБ, iOS 15 и новее это
50 МБ (50 MiB). Apple не документирует лимит как фиксированную константу и прямо
предупреждает, что значение менялось и может меняться, то есть цифра
эмпирическая и версионно-зависимая, вот источник неопределённости. Проектируем к
консервативным 15 МБ как запасу прочности, а 50 МБ считаем headroom, на который
нельзя опираться.

### 4.2 Движок живёт только в процессе расширения

`packetFlow` доступен внутри `NEPacketTunnelProvider`, отгрузить обработку
пакетов в основной процесс приложения нельзя. Значит весь пик памяти движка это
бюджет расширения, и бюджет жёсткий.

### 4.3 Пик памяти по коду

Числа взяты из кода `xr-core`:

- На активное TCP-соединение `smoltcp`-буферы rx+tx: `add_tcp_socket(65535,
  65535)` в `engine.rs`, то есть около 128 КБ, аллокейтся на SYN сразу
  (`vec![0u8; 65535]` дважды).
- Каналы сессии: `to_relay`/`from_relay` это `mpsc::channel(512)`, буфер на
  итерацию до 32 КБ (`vec![0u8; 32768]`). В потоке объём ограничен оконным flow
  control mux: `STREAM_RECV_WINDOW = 1 MiB` на стрим в каждую сторону
  (`xr-proto/src/mux.rs`). Насыщенная передачей сессия это порядка 1-2 MiB
  буферов.
- Клиентского капа на число одновременных сессий НЕТ: `sessions: HashMap`
  растёт по каждому SYN, семафора нет (в `engine.rs`/`session.rs` не найден).
  `max_connections = 256` это серверный семафор в конфиге, к клиенту он не
  относится.
- Очереди пакетов: три `VecDeque` (`inbound`, `smol_outbound`, `tun_outbound`)
  с бэкпрешером на 4096 пакетов каждая, пакет до MTU 1500. Потолок около 18 МБ
  как транзиентный всплеск, стационар почти пуст.
- `tokio`: на Android `new_multi_thread().worker_threads(4)` (стеки воркеров).
- `reqwest`-пул + `rustls` на контрол-плейне (пресеты, инвайты, апдейт): TLS
  по десяткам КБ на соединение.

Итог оценки: и «много одновременных активных передач» (десяток параллельных
скачиваний это порядка 10-20 MiB только на потоковых окнах), и «много активных
соединений» (сотня прокачавших трафик это около 13 МБ только на
`smoltcp`-буферах) поодиночке пробивают консервативные 15 МБ и напрягают 50 МБ.
Простаивающее соединение при этом стоит копейки, и для расчёта это не мелочь:
меряный расклад в 4.7.

### 4.4 Вердикт

Движок в дефолтной раскладке (рассчитанной на роутер и Android, где памяти
вдоволь) НЕ влезает безопасно в консервативный бюджет NE под нагрузкой и рискует
jetsam даже против 50 МБ на активном устройстве. Но архитектурно он совместим:
все рычаги уже параметризованы (размеры буферов это аргументы функций, глубины
каналов и окна это константы, кап сессий добавляется семафором, рантайм
конфигурируется). Влезание это профиль-тюнинг под iOS, а не переписывание, и
риск низкий, потому что дефолты для роутера и Android не трогаются.

### 4.5 Рычаги: что резать под iOS-профиль

С числами и компромиссом, по убыванию эффекта:

1. `smoltcp`-буферы 64/64 КБ -> 16/16 КБ (аргументы `add_tcp_socket`). Сто
   соединений тогда это около 3.2 МБ вместо 12.8 МБ. Компромисс: меньше окно,
   ниже потолок скорости одного соединения на каналах с высоким BDP, на мобиле
   приемлемо. Главный рычаг.
2. Кап одновременных клиентских сессий семафором (нового нет), например 128:
   `128 * 32 КБ = 4 МБ`. Компромисс: всплеск соединений выше капа притормаживает,
   а не съедает память бесконтрольно.
3. `STREAM_RECV_WINDOW` 1 MiB -> 256 KiB (константа в `xr-proto/src/mux.rs`).
   Окно раздаёт получатель через `MUX_FLAG_WINDOW`/`WindowUpdate`, поэтому
   iOS-клиент может анонсировать меньшее окно без слома протокола (отправитель
   его уважает). Для upload сервер анонсирует своё окно, поэтому дополнительно
   урезать `mpsc::channel(512)` до, например, 64. Значение сделать
   конфигурируемым, а не хардкодом.
4. Очереди пакетов 4096 -> 512: `3 * 512 * 1500` это около 2.3 МБ потолка вместо
   18. NE и так читает пакеты пачками, глубокий бэклог бесполезен.
5. `tokio` в расширении: `current_thread` или `worker_threads(1..2)` вместо 4,
   меньше стеков и планировщика.
6. Переиспользовать буфер в relay-петле вместо `vec![0u8; 32768]` на каждой
   итерации (пул буферов): меньше churn аллокатора и фрагментации, что под
   жёстким лимитом важно само по себе.

### 4.6 Как валидировать (только на Xcode-машине)

Замер Instruments Allocations и `os_proc_available_memory`/footprint под
нагрузкой (много параллельных соединений плюс крупные передачи), проверка
отсутствия jetsam в диагностике. Здесь это непроверяемо, оценка выше по коду это
верхняя граница, а не измерение.

### 4.7 Что померено харнессом на macOS

Оценка по коду считает аллокации, а лимит расширения считается по грязным
страницам, и это разные числа. Разницу меряет харнесс
`xr-core/tests/ios_memory_budget.rs`: он поднимает движок на локальном
туннельном сервере и снимает RSS процесса. Прогон
`cargo test -p xr-core --test ios_memory_budget -- --nocapture`, отладочная
сборка, macOS arm64:

| Что | Сколько |
|---|---|
| холостой туннель: движок с прогретым пулом на 4 mux-соединения | +3.4 МБ |
| 256 сессий, буферы заведены и не тронуты | +0.4 МБ, то есть 2 КиБ на сессию |
| 64 сессии, буферы прокачаны целиком | +8.0 МБ, то есть ровно 128 КиБ на сессию |

Отсюда поправка к 4.3: `vec![0u8; 65535]` приходит из calloc, и до первой записи
резидентной памяти не занимает, поэтому сотня открытых, но молчащих соединений
стоит не 13 МБ, а сотни килобайт. Платит соединение, которое реально прокачало
трафик, и платит полностью: страницы буфера остаются грязными до конца сессии,
отдавать их некому. Значит под лимит подводят не открытые сокеты, а активные
передачи: первым рычагом остаётся размер буферов (4.5.1), а кап сессий (4.5.2)
работает страховкой от худшего случая, а не повседневной экономией.

Числа сняты на macOS, iOS считает footprint по своим правилам (сжатая память,
IOKit), поэтому переносить их на устройство один в один нельзя и замер
Instruments из 4.6 они не заменяют. Порядок величины они задают, а границы
харнесс держит сам: буферы сессии вынесены из литералов `engine.rs` в константы
`SESSION_RX_BUF`/`SESSION_TX_BUF`, и подними их кто-нибудь без пересчёта
бюджета, тест падает с текстом про iOS.

## 5. План порта

Фазы, порядок по зависимостям:

1. Крейт `xr-ios-ffi` (`staticlib`, `extern "C"`-шлюзы поверх `xr-core`,
   `cbindgen`-заголовок). Тесты extern-функций гоняются на хосте: staticlib
   собирается и на macOS, юнит проверяет round-trip строки и байтового буфера
   без Xcode.
2. iOS-профиль движка (рычаги 4.5) как конфиг или фича сборки. Дефолты роутера и
   Android не трогаем.
3. Xcode-проект: приложение плюс `NEPacketTunnelProvider`, проводка `packetFlow`
   к `PacketQueue`, `ProtectSocketFn = |_| true`, собственный `tokio`-рантайм в
   расширении.
4. Замер памяти на устройстве, доводка рычагов по факту.
5. Онбординг и UI повторяют Android поверх тех же функций `xr-core` (словари
   строк из XR-092, `client_config`/`presets`/`health` из XR-271).

Фаза 1 и iOS-профиль (2) делаются и проверяются в этом репозитории без Xcode.
Фазы 3 и 4 требуют машины с Xcode.

## 6. Риски

- `ring` под реальным iphoneos SDK: здесь собран только через macOS-шим. Риск
  низкий (таргет поддержан, asm arm64 собрался), но проверить на Xcode.
- Память NE (главный риск): средний-высокий, снимается тюнингом (4.5) плюс
  замером (4.6). Проектируем к 15 МБ.
- jetsam недокументирован и версионно-зависим: не закладываться на 50 МБ.
- Дрейф двух мостов (JNI и C FFI) поверх одного ядра: держать оба тонкими, вся
  логика только в `xr-core`, паритет проверять тем, что обе обёртки зовут одни
  функции ядра.
- Отладка NE тяжёлая (лимит, jetsam-логи): наблюдаемость закладывать сразу,
  общий `journal_bridge` (XR-237) для этого уже есть.

## 7. Дизайн-решения (сводка)

- Мост это C FFI через `cbindgen`, не UniFFI: граница уже строковая, горячий
  пакетный путь без копий, без второго кодогена и чужой async-модели, дисциплина
  аллокаций под лимитом NE (раздел 3.3). Спящую фичу `uniffi` в `xr-core`
  вычистить.
- FFI живёт в отдельном крейте `xr-ios-ffi` (staticlib), параллельно
  `xr-android-jni`, а не внутри `xr-core`: ядро остаётся чистым, оба моста тонкие.
- Под iOS не форкаем движок, а вводим iOS-профиль тюнинга существующих рычагов
  (буферы, окна, кап сессий, рантайм): дефолты роутера и Android не меняются.
- `protect()` на iOS это no-op через уже существующую DI `ProtectSocketFn`,
  андроид-специфика (`VpnService.protect`) остаётся в обёртке.
- Память проектируем к консервативным 15 МБ, 50 МБ считаем headroom, финальную
  цифру снимаем замером на устройстве.
