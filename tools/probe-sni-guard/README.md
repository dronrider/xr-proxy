# Пробник защиты разбора SNI (XR-205)

Стучится в роутер с LAN-машины теми началами соединения, на которых `xr-client`
раньше падал: обрезанный TLS-рекорд (заголовок обещает длину меньше самого
заголовка handshake) и корректный ClientHello с именем в SNI длиннее предела
домена. До правки XR-205 первый же стук абортил процесс, procd поднимал его
заново, и все живые соединения LAN рвались.

```
ноут (LAN-клиент) -> роутер (TPROXY, перехват) -> разбор SNI в xr-client
```

## Запуск

```sh
./probe.py <внешний адрес> [порт]
```

Порт по умолчанию 8080. Он должен быть не 80 и не 443 (там решение принимается
по правилам маршрутизации, и путь до кодирования адреса зависит от пресета) и не
совпадать с `listen_port` самого клиента: свой порт правило редиректа выводит из
перехвата, и стук ушёл бы мимо роутера, не дав ни одной строки. Адрес назначения
любой, до ответа соединение всё равно не доживает.

Перехват по всем портам, кроме короткого чёрного списка, делает только
nftables-ветка редиректа, она и стоит на флоте. На роутере с iptables под
перехват идут лишь 80 и 443, и пробник туда не доедет.

## Что смотреть

Сам пробник ничего не проверяет, он только стучится. Итог снимается на роутере:

```sh
ssh -p 8822 root@<роутер> 'pgrep -f /usr/bin/xr-client; tail -3 /etc/xr-proxy/crash.log; logread | tail -40'
```

PID до и после стука один и тот же, новых записей в `crash.log` нет, а в
`logread` на каждый стук легла своя строка отказа: «рекорд короче заголовка
handshake» и «имя 300 байт, больше предела домена». Строки именно про отказ, а
не общее `[SNI: -]`, которое даёт и обычный не-TLS: без них не отличить починку
от того, что стук вообще не дошёл.
